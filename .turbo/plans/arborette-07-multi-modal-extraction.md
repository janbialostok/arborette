# Plan: Multi-Modal Extraction

## Context

The original hypothesis loop assumes every data source is tabular — interventions are deterministic DuckDB queries. This shell extends that to unstructured documents (the concrete case: a contract PDF, where the goal is "accurately extract effective date, termination date, and SLOs"), where an intervention is instead an extraction/classification task. The key design constraint is that Citations (the natural way to get a precise source locator from Claude) and structured outputs (needed to keep the extracted value strictly typed) are mutually incompatible on the Claude API — so this shell's extraction path returns only a typed value and confidence, and provenance is computed separately via a deterministic post-hoc text search, not requested from the model.

### Divergence notes carried from expansion (read before starting)

The codebase has moved further than the shell assumed; two contract items are **already built**, and one intake decision is **not yet modeled**. Fold these in rather than re-deriving them:

1. **Outcome/PRODUCED schema extensions are already implemented (Implementation Step 5 is verify-only).** `domain.VerificationStatus` with the full five-value domain (`verified`/`unverified`/`confirmed`/`corrected`/`rejected`, `internal/domain/domain.go:24-32`) defaulting to `verified` at node creation, `domain.ProvenanceLocator{Page,CharStart,CharEnd}` (`domain.go:73-77`), `Outcome.Provenance` (`domain.go:81-88`), `ProducedEdge.Confidence` + `EpistemicSource` (`domain.go:102-106`), the graph writes `CreateOutcome`/`CreateProduced`/`UpdateOutcomeVerification` (`internal/graph/neo4j.go:90-111,186-205,290-305`, provenance JSON via `marshalProvenance:436-457`), and the query-path's fixed `Confidence: 1.0`/`EpistemicObservational` (`internal/orchestrator/hypothesis.go:258`) all exist and work today. The graph layer needs **no change**; Step 5 is a verification checkpoint, not new construction.

2. **A new PDF text-extraction dependency is required, and it is CGO-free.** No PDF library is in `go.mod`. `github.com/ledongthuc/pdf` is present in the local module cache and is the pre-vetted candidate (pure-Go, no `import "C"`). **It publishes no semver tags** — the cache holds only the pseudo-version `v0.0.0-20220302134840-0c2507a12d80`, so `go get github.com/ledongthuc/pdf@v0.1.1` fails with "unknown revision." Add it with `go get github.com/ledongthuc/pdf@latest` (resolves to that pseudo-version) or pin the pseudo-version explicitly. Because it is pure-Go the CGO boundary does **not** force any particular placement; the choice below to keep PDF *parsing* in the sandbox is a structural one (document parsing sits beside tabular parsing in the compute node), not a CGO requirement. The library is imported **only inside the sandbox package**; the orchestrator obtains per-page text through a sandbox endpoint (Step 4) and never imports the library.

3. **Extraction runs orchestrator-side; the sandbox keeps only a deterministic PDF-text pass.** (Design decision taken at expansion, deviating from the deleted shell's "extract intervention-execution path in the Sandbox Execution service.") The sandbox is today a stateless, deterministic, LLM-free compute node, and every orchestrator→sandbox call is bounded by `defaultSandboxTimeout = 2 * time.Minute` (`internal/orchestrator/sandboxclient.go:17`) — an adaptive-thinking extraction over an inlined PDF can approach or exceed that and would surface as a sandbox 5xx. So the **Claude extraction call lives in the orchestrator**, whose process already constructs `*llm.Client`, `AnthropicConfig`, and an `*objectstore.Client`. The sandbox's only new document responsibility is a **deterministic per-page text endpoint** (via the PDF library) that serves both the intake sample (Step 2) and provenance (Step 4). Both document LLM calls (field-introspection and extraction) then live together in the orchestrator's `llm` package; no Anthropic secret or long-running call is introduced into the sandbox; the sandbox's existing `type=extract` 400 in `handleExecute` (`server.go:133-136`, asserted by `server_test.go:82`) stays as-is because the orchestrator never routes extraction through `Execute`.

   **Interface-seam caveat (do first):** the `Server` does not call the concrete clients directly — it holds narrowing interfaces (`internal/orchestrator/server.go`): `objectStore` (line 76) exposes only `NewKey`/`Put` (**no `Get`**), `claudeClient` (line 45) has only the four existing methods, and `sandboxExecutor` (line 52) only `Introspect`/`Execute`. Widen all three before the new calls will compile: add `Get(ctx, key) (io.ReadCloser, error)` to `objectStore`, `Extract(...)` and `IntrospectDocumentFields(...)` to `claudeClient`, and the `/document/text` method to `sandboxExecutor` (and update the in-package fakes those interfaces exist for). Steps 2/3/4/6 depend on this.

4. **Risk — document goals do not fit the `EvaluationMatrix` intake model, and this reaches the persistence and read layers.** Intake today is hard-wired to the tabular objective: `handleSubmitGoal` calls `GenerateEvaluationMatrix` → `dryRunObjective` repair loop → persists `store.Goal.EvaluationMatrix` (`internal/orchestrator/submit.go:75-115`). A document goal has no aggregation/direction to optimize — its targets are a *set of fields to extract accurately*. Fixing this is **more than a struct field** and must be treated as explicit sub-steps (Step 2): (a) `internal/store/migrations/0002_goal_registry.up.sql:4` declares `evaluation_matrix jsonb NOT NULL` and `GoalRegistry.Insert` (`internal/store/goalregistry.go:33`) marshals it unconditionally — a new **numbered migration** must relax that column to nullable and add a `target_fields jsonb` column (or equivalent). The migrations directory already runs contiguously `0001`–`0006` (`0003` is `0003_audit`), embedded via `go:embed *.sql` into golang-migrate (`migrations/migrations.go`), which parses the leading integer as the version — so the new file must be the next free ordinal, **`0007_document_goals.up.sql`/`.down.sql`** (a duplicate version 3 fails startup for every service, not just the document path); (b) `GoalRegistry.Get`/`List` (`goalregistry.go:60,86`) `json.Unmarshal` the matrix with **no null guard**, so once one document goal exists, `handleListGoals` (the web-UI goal list) errors for every caller unless the decode tolerates a null/absent matrix; (c) `runLoop` must branch on goal kind before the tabular objective path so `pinObjective` does not return `errNoObjective` and fail a document run (the `EvaluationMatrix` value is nil-safe, so this is a control-flow branch, not a panic guard). Resolve this early: Steps 2 and 6 both depend on it.

## Pattern Survey

### Analogous Features
- `internal/sandbox/filesource.go:41-63` — `FileSource` is the exact template a document source mirrors: struct holds `objects`/`dataSourceRef`/limits, `NewFileSource` primitive constructor, `var _ datasource.DataSource = (*FileSource)(nil)` compile-time assertion, `Kind()` returns `KindTabular`. A `DocumentSource` returning `KindDocument` slots in beside it.
- `internal/sandbox/filesource.go:135-211` — `stage()`/`download()` is the reusable object-store→temp-file staging pattern: `os.MkdirTemp`, deferred `cleanup`, `download` with `io.LimitReader(r, max+1)` over-limit detection and `ctxReader` cancellation. The extract path needs the same staged local PDF file (both to send to the model and to run the deterministic provenance text-search over).
- `internal/sandbox/filesource.go:238-249` — `tableFunction(ref)` dispatches by lowercased extension (`.csv`/`.parquet`) and returns `errUnsupportedFormat` otherwise. A document source dispatches `.pdf` the same way; the two readers must agree on which extensions each owns.
- `internal/sandbox/server.go:30-35,107` — `Routes()` and `handleIntrospect` are the pattern a new deterministic document-text endpoint mirrors (route registration + handler + staged-source read). `handleExecute`'s line-133 `Type != InterventionQuery` 400 (`server_test.go:82`) **stays unchanged** under the orchestrator-side-extraction decision — extraction never routes through `Execute`.
- `internal/orchestrator/hypothesis.go:87-165` — `runLoop` (introspect → pin objective → root proposal → baseline Execute → per-candidate expansion) and `processCandidate:171-217` (recursive depth expansion via `defaultDepth`, breadth via `defaultBreadth`). This is where per-field sub-trees branch: today one objective is pinned for the whole tree; the multi-modal design wants one sub-tree per extractable field.
- `internal/llm/client.go:63-124` — the two structured-output calls (`GenerateEvaluationMatrix`, `ProposeInterventionTree`) plus their repair-loop twins, all routing through `complete()`. Document-field-introspection and extraction are new methods in this same seam.
- `internal/graph/neo4j.go:90-111,186-205,290-305` — extract-outcome graph writes already exist and work: `CreateOutcome` marshals `o.Provenance` (nil→null, else JSON), `CreateProduced` writes `confidence`+`epistemic_source`, `UpdateOutcomeVerification` applies HITL status. The graph layer needs no change.

The contract is pre-built for the document shape.
- `internal/domain/domain.go:11-18,71-88,99-106` — `InterventionExtract`, `ProvenanceLocator`, `Outcome.Provenance`, `VerificationUnverified`, `ProducedEdge.EpistemicSource` are all already defined. `writeTriplet` currently hardcodes `InterventionQuery`, `VerificationVerified`, `Confidence:1.0`, `EpistemicObservational` (`hypothesis.go:239,250,258`); the extract path populates the reserved values instead.
- `internal/llm/client.go:312-348` — `complete()` (adaptive thinking + effort + `JSONOutputFormatParam` schema) and `textBlock()`. Note `complete()` takes only a `user string` and hardcodes `NewUserMessage(NewTextBlock(user))` (line 324) — it has **no seam for a document block**, so extraction cannot reuse it as-is (see Step 3 for the required completion variant).
- `internal/llm/schema.go:135-152` — `object()`/`arrayOf()`/`stringProp()`/`enumSchema()` JSON-schema builders with `additionalProperties:false`. The extraction structured-output schema (typed value + confidence) builds from these. Per the grammar-ceiling convention, keep enums small and emit anything recursive/high-cardinality as a JSON-encoded string field (as `evaluationMatrixSchema`'s `value` does).
- `internal/objectstore/client.go:69-95` — `Get(ctx, key) (io.ReadCloser, ...)` streaming read + `IsNotFound(err)` for 404 mapping.
- Anthropic SDK (v1.58.0) document support is present: `message.go:1899` `NewDocumentBlock[Base64PDFSourceParam | PlainTextSourceParam | ContentBlockSourceParam | URLPDFSourceParam]`, `Base64PDFSourceParam:176`, and a Beta Files API `BetaFileService.Upload` (`betafile.go:122`). `CitationsConfigParam` exists (`message.go:801`) but is deliberately unused. No existing `DocumentBlock`/Files/base64 usage in the repo (confirmed).

### Convention Anchors
- **Two hand-kept DTO mirrors, both must be edited**: `internal/sandbox/server.go:40-94` (canonical, snake_case JSON, drives HTTP) and `internal/orchestrator/sandboxclient.go:27-77` (byte-compatible CGO-free copy — the orchestrator must NOT import `internal/sandbox` because of the blank CGO DuckDB import). Any new `ExecuteRequest`/`ExecuteResponse`/`IntrospectResponse` field must be added to **both** structs identically. `hypothesis.go:538` `toSandboxSchema` maps the response DTO into `llm.SandboxSchema`.
- **CGO isolation boundary**: `internal/datasource` is the pure dependency-free contract; DuckDB (CGO) and now the PDF library live only behind the sandbox boundary. Shared types cross to the orchestrator through `internal/domain` (CGO-free), never through `internal/sandbox`.
- **Error→HTTP mapping via sentinels + `writeStageErr`**: `server.go:190-211` maps `errors.Is` sentinels to 400, `objectstore.IsNotFound`→404, else masked 500. New extract-path validation errors follow this. Orchestrator classifies by `SandboxError.Status` (`sandboxclient.go:83-88`, `submit.go:260-276`).
- **Intake repair loop**: `submit.go:85-99` runs dry-run → `RepairEvaluationMatrix` up to `maxObjectiveRepairs` on `isObjectiveValidationFailure`. The document branch mirrors the ingest→Introspect→(LLM fit) structure but replaces the objective dry-run with field-candidate production.
- **LLM prompt grounding + post-hoc deterministic validation**: schemas keep only fixed-cardinality enums; free-form/recursive values are prompt-grounded strings validated deterministically after generation (`schema.go:48-87`, `domain.go:309-343`). The extraction schema (typed value + confidence) follows this.
- **Test conventions**: sandbox `filesource_test.go`/`server_test.go` are integration-gated (`testutil.RequireIntegration` → live MinIO/DuckDB); pure unit tests use `httptest.NewRecorder`. LLM tests use a `fakeMessages` implementing `messagesClient` and build canned `*anthropic.Message` by `json.Unmarshal` of a raw JSON map (`client_test.go:18-49`) — the mandated way to fake SDK responses; it extends directly to a canned extraction response.
- **Config**: `AnthropicConfig{APIKey,Model}` (`config.go:113-116,213-216`); `SandboxConfig.MaxObjectBytes` caps staged objects (`env`/`int64Env` helpers).

### Proposed Alignment
Follow the existing patterns closely — the groundwork for extract is already laid across `internal/datasource`, `internal/domain`, and the whole graph layer (which needs no change). New work: a `DocumentSource` mirroring `FileSource`'s staging/dispatch plus a deterministic per-page text endpoint in the sandbox (paired DTO edits in both mirrors); two new orchestrator `llm` methods through `complete()` (field-introspection + extraction, the latter adding `NewDocumentBlock`); the goal-registry migration + read-path null handling; and a per-field extraction expansion path in the orchestrator that runs in parallel to the tabular `processCandidate` rather than reusing it verbatim. Deviate from the tabular path in exactly two documented places — extraction runs orchestrator-side (not through the 2-minute-bounded sandbox `Execute`), returning only typed value + confidence (no Citations) with provenance computed separately by a deterministic PDF-text pass; keep PDF *parsing* inside the sandbox package for structural consistency with tabular parsing (not a CGO requirement, since the library is pure-Go).

## Implementation Steps

1. **Document `DataSource` implementation + deterministic per-page text endpoint** (`internal/sandbox/documentsource.go` new, `internal/sandbox/server.go`, both DTO mirrors)
   - Mirror `FileSource` (`internal/sandbox/filesource.go:41-63`): a `DocumentSource` struct holding `objects *objectstore.Client`, `dataSourceRef string`, and the max-object-bytes cap; `NewDocumentSource(...)` primitive constructor; `var _ datasource.DataSource = (*DocumentSource)(nil)`; `Kind()` returns `datasource.KindDocument`.
   - Reuse the staging pattern (`stage()`/`download()` at `filesource.go:135-211`: `os.MkdirTemp`, deferred cleanup, `io.LimitReader(r, max+1)` over-limit detection, `ctxReader` context cancellation) to land the PDF as a temp file. Extract to a small shared helper if practical so both sources share it; otherwise duplicate the proven code rather than refactoring `FileSource`.
   - Dispatch by extension the way `tableFunction` (`filesource.go:238-249`) does: this source owns `.pdf`; anything else returns a sentinel (`errUnsupportedFormat` or a new `errUnsupportedDocument`). Keep the tabular/document extension ownership non-overlapping.
   - Add the `.pdf` per-page text-extraction helper here using `github.com/ledongthuc/pdf` (add via `go get github.com/ledongthuc/pdf@latest`, since the module has no semver tags — see Context divergence 2; import only in this package). It reads the staged PDF into an ordered list of per-page plain text (page index → text), the deterministic substrate for both the intake sample (Step 2) and provenance (Step 4).
   - Expose it over HTTP as a new deterministic endpoint — register a route in `Routes()` (`server.go:30-35`) beside `/introspect`/`/execute` (e.g. `POST /document/text`) with a handler mirroring `handleIntrospect`'s stage-and-read shape. Add the request/response DTOs (`{DataSourceRef}` → `{Pages []string}` or a page-offset structure) to **both** `internal/sandbox/server.go` and `internal/orchestrator/sandboxclient.go`, byte-identical per the mirror convention. Map read failures via the sentinel + `writeStageErr` pattern (`server.go:190-211`).

2. **Field-introspection for documents** (`internal/sandbox/server.go`, `internal/orchestrator/submit.go`, `internal/orchestrator/sandboxclient.go`, `internal/store/`, `internal/llm/`)
   - Sandbox side: in `handleIntrospect` (`server.go:107`), construct a `DocumentSource` when the ref is a `.pdf` (kind detection by extension) and return `Schema{Kind: KindDocument}` plus a bounded plain-text **sample** (first page / first N chars from the Step-1 text helper). Add a `Sample string` field to the `IntrospectResponse` DTO — mirrored in **both** `server.go` and `sandboxclient.go`. `Fields` stays empty at sandbox time; field candidates are LLM-derived (the sandbox holds no Claude client).
   - New orchestrator `llm` method `IntrospectDocumentFields(ctx, goalText, sample) ([]Field, error)`: routes through `complete()` with a small structured-output schema built from `schema.go` helpers (`arrayOf(object({name, description}))`, `additionalProperties:false`) returning candidate extractable fields grounded in the goal + sample. New schema in `internal/llm/schema.go`, new system prompt beside the existing ones (`client.go:350+`).
   - **Persistence (Context risk 4 — explicit sub-steps):**
     - New numbered migration `internal/store/migrations/0007_document_goals.up.sql` (+ `.down.sql`) — **`0007`, the next free ordinal** (`0003` is already `0003_audit`; the directory runs contiguously `0001`–`0006`): make `evaluation_matrix` nullable and add a `target_fields jsonb` column (nullable). Follow the ordered-migration convention already in `migrations/`.
     - `internal/store/goalregistry.go`: add a `TargetFields` field to `store.Goal`; make `Insert` (line 33) write a NULL matrix + populated `target_fields` for document goals (and vice-versa for tabular); **null-guard the decode** in `Get` (line 60) and `List` (line 86) so a NULL `evaluation_matrix` unmarshals to a zero value instead of erroring — otherwise `handleListGoals` breaks for all callers once one document goal exists.
   - Orchestrator side: branch `handleSubmitGoal` (`submit.go:65-115`) on `introspect.Schema.Kind`. Tabular → the existing `GenerateEvaluationMatrix` → `dryRunObjective` path unchanged. Document → call `IntrospectDocumentFields`, reject with 422 if zero fields come back, else persist the target fields via the new column; keep the API response (`optimization_function_id`) stable. Covers R2 (partial) and R16.

3. **Extraction call (orchestrator-side)** (`internal/llm/client.go`, `internal/llm/schema.go`, `internal/config/config.go`, `internal/orchestrator/hypothesis.go`)
   - Per Context divergence 3, extraction runs in the **orchestrator**, not the sandbox — the sandbox is untouched here beyond Step 1's text endpoint. New orchestrator `llm` method `Extract(ctx, pdfBytes, field, method) (value map[string]any, confidence float64, err error)`: build `NewUserMessage(NewDocumentBlock(Base64PDFSourceParam(...)), NewTextBlock(instruction))` with a structured-output schema returning **only** typed value + confidence — **no** `CitationsConfigParam`. Use `Base64PDFSourceParam` (inline PDF) for the MVP; note `BetaFileService.Upload` (Files API) as the scale path for large/repeated PDFs.
   - **Completion-path change (required):** `complete()` (`client.go:312`) accepts only a `user string` and builds `NewUserMessage(NewTextBlock(user))` internally — it cannot carry a document block. Introduce a content-accepting variant, e.g. `completeWithContent(ctx, effort, schema, system string, content []anthropic.ContentBlockParamUnion) (string, error)` that holds the same adaptive-thinking + effort + `JSONOutputFormatParam` + stop-reason plumbing, and refactor the existing `complete()` to delegate to it with a single text block (so the four current callers — `GenerateEvaluationMatrix`/`RepairEvaluationMatrix`/`ProposeInterventionTree`/`RepairInterventionTree` — are unchanged in behavior). `Extract` calls the new variant with the document + text blocks.
   - Fetch the raw PDF bytes for the base64 document block via the object store's `Get(ctx, ref)` (opaque bytes — no PDF parsing in the orchestrator; parsing stays behind Step 1's sandbox endpoint). This requires widening the `Server`'s `objectStore` interface to expose `Get` (Context divergence 3 interface-seam caveat) — it currently exposes only `NewKey`/`Put`.
   - The **extraction method** is the sub-tree breadth axis (Step 6): a small prompt-strategy discriminator (kept as a small enum or a prompt-grounded string per the grammar-ceiling convention) that varies the instruction/approach per competing sibling.
   - Reuse the existing `AnthropicConfig`/`Client` already wired into the orchestrator (`submit.go` constructs `s.claude`); no sandbox config change. Covers R17.

4. **Provenance-locator computation (orchestrator-side)** (`internal/orchestrator/hypothesis.go` or a new `internal/orchestrator/provenance.go`)
   - The per-page text of a data source is **run-invariant**, so fetch it **once at run start** — in `runLoop`, beside the introspect call, via Step 1's sandbox `/document/text` endpoint (`SandboxClient`, whose `sandboxExecutor` interface must be widened per Context divergence 3) — and thread the page slice into `processExtractionCandidate` (Step 6). Do **not** re-fetch per node: a breadth-3 × depth-4 sub-tree per field would otherwise re-download and re-parse the whole PDF at every measurement.
   - After each successful `Extract`, run a standalone deterministic pass over that cached per-page text (independent of the Claude call): locate the **first** exact occurrence of the stringified extracted value across pages and record `domain.ProvenanceLocator{Page, CharStart, CharEnd}` (`domain.go:73-77`); yield `nil` when no exact match is found. No fuzzy matching in the MVP.
   - The locator is written onto the outcome in Step 6's write path. Covers R18 (partial — extraction-time locator only; queue/resolution/UI are Shells 08/10).

5. **`Outcome`/`PRODUCED` schema extensions — VERIFY ONLY** (`internal/domain/domain.go`, `internal/graph/neo4j.go`)
   - This step is already implemented (Context divergence 1). Do **not** re-add fields. Verify the domain has the full five-value `VerificationStatus` defaulting to `verified` at node creation, `ProvenanceLocator`, `Outcome.Provenance`, and `ProducedEdge.Confidence`/`EpistemicSource`; verify `CreateOutcome`/`CreateProduced` persist provenance + confidence; verify the query path still writes `Confidence: 1.0`. Confirm nothing in Steps 1-4/6 forces a schema change; if it does, that is a new finding to raise, not a silent edit here.

6. **Per-field hypothesis sub-trees — parallel expansion path** (`internal/orchestrator/hypothesis.go`)
   - Branch `runLoop` (`hypothesis.go:87-165`) on the goal's source kind **before** the tabular objective path (so `pinObjective` does not return `errNoObjective` for a document goal). Tabular → the existing single pinned-objective tree, unchanged. Document → fetch the run-invariant per-page text once (Step 4), then iterate the goal's extraction target fields (from Step 2's persistence); each field is its own sub-tree.
   - **Do not reuse `processCandidate` verbatim** — it is welded to the tabular objective model: `processCandidate` (`hypothesis.go:171-217`) takes an `objective` and calls `executeRequestFor` (hardcodes `InterventionQuery` + `obj.aggregation`/`expr`/`label`), `numericValue(resp.Value, obj.label)` (`:512`), `improves(baseline, value, obj.direction)` (`:473`), and `constraintsSatisfied(goal.EvaluationMatrix.Constraints, ...)` (`:483`). A document goal has none of these. Write a **parallel expansion function** (e.g. `processExtractionCandidate`) that takes the field + the cached per-page text and mirrors the recursion/pruning shape but drives the extraction measurement (Step 3 `Extract` + Step 4 provenance over the cached text) instead of `sandbox.Execute`, and **skips the constraint check entirely** (extraction has no matrix constraints).
   - Sub-tree parameters: keep the existing `defaultBreadth = 3` / `defaultDepth = 4` (`server.go:33-34`) per the approved decision. Axes: breadth = competing extraction methods per field (Step 3's method discriminator); depth = refinement iterations. **Improvement signal = model confidence**: define the field sub-tree's root **baseline confidence as 0** (no extraction attempted yet), so the first extraction's confidence is compared against 0 and each refinement must raise confidence over its parent to avoid pruning — reuse `improves(parentConfidence, childConfidence, domain.Maximize)` with a fixed `Maximize` direction, or an equivalent inline `childConfidence > parentConfidence` check. Stopping = the same depth cap + no-improvement pruning as tabular.
   - Write path: factor `writeTriplet` (`hypothesis.go:225-291`) so the query path is unchanged (still `InterventionQuery`/`VerificationVerified`/`Confidence:1.0`/`EpistemicObservational`) and an extract variant writes the outcome with `Intervention.Type: InterventionExtract`, `Outcome.VerificationStatus: VerificationUnverified`, `Outcome.Provenance:` the Step-4 locator, `ProducedEdge.Confidence:` the model's self-reported confidence (not 1.0), `EpistemicSource: EpistemicObservational`. The `unverified` status feeds Shell 08's HITL queue and Shell 04's MCTS eligibility filter.
