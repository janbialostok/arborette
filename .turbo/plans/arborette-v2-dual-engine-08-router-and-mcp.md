# Plan: Control Plane Router & MCP Surface

## Context

With verification able to run, the Router decides when it runs: intent classification at intake (explore vs verify, with claim extraction and reification of directly-constructed claims), an explicit per-finding verify affordance (REST + MCP), budgeted auto-promotion of top findings at Phase-1 completion, and the correction → staleness → re-verification flow that makes analyst domain knowledge actually propagate. The MCP surface rides here because R2's verify affordance and R33's `verify_finding` tool are the same contract, and downstream agents get epistemic labels (with the sufficiency caveat) on everything served.

Covers spec requirements R1, R2, R3, R7, R13 (partial: caveat carried on MCP output), R33.

Settled defaults (escalated at expansion): auto-promotion top-N = 5 (`ORCHESTRATOR_AUTOPROMOTE_TOP_N`), per-goal verification budget stays 20 (`VERIFIER_VERIFICATION_BUDGET`, already built in shell 07), staleness re-verification cap = 10 (`ORCHESTRATOR_STALE_REVERIFY_CAP`), kill switch `ORCHESTRATOR_AUTOPROMOTE_ENABLED` (default true).

Plan risks noted during expansion:

- `discoveryVersion` is hardcoded `1` in `internal/verifier/worker.go:137` with a comment reserving the analyst-correction/version-increment path for "a later shell" — this is that shell. The supersession + `MarkStale` machinery from shell 07 is already version-aware; the correction flow (Step 5) supplies the bump.
- `CAUSES` edges are version-keyed (`UpsertCausalEdges` MERGEs on `{version}`, `causal.go:232`) and `GetCausalGraph` reads edges at exactly `meta.Version` (`causal.go:353-355`) — Step 5's correction therefore copies the full edge set forward to the new version rather than bumping meta alone, and analyst durability (R7 acceptance) comes from version separation: discovery only ever writes its initial version, corrections live at higher versions.
- Downstream shell 09 (knowledge-guided sleep cycle) consumes the causal-evidence lookup and shell 10 (web UI) consumes the correction endpoints, the verify endpoint, and the causal-verification listing — the DTO shapes in Steps 3 and 5 are the seams they build on, so keep field names snake_case and stable.

4. **Hook auto-promotion into Phase-1 completion**
   - Export the ranking formula: lift `shrunkScore` + `directionalDelta` (`internal/sleepcycle/publish.go:140-155`) into `internal/domain` as `ShrunkScore(value, baseline float64, support int64, k float64, dir TargetDirection) float64` and `DirectionalDelta`; `sleepcycle` delegates (k stays `w.cfg.MinSupport` there).
   - New `internal/orchestrator/promote.go`: `autoPromote(ctx, goal, runBaseline)` called from `runLoop`'s deferred closure at the `termErr == nil` site (`hypothesis.go:129-136`), before the `loop_complete` publish. Three prerequisites at the hook site: (a) the root baseline (`hypothesis.go:191`) and pinned objective (`:148`) are declared *after* the `defer` literal, so they are lexically unreachable from the closure — hoist `var obj objective.Objective; var baseline float64; var baselineSet bool` (`objective.Pin` returns `objective.Objective`, `internal/objective/objective.go:50`) above the `defer` and assign at the existing sites; (b) the closure's `recover()` (`hypothesis.go:112`) has **already returned** by the time any statement after it runs, so a panic inside `autoPromote` would propagate to the run goroutine (`hypothesis.go:77-80`, no recover) and crash the whole orchestrator, defeating R3's isolation — and up to ~16 sequential `Launch` POSTs (10s `launchTimeout` each, `joblauncher.go:46`) before the terminal publish would stall `loop_complete` under a degraded Verifier. Therefore `autoPromote` runs as a **child goroutine spawned from the closure just before the `loop_complete` publish, opening with its own `defer`/`recover`** (log + audit on panic); its `auto_promotion_complete` SSE event becomes best-effort (the hub may already have completed — the audit record is the durable signal, and the per-verification SSE flow rides the verification-events path regardless); (c) the closure region runs after the loop's own `ctx` may already be dead (that is why `SetStatus` uses a detached `writeCtx`, `hypothesis.go:118-131`) — `autoPromote` builds its own detached context (`context.Background()` + a dedicated timeout sized for the graph read plus the top-N launcher POSTs, not the 5s `statusWriteTimeout`); (d) the closure also fires for document goals (`goal.IsDocument()` returns before any baseline) and for failed runs — `autoPromote` receives `(goal, baseline, baselineSet, runSucceeded)` and gates internally per the behavior below rather than being skipped wholesale, because the primary claim dispatch must not depend on run outcome. Behavior:
     - `verify` track, first, **outside the kill switch and regardless of `runSucceeded`**: dispatch the goal's stored claim via `kind: claim` — R1's primary constructed-claim verification "always runs" and is budget- and kill-switch-exempt per R3's accounting, and the claim is loaded from the stored jsonb and measured directly, so it must not be gated on Phase-1 success either (a verify-track goal whose Phase-1 run failed still gets its claim tested — "never gated on Phase 1"). Gating it behind `AutoPromoteEnabled` would let an operator disabling explore auto-promotion silently stop verify-track goals from verifying their claim. **Skip this dispatch when the goal's `claim` is NULL** (cannot-construct at intake) — dispatching an empty claim would reify the global baseline as its own claim, the exact "claim was tested" outcome R1 forbids (the Verifier's `VerifyClaim` guards this server-side too, but the router must not dispatch it at all).
     - Everything below runs only when `runSucceeded && baselineSet`, and returns unless `AutoPromoteEnabled` (the kill switch).
     - `explore` track: pool = `ListEligibleFindings` (`neo4j.go:399`); rank by `domain.ShrunkScore` (value from `Outcome`, baseline from the hoisted root-segment value, support from `Outcome.Support`, k = `AutoPromoteShrinkageK` — a new orchestrator knob, `ORCHESTRATOR_AUTOPROMOTE_SHRINKAGE_K`, default 30 to match the sleep-cycle `MinSupport` default, because the orchestrator holds no support floor of its own: `MinSupport` is `SLEEPCYCLE_SEARCH_MIN_SUPPORT` (`config.go:426`) and the hypothesis loop deliberately does not prune on support); take top-N (`AutoPromoteTopN`, default 5); dispatch each via `verifierJobs.Launch` with `"budgeted":"true"`.
     - `verify` track (under the kill switch, budgeted): score Phase-1 findings against the claim by **deterministic filter-overlap** (fraction of claim conjuncts present in the finding's filter conjunction; ties broken by shrunk score) and dispatch matches under the budget (`budgeted="true"`) — these are R1's "claim-match extras," autonomous spend per R3. Skipped entirely when `claim` is NULL.
     - Every dispatch failure is log + `recordAudit("auto_promotion_failure", …)` only — auto-promotion never fails the Phase-1 run (R3). Budget refusals surface later at the Verifier's `DispatchAccept` as non-fault `verification_rejected`; the launcher fire-and-forget 202 is enough here.
     - Publish one SSE `auto_promotion_complete` event with counts.
   - Config: add `AutoPromoteEnabled bool` (`ORCHESTRATOR_AUTOPROMOTE_ENABLED`, default true), `AutoPromoteTopN int` (`ORCHESTRATOR_AUTOPROMOTE_TOP_N`, default 5), `AutoPromoteShrinkageK int` (`ORCHESTRATOR_AUTOPROMOTE_SHRINKAGE_K`, default 30), `StaleReverifyCap int` (`ORCHESTRATOR_STALE_REVERIFY_CAP`, default 10) to the orchestrator section of `internal/config/config.go` via `boolEnv`/`intEnv`, threaded through `cmd/orchestrator/main.go`.
   - Tests: kill switch suppresses explore promotion and claim-match extras but NOT the primary claim dispatch; a **failed** Phase-1 run on a verify-track goal still dispatches the primary claim; a NULL-claim verify-track goal dispatches nothing claim-related; top-N cutoff respects shrunk-score order (thin high-delta segment ranks below well-supported one); verify-track dispatches the claim exactly once plus overlap matches; a launcher error does not propagate to the run status; a panicking `autoPromote` is contained by its own recover (run status and `loop_complete` unaffected).

5. **Build the correction flow: endpoints → version bump → staleness → capped re-dispatch**
   - New graph methods in `internal/graph/causal.go` (openCypher subset, id-keyed MERGE conventions). Load-bearing constraint: `CAUSES` edges are **version-keyed** — `UpsertCausalEdges` MERGEs on `{version: row.version}` (`causal.go:232`) and `GetCausalGraph` reads edges with an exact `version: meta.Version` filter (`causal.go:353-355`) — so a meta-only bump would strand the entire discovered edge set at the old version and every subsequent verification would adjust against an empty graph. The correction must therefore **copy the full current edge set forward to the new version with the correction applied**:
     - `CorrectCausalEdge(ctx, goalID, datasourceRef string, correction domain.EdgeCorrection) (int, error)`: read the current graph (`GetCausalGraph`), apply the op in memory — **flip** = set the edge's direction, provenance `analyst`; **delete** = plain omission from the copied-forward set (durable without a tombstone: discovery early-returns whenever committed meta exists, `worker.go:156-170`, and only ever writes its initial version, so nothing can re-add the edge at the served version — no `deleted` field is needed on `domain.CausalEdge` and none exists); **add** = append the edge with `provenance='analyst'`, confidence 1.0 — then write the whole corrected set at `version+1` via `UpsertCausalEdges` (all rows carry the new version) and commit **meta-last** with `UpsertCausalGraphMeta` at `version+1` (`causal.go:249`), so a crash mid-copy leaves the old version served (the meta-last commit-marker invariant). Returns the new version. Analyst provenance survives subsequent corrections because the copy-forward preserves per-edge provenance.
     - Re-discovery durability: discovery writes only at its initial version (`worker.go:137`), and corrections live at higher versions that `GetCausalGraph` serves via its latest-meta read — so version separation is what protects analyst edges from a crashed-discovery re-run. Add a test asserting a re-run of discovery at version 1 leaves a version-2 corrected graph being served; only if `DeleteCausalGraphVersion` or any re-discovery path can touch higher versions does an explicit `analyst`-provenance guard become necessary.
   - `domain.EdgeCorrection{Op, From, To, Direction}` with op enum `flip|delete|add` in `internal/domain/causal.go` alongside `EdgeProvenance`.
   - New `internal/orchestrator/corrections.go`: `POST /goals/{id}/causal-graph/corrections` → `handleCausalCorrection`: `lookupGoal`; decode + validate the correction (columns must exist in the goal's graph); **serialize the read-modify-write** — two concurrent corrections would both read version N and interleave their copied-forward sets at N+1, silently resurrecting a deleted edge or dropping a flip (R7 violation) — by holding the same per-(goal, data-source) Postgres advisory lock discovery uses (`store.AdvisoryLock`, try-acquire + short poll per the session-lock conventions; on timeout answer 409 "correction in progress") across the `CorrectCausalEdge` call; then `CorrectCausalEdge` → new version; `store.CausalVerifications.MarkStale(ctx, goalID, [from, to])` (`causalverifications.go:240`); list the goal's now-stale completed records (`ListForGoal` filtered on `stale`), re-dispatch up to `StaleReverifyCap` (10) via `verifierJobs.Launch` with `"budgeted":"false"` (analyst-initiated, exempt — R3/R7 accounting; the graph-version bump makes each re-dispatch a new record rather than a coalesced duplicate, R12). Publish SSE `causal_graph_corrected` (op, columns, new version, re-dispatched count) + `recordAudit("causal_graph_corrected", "causal_graph", …)`. Respond 200 with the new version and re-dispatch count.
   - Register the route in `Routes()`; wire the corrector interface through `NewServer`.

   - Tests: flip/delete/add each bump the version by one, stamp `analyst` provenance, and — critically — the new version serves the **full copied-forward edge set**, not just the corrected edge (the regression the version-keyed storage makes possible); a deleted edge is absent from the new served version and from adjustment derivation, and stays absent across a subsequent correction; a second correction preserves the first's analyst provenance; two concurrent corrections serialize (advisory lock) — the loser sees the winner's version and neither edit is lost, or answers 409 on lock timeout; `MarkStale` + capped re-dispatch stops at 10; correction on unknown column 422s.
