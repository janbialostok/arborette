# Plan: Orchestrator/API Service

## Context

The Orchestrator is the system's center of gravity: it's the only service the web UI talks to, the only service holding audit-table credentials, and the owner of both the goal registry and the Active Hypothesis Loop (Phase 1). It registers analyst goals, translates them into a structured Evaluation Matrix via Claude, and — on a separate, explicit trigger — runs the interactive hypothesis-tree loop against the Sandbox Execution service, writing empirically-grounded causal triplets and streaming live progress to the analyst's session. It's also the sole audit-table writer, exposing an internal API so other services (the Sleep-Cycle Worker) can log without direct database access.

### Decisions locked in at expansion

- **Hypothesis-tree defaults (Open Question 1):** breadth **3** (candidate interventions proposed per node), depth **2** (refinement levels), stopping condition **"no child improves the objective against the Evaluation Matrix, or the depth cap is reached."** These live as named constants so they are tunable against real sample data without touching call sites. Worst case ≈ 3 + 9 = 12 candidate evaluations per run (each a Claude proposal already made + one Sandbox execute call).
- **Analyst identity (Open Question 2):** an `Identity` interface with a `StubIdentity` implementation reading a single configured analyst id. The audit-write path depends on `Identity`, so the deferred SSO/per-department work is a new implementation, not a refactor of call sites. Full auth/SSO/access-control remains out of scope for this shell.
- **Claude access via the official SDK (deviation from the hand-rolled-client convention — noted risk):** the codebase's only outbound-HTTP prior art is `internal/embedding/ollama.go` (hand-rolled `net/http`). Structured outputs (`output_config.format`), model-ID currency, and response parsing are materially more involved than Ollama's single embed call, and the `claude-api` guidance is to use the official SDK when one exists. This plan adds `github.com/anthropics/anthropic-sdk-go` (pure Go, no CGO — safe under the Go-1.24 pin) rather than hand-rolling. This is the one place the plan departs from the infra-constructor/hand-rolled-HTTP convention; contained inside a single `internal/llm` package so the rest of the service is unaffected.
- **Claude model:** default `claude-opus-4-8` (the current-generation default), read from config (`ANTHROPIC_MODEL`) so it can be tuned to a cheaper/faster structured-output model (e.g. `claude-haiku-4-5`) for demos without a code change. Structured outputs are used for both the Evaluation Matrix and the intervention-tree proposal — never freeform text — via `output_config.format` with a `json_schema` (not the deprecated `output_format`).
- **UUIDs:** promote `github.com/google/uuid` from indirect to a direct dependency (no production UUID helper exists today; only test-scoped `testutil.NewID`). Used for `optimization_function_id` and every graph node id (`domain.State/Intervention/Outcome.ID`), which the graph layer documents as application-assigned v4 UUIDs.
- **Sandbox wire DTOs are orchestrator-owned, not imported (CGO boundary):** `internal/sandbox` blank-imports the CGO DuckDB driver, and the orchestrator builds `CGO_ENABLED=0` on `distroless/static-debian12` — so the orchestrator must **not** import `internal/sandbox` to reuse its `IntrospectRequest`/`ExecuteRequest`/`ExecuteResponse` types (doing so breaks the image build). Instead the sandbox client defines its own copies of these wire structs, with fields typed from the dependency-free `internal/domain` package (`domain.Target`, `domain.Constraint`, `domain.InterventionType`). Cost/risk: these structs must stay byte-for-byte JSON-compatible with `internal/sandbox/server.go` — a documented coupling to keep in sync (a future CGO-free `internal/sandboxapi` shared package that both services adopt would remove the duplication, but that reopens shipped shell-03 code and is out of scope here).

### Convention Anchors
- **No Anthropic/Claude SDK exists anywhere** — the orchestrator introduces the first Claude client; `google/uuid` is present only as an indirect dep (`go.mod`).
- **UUID generation**: no production UUID helper. Application-assigned ids (graph node ids, `optimization_function_id`) are documented as v4 UUIDs (`graph/repository.go:7`, `store/embeddingstore.go:11`); `goal_registry.optimization_function_id` is a Postgres `uuid` column. Only `testutil.NewID` generates them (crypto/rand, test-scoped). Decision: promote `google/uuid` to a direct dep.
- **Infra constructors take primitives, not config**: `NewClient`, `NewNeo4jRepository`, `NewOllamaProvider`, `NewFileSource`, `NewServer` all accept individual scalars; `cmd/<service>/main.go` unpacks `cfg.X.Field` at the call site. New sandbox/Claude clients follow — take a base URL / API key / model as args, not a `config.Config`.
- **Config**: `internal/config/config.go` — add a nested struct to `Config` (`config.go:16-23`), a typed sub-config, and populate it in `Load()` (`config.go:129-168`) using the `env`/`intEnv`/`boolEnv` helpers with local-compose defaults. Secrets (API keys) use bare `os.Getenv` with no default (see `NEO4J_PASSWORD`, S3 keys). Add matching vars to `.env.example`.
- **Error idioms**: sentinel `errors.New` vars mapped via `errors.Is` in a status switch (`sandbox/server.go:30-33`, `176-194`); `fmt.Errorf("context: %w", err)` wrapping everywhere. Internal 500s mask detail from the client but `log.Printf` the real error (`server.go:191`).
- **Postgres role separation**: orchestrator uses `cfg.Postgres.OrchestratorDSN()` (`config.go:112`) — the only role with `INSERT` on `audit_log` and write on `goal_registry` (`0005_grants.up.sql`), `SELECT`-only on embeddings. This is why the orchestrator is the sole audit writer; enforced at the DB grant level, verified in `store_test.go:183-223`.
- **Test conventions**: table-driven subtests with `t.Run` (`sandbox/server_test.go:36-47`); `net/http/httptest` `NewRecorder`/`NewRequest` driving `Routes().ServeHTTP` with a nil infra client when validation returns before I/O (`server_test.go:73-96`). Integration tests gated by `testutil.RequireIntegration(t)` (skips unless `ARBORETTE_INTEGRATION` set), run with `-p 1`. Pure-logic error-mapping tables run without any gate.
- **Service wiring/deploy**: each service is a `cmd/<name>/main.go` + `cmd/<name>/Dockerfile` + a `docker-compose.yml` block. The orchestrator block (`docker-compose.yml:127-142`) currently exposes **no ports** — adding an HTTP listener means adding a `ports:` mapping (mirror `sandbox`'s `8081:8081`) and a new `ORCHESTRATOR_PORT` env var. Non-CGO service = distroless-static Dockerfile (orchestrator already has one).

### Notably Absent (net-new, no prior art)
- **SSE**: no `text/event-stream`, `http.Flusher`, or streaming handler anywhere. The Phase 1 progress stream is net-new; only `RunHTTPServer` (no write timeout set, so it won't kill a long-lived stream) is reusable.
- **AWS Batch / SubmitJob / ephemeral-container invocation**: no code exists. `aws-sdk-go-v2/config` + `credentials` are already deps (used by objectstore) but no `service/batch`. Phase-2 job trigger is entirely net-new.
- **Claude structured outputs**: net-new (see SDK decision in Context).

### Proposed Alignment
Build the orchestrator server as a `sandbox`-style `Server` with a `Routes()` mux and per-handler decode/validate/writeJSON/writeStageErr; extend `cmd/orchestrator/main.go` to end in `service.RunHTTPServer` instead of `WaitForShutdown`; add an `OrchestratorConfig` (+ `AnthropicConfig`) to `config.go`. The outbound sandbox client is modeled on `ollama.go`'s HTTP-client shape but defines **its own** CGO-free request/response structs mirroring the sandbox wire contract (it must not import the CGO-tainted `internal/sandbox` package). The four net-new areas (production UUID source, SSE hub, Claude structured-output client, Phase-2 job dispatcher) are each built as a new primitive-constructor client/package consistent with the infra-constructor convention rather than forced onto an ill-fitting existing seam.

2. **`internal/llm` — Claude structured-output client**
   - New package `internal/llm` wrapping `anthropic-sdk-go`. `NewClient(apiKey, model string) *Client` (primitive-constructor convention). `anthropic.NewClient(option.WithAPIKey(apiKey))`.
   - **Model/thinking/effort config (spec Tech Stack, Phase 1):** every call uses model `claude-opus-4-8` (configured), **`thinking: {type: "adaptive"}`** and **`output_config.effort: "high"`** (raise to `"xhigh"` for the hardest hypothesis-generation cases). This is load-bearing, not optional: on Opus 4.8 an omitted `thinking` field runs with *no* thinking, silently dropping the spec's quality lever. Structured outputs are compatible with adaptive thinking. Because a response may carry a leading `ThinkingBlock` before the text block, parse by **selecting the text block** (type-switch over `resp.Content`), not by assuming `Content[0]`.
   - `GenerateEvaluationMatrix(ctx, goalText string) (domain.EvaluationMatrix, error)`: one `client.Messages.New` call with `output_config.format` = a `json_schema` describing `{targets:[{field,direction}], constraints:[{field,op,value}]}` (matching `domain.EvaluationMatrix` json tags; `direction` enum `maximize|minimize`, `op` enum `lt|lte|gt|gte`). Parse the response's text block JSON into `domain.EvaluationMatrix`. Per R1, the Matrix is produced from goal text **alone** — introspection (Step 4) is a separate validation step and does not block matrix generation.
   - `ProposeInterventionTree(ctx, goalText string, matrix domain.EvaluationMatrix, schema SandboxSchema, node TreeContext) (Proposal, error)`: structured-output call. At the **root** it returns both the run's **objective aggregation** (one of `count/sum/avg/min/max`, paired with the Evaluation Matrix's primary `Target.Field`) *and* up to `defaultBreadth` candidate interventions; at **deeper nodes** it returns candidate interventions only. Per the Step-6 fixed-objective invariant, a candidate carries **filters only** (the aggregation+target are the run's fixed objective, never re-proposed per candidate). `TreeContext` carries the parent state / prior outcome so depth-2 refinement re-proposes filters against the previous result. Constrain the output schema so a candidate's `filters` and the objective `target` reference only introspected columns, and the aggregation is one of the allowlisted `count/sum/avg/min/max` the Sandbox accepts.
   - Handle `stop_reason == "refusal"` and `max_tokens` explicitly (return a wrapped error); do not raw-string-match tool/JSON output — `json.Unmarshal` the selected text block. Guard against the deprecated `output_format` param — use `output_config.format` only.
   - Unit-test the JSON-schema construction and response parsing with a fake `Messages.New` (or a thin interface over the one call) so no network/API key is needed; gate any live-API test behind an env flag.

4. **Sandbox HTTP client + goal-intake introspection**
   - `internal/orchestrator/sandboxclient.go`: `SandboxClient` (primitive-constructor: `NewSandboxClient(baseURL string, httpClient *http.Client)`), modeled on `ollama.go`. Define orchestrator-local, CGO-free request/response structs mirroring the sandbox wire contract (`IntrospectRequest`/`IntrospectResponse` with `TargetBinding` + schema/column DTOs, and `ExecuteRequest`/`ExecuteResponse`), with the same snake_case `json:` tags and fields typed from `internal/domain` — **do not** import `internal/sandbox` (its DuckDB CGO blank-import would break the orchestrator's `CGO_ENABLED=0` build; see the DTO decision in Context).    - `submit_analyst_goal` (Step 5) calls `Introspect` during intake to **validate and surface** the target→column bindings: log/return any target with `Matched:false` so an unresolvable objective is caught at intake, not mid-loop. There is **no binding-persistence path** — `store.Goal`, `domain.Target` (`{Field,Direction}` only), and the `goal_registry` schema carry no binding column, and the sandbox re-resolves `Target.Field`→column at execute time (`bindTargets`/`matchColumns` in `server.go`). So bindings are validate/log-only; the loop relies on execute-time re-binding. Per R16's acceptance, the Matrix is not blocked on introspection: generate the Matrix first (Step 2), then run this validation pass.

5. **`submit_analyst_goal` endpoint + file ingestion**

     - **Uploaded file** (multipart or streamed body): `objects.Put(ctx, objects.NewKey("datasources", uuid, filename), body, contentType)`.

6. **Phase 1 trigger + hypothesis-tree proposal**
   - `internal/orchestrator/hypothesis.go`: `Loop` type driving the tree. `handleTriggerLoop` looks up the goal via `GoalRegistry.Get(ctx, id)` (404 on miss), then launches the loop **in a goroutine** with a background-derived context so an SSE disconnect (Step 8) never aborts it (R8/Produces: decoupled from the stream), and returns `202 Accepted`.
   - Tree constants: `defaultBreadth = 3`, `defaultDepth = 2`. Root: `llm.ProposeInterventionTree(...)` proposes up to 3 candidates using the system defaults (R5 — no analyst configuration). Each node expands to `defaultDepth` refinement levels; a branch stops when no child improves the objective vs the Evaluation Matrix or the depth cap is hit (the locked stopping condition).
   - **Fixed-objective-measurement invariant (load-bearing — do not violate):** the stop-on-no-improvement comparison is only meaningful if every value it compares is the *same* measurement over *comparable* scopes. The invariant has three parts, all fixed for the whole run:
     1. **One objective `(aggregation, target field)`**, held constant across the entire tree. The target field is a single field pinned once from the Evaluation Matrix (`Targets` is an unordered `[]Target` with no inherent "primary" — the run pins one: `ProposeInterventionTree`'s root `Proposal` returns the chosen objective target field, defaulting to `Targets[0]` if the model does not choose; its `Direction` decides whether higher or lower is "improvement"). The aggregation (one of `count/sum/avg/min/max`) is likewise chosen **once** at run start — returned in the root `Proposal` (or a system default applied) — and reused for every `Execute`.
     2. **Candidates vary only filters**, never the aggregation or target field — so `ProposeInterventionTree`'s per-candidate output carries **filters only** at depth ≥ 1.
     3. **Filters nest cumulatively down a branch.** A node's effective filter set is its parent's effective filters **∪** the candidate's newly proposed refinement filters. This is what makes the depth-≥1 baseline reuse in Step 7 correct: measuring the objective at the parent's effective filter set yields exactly the parent's `Outcome.Value`, so reusing it as the child's start-state baseline is valid, and the child's outcome (measured at parent ∪ new filters) is comparable to that baseline.
   - **Failures this prevents:** (a) a different aggregation/target at a refinement level → incommensurable numbers (`avg` vs `count`) → pruning on garbage; (b) non-cumulative (freshly-proposed, non-nested) child filters → the child measures a different segment than the parent, so the parent value is not a valid baseline; (c) "objective without the candidate's filters" read as removing *all* filters → the unfiltered root value at every depth. Persist the fixed `(aggregation, objective target field)` **and** each node's effective (cumulative) filter set in the run's in-memory tree state so Steps 6–7 read them consistently.

7. **Per-candidate execution + causal-triplet writes**
   - For each candidate: build a `sandbox.ExecuteRequest{DataSourceRef, Type: domain.InterventionQuery, Aggregation, Target, Filters}` where `Aggregation` and `Target` are the **run's fixed objective measurement** and `Filters` is the node's **effective (cumulative) filter set** — the parent's effective filters ∪ this candidate's newly proposed filters (Step 6 invariant, part 3) — call `SandboxClient.Execute`. Measure the returned `Value` against the Evaluation Matrix (does it move the objective in the desired `Direction` vs. the start-state baseline, without violating hard `Constraints`?) to compute the effect and decide branch continuation.
   - **Measured start state (`domain.State.Properties`, a `map[string]any`):** the "start state" is the baseline the candidate is judged against — the objective measured at the **parent's** effective filter set (i.e. without this candidate's *newly added* filters). At the root, run one `Execute` with the objective aggregation/target and no filters, and store its value plus the `data_source_ref`, objective aggregation/field, and the (empty) effective filter set in `Properties`. At deeper nodes, the parent node's measured `Outcome.Value` **is** the child's start state (reuse it rather than re-measuring) — valid because cumulative nesting (part 3) makes the parent's outcome exactly the objective at the parent's effective filters, which is the child's baseline. Give the state a fresh `uuid.NewString()` id.
   - Write the triplet to Neo4j (`graph.Repository`): `CreateState` (the measured start state above), `CreateIntervention` (`domain.Intervention{Type: InterventionQuery, Properties}` — carries the candidate's filter params + the fixed objective aggregation/target for provenance), `CreateOutcome` (`domain.Outcome{VerificationStatus: domain.VerificationVerified, Value}` — query outcomes are always verified per R7), `CreatePreConditionFor(stateID, interventionID)`, `CreateProduced(interventionID, outcomeID, domain.ProducedEdge{EffectSize, Confidence: 1.0})`. **Confidence is fixed at 1.0 for query-type triplets (R7)** — no HITL, no verification.
   - **Audit each intervention and outcome (R13):** after a successful triplet write, write audit records via the internal identity-stamped helper (Step 10) — one for the intervention event and one for the outcome event (R13 requires an audit record for *every* intervention and outcome, not only failures). Then emit an SSE event (Step 8) per node and per triplet.
   - **Append-not-replace on re-trigger:** because all graph writes are MERGE upserts keyed on fresh UUIDs, re-triggering the loop for a goal with existing triplets adds new nodes rather than replacing prior ones (Produces requirement). Do not delete or overwrite prior triplets.

8. **SSE progress streaming + failure handling**
   - `internal/orchestrator/hub.go`: a small in-memory pub/sub `Hub` keyed by `optimization_function_id` — subscribers register a channel; the loop publishes tree-node and causal-triplet events. Net-new (no SSE prior art). **Because trigger (Step 6, returns `202`) and subscribe are independent HTTP calls, an in-memory hub with no history would lose every event published before the client subscribes** — the natural UI order (trigger, then open the stream) would miss the first tree nodes on every run, weakening R8's "streams progress as produced" (and R20's live-confidence view downstream). Mitigate with a bounded **per-`optimization_function_id` replay ring buffer**: the hub retains the last N events per run and replays them to a new subscriber before switching it to live, so a subscribe-after-trigger client still sees the run's start. Document the client contract (subscribe before trigger where possible; the replay buffer covers the race either way). Bound the buffer and evict runs on completion to cap memory.
   - `handleStream` (`GET /goals/{id}/stream`): set `Content-Type: text/event-stream`, `Cache-Control: no-cache`; type-assert `http.Flusher`; subscribe to the hub (replaying buffered events first, then live); write `data: <json>\n\n` and `Flush()` per event; return when the request context is done. A dropped SSE connection unsubscribes but **must not** cancel the loop (the loop runs on its own context from Step 6).
   - **Failure handling:** a candidate whose Sandbox call errors (or violates a hard constraint) aborts only that branch — record a branch-failure event through the internal audit-write API (Step 10) with the failing intervention detail, emit a failure SSE event, and continue sibling branches (Produces requirement; R13 failure events).

9. **Phase 2 (Sleep Cycle) trigger — job invocation**
   - `internal/orchestrator/joblauncher.go`: `JobLauncher` interface `Launch(ctx, jobName string, args map[string]string) error`. The MVP/local implementation is a **stub launcher** that records the named-job invocation — audit it (Step 10) and `log.Printf` the job name + args — and returns success; it does **not** shell out to `docker`/`docker compose` (running the Docker CLI from inside the orchestrator container would require a mounted Docker socket, which the compose `orchestrator` block does not provide, so a real docker invocation would fail at runtime). The production implementation calls AWS Batch `SubmitJob` (deferred — `service/batch` is not a dep yet; leave a clearly-marked seam behind the interface). This is an **infra-level invocation, not a direct code call** into the Worker, so this shell agrees only on the job/container name contract and does not require the Sleep-Cycle Worker shell to exist yet.
   - `handleTriggerSleepCycle` (`POST /goals/{id}/sleep-cycle`): validate the goal exists, call `JobLauncher.Launch(ctx, cfg.Orchestrator.SleepCycleJobName, {optimization_function_id})`, audit the trigger, respond `202`.

10. **Internal audit-write API + Identity seam**
    - `internal/orchestrator/identity.go`: `Identity` interface `Current(ctx) (Analyst, error)` (or a simpler `Actor(ctx) string`); `StubIdentity{ID string}` returns the configured `ARBORETTE_ANALYST_ID`. This is the single seam a future SSO implementation replaces (Open Question 2).
    - `handleAudit` (`POST /internal/audit`): the single write path to `audit_log`. Decode `{action, event_type, detail}`, stamp `Actor` from `Identity`, call `store.AuditLog.Append`. Used by this service's own intervention/outcome/failure events (Steps 5/7/8/9) via a small internal helper that calls `AuditLog.Append` directly (same process, no HTTP hop) and by the Sleep-Cycle Worker over HTTP (R13/R14 — every record carries the stub identity; the orchestrator remains the sole audit-table writer via `OrchestratorDSN`).

11. **Heuristic-browsing endpoints**
    - **Response DTOs (do not marshal domain types directly):** `heuristics.Match` wraps `domain.MetaHeuristic`, and `graph.CausalTriplet` wraps `domain.State/Intervention/Outcome` — none carry `json:` tags, so marshaling them directly emits PascalCase keys and leaks internal fields (`EmbeddingPending`, `Provenance`, `VerificationStatus` internals) inconsistent with the snake_case contract every other handler uses (this is exactly why `sandbox/server.go:37-39` maps to local snake_case DTOs). Define orchestrator response DTOs that select and snake_case the fields the web UI needs.
    - `handleHeuristicSearch` (`GET /heuristics/search?q=<state>&k=<n>`): call `heuristics.Service.Query(ctx, q, k)`, map `[]heuristics.Match` to a search-result DTO (`{id, definition}` per match). Backs the web UI's heuristic browser search (embedding similarity via the shared package).
    - `handleHeuristicTrace` (`GET /heuristics/{id}/trace`): call `heuristics.Service.Trace(ctx, id)`, map `[]graph.CausalTriplet` to a trace DTO (snake_case state/intervention/outcome fields). Backs the trace view.
