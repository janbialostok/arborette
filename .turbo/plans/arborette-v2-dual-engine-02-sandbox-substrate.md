# Plan: Sandbox Substrate — Staging Cache & Boundary Hardening

## Context

Engine B turns the sandbox from an occasionally-hit query executor into the hot substrate for CI-test sweeps, adjustment queries, refutation batteries, and MCTS measurement volume — every one of which re-pays a full object-store download and DuckDB re-parse today. Meanwhile the service boundary has no auth, no ref scoping, no concurrency cap, and validates allowlists only after staging a full download. The spec requires the cache (R22) and the hardening (R28) to be designed together, because a cache changes the disk/eviction story the hardening must bound.

Decisions locked at expansion:

- **Per-class concurrency cap** (user decision on the shell's open question): the limiter is keyed by a request-class string with one default class today covering `/introspect`, `/execute`, and `/document/text`. When shells 06/07 add `/analyze` request kinds, they register a new class plus its own env knob without reshaping the limiter (spec open question at `.turbo/specs/arborette-v2-dual-engine.md:178`).
- **Registry validation means a read-only Postgres check against a ref registry populated at ingest.** R28 says refs are "validated against the registry, not arbitrary bucket paths"; a static key-format check would still accept arbitrary bucket paths. `goal_registry.datasource_ref` alone cannot be the registry: the intake flow (`internal/orchestrator/submit.go:101-156`) stages the object and calls `/introspect` plus the dry-run `/execute` *before* `goals.Insert`, so a goal_registry-only check would 404 every registration. Instead, `ingest()` records each minted ref in a new `data_source_registry` table the moment the object lands, and the sandbox validates against that table (read-only, via the existing `arborette_service` role-grant pattern from `internal/store/migrations/0005_grants.up.sql`). This makes Postgres a hard boot dependency of the sandbox — a deliberate change from today's object-store-only wiring, fail-closed like every other service main — contradicting the letter of `cmd/sandbox/main.go`'s "holds no graph or Postgres connection" doc comment; that comment's rationale is about *writes* (triplet ownership), and spec R28 is explicit, so the comment and the compose wiring get updated.
- **One internal secret.** The sandbox verifies the same `INTERNAL_AUTH_TOKEN` the orchestrator's `/internal/audit` verifies, extending the one-env-var invariant pinned by `TestInternalAuthTokenIsOneSecret` (`internal/config/config_test.go:178`) rather than minting a second secret.
- **Cache is boot-scoped, not persistent.** The cache directory starts empty at service start — a configured `SANDBOX_STAGE_CACHE_DIR` is *emptied* at boot (not merely created), so prior-boot files can never sit on disk uncounted by the boot-fresh byte accounting. No cross-restart index rebuild. Refs are immutable/content-addressed (R22) so persistence would be *safe*, but amortization within a run is the requirement and boot-scoping keeps the design free of index-recovery logic.

Known spec drift (do not edit the spec): R22 says cache sizing is "designed together with R26's disk-cap concerns," but R26 in the spec body is the pgvector reconcile pass. The disk-cap concerns actually live in this shell's own `MaxObjectBytes`/`MaxTempDirSize`/cache-size budget; treat the cross-reference as pointing at those.

## Implementation Steps

1. **Staging cache with reservation-based admission and refcounted LRU eviction** — new `internal/sandbox/stagecache.go` + `stagecache_test.go`
   - `StageCache` struct: root dir, max total bytes, mutex-guarded entry map (ref → on-disk path, size, refcount, LRU stamp), an in-flight reservation total, and an `x/sync/singleflight.Group` so concurrent first requests for one ref pay one fill.
   - API: `NewStageCache(root string, maxBytes int64)` and `Acquire(ctx, ref string, reserve int64, fill func(scratch, dest string) error) (path string, release func(), err error)`. Hit: take a refcount, return. Miss: enter `singleflight.Do` keyed by ref; **the leader alone reserves, fills, and settles** — waiters block on `Do` and, like the leader, take their own refcount on its success. The artifact is a cache-owned file at exactly `dest` = `<root>/sha256(ref)` (refs are object keys with `/` and arbitrary bytes — never used raw as filenames; no extension suffix — `dest` is the one path the cache stats, serves, and evicts).
   - **Disk invariant (the R22/R28 "designed together" contract): resident bytes + in-flight reservations ≤ `maxBytes`, always.** The reservation is made **once per fill, inside the singleflight leader** — never once per calling Acquire, or N concurrent same-ref cold requests would charge N×reserve (three cold requests for one 512MiB CSV would reserve 3GiB against the 2GiB default cap, bypassing two of them and re-downloading under exactly the concurrent-rollout load the cache exists to amortize). The leader reserves the caller-supplied worst-case size (`maxObjectBytes` for refs cached as-is; 2× for CSV, which transiently needs raw + Parquet — see Step 2), settles it to the artifact's actual size after the fill, and if the reservation cannot fit even after evicting every refcount-0 entry in LRU order, returns a sentinel `errCacheBypass` **before any download** — every waiter on that `Do` sees the same bypass, no cache-dir orphan is ever written, and no object is downloaded twice for one request. Worked failure modes this invariant exists to prevent: N concurrent distinct-ref cold fills overshooting the cap by their sum; N concurrent same-ref requests multiplying one fill's reservation; a conversion's raw-CSV transient escaping the accounting; a bypass decision made only after a completed fill already wrote a cache-owned file.
   - Admission-vs-concurrency disposition: at defaults (`StageCacheMaxBytes` 2GiB, CSV reserve 1GiB) only ~2 truly simultaneous *distinct-ref* cold CSV fills can be admitted against 8 request slots — accepted, not an oversight. Same-ref concurrency (the dominant case: a run hammers one goal's ref) collapses to one fill via singleflight, reservations settle to actual size the moment a fill completes, and a bypassed request degrades to today's per-request staging: correct, just un-amortized. Sustained bypass is therefore a cold-start transient, not a steady state.
   - Fill workspace: each fill gets a scratch subdir under the cache root — covered by its reservation — removed on every exit path (success, fill error, or panic-safe defer), so transients never outlive the fill.
   - **Failure dispositions (both load-bearing, both previously the invariant's blind spots):** (1) *Reservation drain:* a reservation charged by the leader drains on **every** fill exit — settled to actual size on success, released in full on fill error or panic. Without the error arm, every failed fill (object-store hiccup, conversion failure) leaks its reservation and monotonically shrinks the effective cap until the cache bypasses everything. (2) *Decorrelated cancellation:* the shared fill runs detached from any single caller's request context — `singleflight.DoChan` with the fill goroutine under its own staging-scoped context (derived from `context.WithoutCancel` plus a generous absolute timeout), each caller selecting on its own `ctx.Done()` versus the result channel. A cancelled or timed-out caller returns its own ctx error *without* aborting the fill the other N−1 callers are waiting on — plain `Do` under the leader's request ctx would convert one client timeout into correlated masked-500s for every concurrent same-ref request, a failure mode today's per-request staging does not have. The fill aborts only when its own staging timeout expires or no waiter remains.
   - **Refcount contract: the refcount is taken by each calling `Acquire` — outside the singleflight body — and every caller gets its own independent `release`.** N concurrent first-requesters ⇒ one `fill`, N refcounts, N releases; the entry becomes evictable only when the last holder releases. (The idiomatic bump-inside-`singleflight.Do` shape under-counts — N holders share one refcount, eviction can delete an in-use staged file mid-query — and the test below discriminates exactly that.)
   - Eviction: refcount-0 entries in LRU order, checked when a reservation needs room and when a release drops an entry to refcount 0 over budget. An entry still referenced is never evicted. **Eviction may never select an entry between publication and its first refcount attach:** with refcounts taken strictly outside the singleflight body, a freshly-published entry would otherwise sit at refcount 0 in the create-to-attach window, and a concurrent distinct-ref fill needing room could evict it — deleting the file every waiter is about to be handed a path to. Close the window by publishing the entry already holding a *birth reference* owned by the fill (handed off to its initiating caller's `release`, or released by the detached fill goroutine after result delivery when that caller has gone), so an entry's refcount is never observably 0 before its first real holder attaches.
   - Pure unit tests (no object store): the `fill` callback abstraction lets tests count fills, force sizes, and race Acquire/release to prove hit-amortization, LRU order, singleflight dedup, the per-caller refcount contract (N concurrent Acquires on one ref yield N independent releases and the entry survives eviction pressure until the last), reservation admission (concurrent cold fills cannot exceed `maxBytes` in sum; a too-big singleton bypasses pre-download), failure dispositions (a failing `fill` releases its full reservation; a caller cancelled mid-fill returns its own ctx error while the surviving waiters still get the artifact; a distinct-ref fill under eviction pressure cannot evict a just-published entry before its first attach), and scratch-dir cleanup on fill failure.

2. **Route both readers' staging through the cache; amortize the parse, not just the download** — `internal/sandbox/filesource.go`, `documentsource.go`, `server.go`
   - `Server` gains a `cache *StageCache` field (nil ⇒ per-request staging, preserving today's behavior for tests and cache-disabled config); `NewServer` grows the param; the per-request `NewFileSource`/`NewDocumentSource` constructors take the cache through.
   - `FileSource.stage()` (`filesource.go:167`): the per-request `os.MkdirTemp` dir *remains* — but only for DuckDB spill (`SET temp_directory`); the source file now comes from `cache.Acquire(ctx, ref, reserve, fill)` where `fill` wraps the existing `stageBoundedObject` (reserve = `maxObjectBytes`, or 2× for CSV per Step 1's invariant); an `errCacheBypass` return falls back to staging into the request's own temp dir. `release` is folded into the returned `cleanup`.
   - Parse amortization (R22 "download/parse cost once"): for `.csv` refs, `fill` downloads the raw CSV into its scratch subdir (inside the reservation — see Step 1's 2× CSV reserve) and converts once to Parquet — open a throwaway in-memory DuckDB and run `COPY (SELECT * FROM read_csv_auto('<scratch>/source.csv')) TO '<dest>' (FORMAT PARQUET)` — writing **to exactly the extension-less `dest` the cache tracks** (a bare `COPY ... TO` without `FORMAT PARQUET` would default to CSV output, and a `dest.parquet` suffix would orphan the artifact from the cache's stat/evict/serve path). Only the Parquet artifact survives into the cache; the scratch raw CSV is removed with the scratch dir.
   - **Conversion spill goes outside the cache root.** The conversion engine applies the same `SET temp_directory`/`SET max_temp_directory_size` setup as `stage()` (`filesource.go:196-208` documents why: an in-memory DuckDB otherwise spills to `./.tmp`, unwritable on the distroless image), but pointed at a per-fill `os.MkdirTemp` dir **outside the cache root**, removed with the fill. Spill is bounded by `maxTempDirSize` (2GiB default), not by the 1GiB CSV reservation — directing it into the accounted cache root would let each concurrent conversion exceed `StageCacheMaxBytes` by up to the spill bound, falsifying Step 1's invariant. Peak disk is therefore explicitly: `StageCacheMaxBytes` + (in-flight fills × `maxTempDirSize` spill) + per-request spill dirs — the same spill exposure `stage()` has today, just enumerated.
   - **Reader dispatch depends on which path staged the file, not on the ref's extension.** `tableFunction(ref)` (`filesource.go:279`) is extension-keyed and cannot serve a cache hit: a `.csv` ref's cached artifact is Parquet at an extension-less path (`read_csv_auto` over it fails or reads garbage; `tableFunction` on the bare `sha256(ref)` name returns `errUnsupportedFormat`). `stage()` therefore branches: the cache path constructs `read_parquet('<path>')` directly for `.csv` and `.parquet` refs (documents pass raw bytes to the PDF reader unchanged), while the `errCacheBypass` fallback keeps today's `tableFunction(ref)` dispatch over the raw staged file. `.parquet` refs cache as-is (columnar, parse ~free). `.pdf` refs cache the raw staged bytes for `DocumentSource.Pages`. Type-freeze at conversion is a feature: introspect and execute see one consistent sniff instead of re-sniffing per query. File-path literals embed via the existing `escapeLiteral` (`filesource.go:292`) — same bind-time file-literal constraint as today.
   - `DocumentSource` staging routes through the same `Acquire`.
   - Update the stateless doc comments (`server.go:17-19`, `filesource.go` doc, `cmd/sandbox/main.go` header) to the new invariant: stateless in semantics; the cache is a pure performance layer keyed on immutable content-addressed refs.

3. **Schema-independent validation before staging** — `internal/sandbox/compile.go`, `server.go`

Column-name/type checks intrinsically need the schema and stay post-staging in `compileQueryCounted`.
