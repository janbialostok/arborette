# Plan: MCP Server

## Context

The MCP Server is arborette's read-side interface for downstream AI agents: it lets any MCP-speaking consumer query the accumulated `Meta-Heuristic` knowledge and its supporting evidence without understanding the graph schema or writing Cypher. Its role in the MVP is intentionally narrow — heuristic consumption (`get_optimized_heuristics`, `trace_causal_chain`) plus goal registration (`submit_analyst_goal`, proxied through) — advancing a goal through either phase is a human-analyst, REST-only action in this MVP. The server itself never mutates state directly; it reads through the same shared query logic the Orchestrator's REST endpoints use, and proxies writes to the Orchestrator.

The transport is **Streamable HTTP**, not stdio: mcpserver is a long-running, always-on daemon service (ECS/Fargate in production, a compose container locally), so it serves over the network rather than being launched as a subprocess. The server uses the official Go MCP SDK (`github.com/modelcontextprotocol/go-sdk` v0.8.0), which is pure-Go/CGO-free and therefore compatible with mcpserver's `CGO_ENABLED=0` distroless-static build.

**Downstream seam (plan risk — deliberately out of scope here).** R12/R21/R23 require this server to eventually be reachable on a *public*, `authorization_token`-protected endpoint (Anthropic's native MCP connector — server-side Anthropic infrastructure — opens the connection, so the address cannot be VPC-private). That public-exposure-plus-token responsibility belongs to the downstream **Agent Chat Backend** shell (arborette-09), which lists "MCP Server exposed on a public, `authorization_token`-protected endpoint" among its own Produces and consumes this shell's two read tools "to expose on a public endpoint." To keep that a clean, additive step rather than a redesign, this plan builds the MCP server so its `http.Handler` is constructed once and handed to the serve loop as a single value — arborette-09 wraps that handler with bearer-token middleware without touching the tool handlers or transport. This shell therefore adds **no** auth layer; within the compose network the server is an unauthenticated internal service until arborette-09 gates it.

## Pattern Survey

### Analogous Features
- `cmd/orchestrator/main.go:22-74` — Canonical HTTP-service main: `config.Load()`, wire Neo4j/Postgres/embedding collaborators, build `heuristics.NewService(...)`, construct a server, then `service.RunHTTPServer(name, ":"+port, srv.Routes())` which blocks until shutdown. The mcpserver main should follow this shape (it currently only wires and calls `service.WaitForShutdown`).
- `cmd/sandbox/main.go:18-38` — Leaner variant (no Postgres/graph): wires only what it needs, then `RunHTTPServer`. Shows the "wire only your collaborators" precedent — mcpserver needs Neo4j + Postgres + embedding (for `heuristics.Service`) but NOT object store or Anthropic.
- `cmd/mcpserver/main.go:18-49` — Existing scaffold already wires exactly the read stack the tools need: `graph.NewNeo4jRepository`, `store.NewPool(cfg.Postgres.ServiceDSN())`, `store.ValidateEmbeddingDimension`, `embedding.NewOllamaProvider`, and `heuristics.NewService(provider, store.NewEmbeddingStore(pool), repo)` into `queries`. It ends with `_ = queries; service.WaitForShutdown("mcpserver")` — the query service is built but discarded, and there is no HTTP server or Orchestrator client yet.
- `internal/orchestrator/heuristics.go:53-96` — `handleHeuristicSearch` (over `heur.Query`) and `handleHeuristicTrace` (over `heur.Trace`): the exact same query logic the two MCP read tools must expose. Shows k-clamping (`defaultSearchK=10`, `maxSearchK=100`), error masking (`log.Printf` + `writeErr(500,"internal error")`), and DTO mapping. `get_optimized_heuristics`/`trace_causal_chain` are MCP-transport re-skins of these two handlers.
- `internal/orchestrator/sandboxclient.go:73-130` — The only existing outbound service-to-service client: `SandboxClient{baseURL, client}`, `NewSandboxClient(baseURL, httpClient)` (nil → `http.Client{Timeout: defaultSandboxTimeout}`), and a private `post(ctx, path, in, out)` that JSON-marshals, sets `Content-Type: application/json`, checks `StatusOK`, and JSON-decodes. This is the template for the Orchestrator proxy client — but see the multipart caveat below.
- `internal/orchestrator/submit.go:39-98` — The `POST /goals` target the `submit_analyst_goal` proxy must call. It is `multipart/form-data`, not JSON: `r.ParseMultipartForm`, reads `goal` (`r.FormValue`), and a data source via `ingest` — either a `file` part (`r.FormFile("file")`) OR an `import_path` field (exactly one; both → 400). Returns `201` with `{"optimization_function_id": ...}`. The proxy must construct a multipart body with a `goal` field plus `file`/`import_path`, which the JSON `sandboxclient.go` pattern does not cover.

### Convention Anchors
- Consumer-defined narrow interfaces: `internal/orchestrator/server.go:36-70` defines `heuristicsService`, `goalStore`, etc. at the consumer, with `cmd/` passing concrete `*heuristics.Service` etc. The MCP server should define its own narrow interfaces (e.g. a `heuristicsQuerier` with `Query`/`Trace`, and a `goalSubmitter` for the proxy) so tool handlers are unit-testable with fakes — mirroring `fakeHeur` in `server_test.go:66-80`.
- Infra-constructor convention: constructors take primitive args / already-built collaborators (`NewSandboxClient(baseURL, httpClient)`, `NewServer(...)`), never a `Config`. cmd/ reads config and passes pieces.
- Error masking + logging in handlers: `log.Printf("<service>: <what>: %v", err)` then `writeErr(w, 5xx, "internal error")` (heuristics.go:70-72, submit.go). Validation errors return the real message at 4xx. MCP tool handlers return errors via `CallToolResult.IsError`; internal failures should log server-side and surface a masked message.
- DTO snake_case mapping: internal domain/graph types carry no JSON tags, so every wire response defines a local `*DTO` struct with explicit `json:"snake_case"` tags (heuristics.go:18-49). Same discipline applies to MCP tool output schemas.
- `Routes()` returns `http.Handler` from `http.NewServeMux()` with method-prefixed patterns (server.go:120, sandbox server.go:30). The MCP transport instead produces its handler via `mcp.NewStreamableHTTPHandler` — a different handler-construction path than the mux convention, handed to `RunHTTPServer`.
- CGO_ENABLED=0 distroless-static build: `cmd/mcpserver/Dockerfile:8-11` is identical to orchestrator's. This is the same constraint that forces `sandboxclient.go` to keep CGO-free copies of the sandbox wire DTOs and never import `internal/sandbox` (sandboxclient.go:19-25). The MCP server must not import `internal/sandbox` either; it only needs `heuristics`/`graph`/`domain`, all CGO-free.
- Integration vs unit tests: unit tests use `httptest.NewRequest`/`NewRecorder` + `srv.Routes().ServeHTTP` with in-package fakes (`server_test.go`); live-stack tests gate on `ARBORETTE_INTEGRATION` via `testutil.RequireIntegration` (`heuristics_test.go:17`). The multipart-body test helper `multipartBody` (server_test.go:122) shows how to build the exact form the proxy must emit.
- Compose wiring already exists: `mcpserver` service is in the compose file (build context + Dockerfile, `env_file: [.env]`, `<<: *app-environment`, depends_on migrate/ollama-pull/neo4j) but publishes **no ports** and sets no MCP-specific env. Serving HTTP requires adding a port mapping and the new MCP env vars.

### go-sdk (v0.8.0) notes — not yet in go.mod
- Present in module cache at `/Users/janbialostok/go/pkg/mod/github.com/modelcontextprotocol/go-sdk@v0.8.0/mcp/`; needs `go get`/`go mod tidy` to enter `go.mod`. Pure-Go, CGO-free (safe for the distroless-static build).
- Server: `mcp.NewServer(*mcp.Implementation, *mcp.ServerOptions)` (server.go:107). Typed tools via the generic `mcp.AddTool[In, Out](s, *mcp.Tool, ToolHandlerFor[In,Out])` (server.go:397) — it auto-infers input/output JSON schemas from the Go `In`/`Out` types via `jsonschema.ForType` (reading `jsonschema` struct tags), so tool DTOs drive the schema directly. `ToolHandlerFor[In,Out] = func(ctx, *CallToolRequest, In) (*CallToolResult, Out, error)` (tool.go:55). A raw form `Server.AddTool(*Tool, ToolHandler)` (server.go:185) exists for hand-written schemas but is not needed here.
- **Two SDK constraints that shape the tool DTOs (both verified against v0.8.0 source):**
  - *Both `In` and `Out` must infer to a `type:"object"` schema.* `Server.AddTool` panics at registration if either schema's type is not `"object"` (server.go:191-215: `output schema must have type "object"`). A slice `Out` infers to `type:"array"` and therefore **panics** — so a tool that returns a list must wrap it in an object DTO (`{ "heuristics": [...] }`, `{ "triplets": [...] }`), never a bare `[]T`. Since `RegisterTools` runs at startup, getting this wrong crashes the server (and every test that registers the tools) on boot.
  - *Input validation happens before the handler runs.* The SDK validates the arguments against the inferred input schema and returns `jsonrpc2.ErrInvalidParams` on failure (server.go:263-266) — this reaches the client as a **call error** (non-nil `error` from `CallTool`), not a `CallToolResult{IsError:true}`. jsonschema-go marks every struct field required unless it is tagged `omitempty`/`omitzero`, so an optional input field (e.g. `k`) must be tagged `json:"k,omitempty"` (or made a pointer) or callers omitting it are rejected pre-handler. The `IsError:true` result path (server.go:281-292) is reached only for errors the handler itself returns (collaborator failures, or semantic checks on a present-but-invalid value).
- Transport: `mcp.NewStreamableHTTPHandler(getServer func(*http.Request) *mcp.Server, *mcp.StreamableHTTPOptions) *StreamableHTTPHandler` (streamable.go:78) is an `http.Handler` — feed it to `service.RunHTTPServer`. In-memory client/server for tests via `mcp.NewInMemoryTransports()` + `mcp.NewClient`/`s.Connect` (`server_example_test.go`). Examples at `streamable_example_test.go`.
- Auth (used downstream, not here): the SDK ships `auth.RequireBearerToken(...) func(http.Handler) http.Handler` (auth/auth.go:61) — standard middleware wrappable around the streamable handler. This is the seam arborette-09 uses to add the `authorization_token` gate; this shell only needs to expose the handler as a single wrappable value.

### Proposed Alignment
Follow the existing service patterns closely: replace the mcpserver main's `WaitForShutdown` tail with `service.RunHTTPServer`, keep the already-correct read-stack wiring (`ServiceDSN`, `heuristics.NewService`), and reuse the orchestrator's DTO-mapping and error-masking conventions inside MCP tool handlers rather than inventing new ones. Put the tool-handler + client logic in a new `internal/mcpserver` package (mirroring `internal/orchestrator`), keeping `cmd/mcpserver/main.go` a thin wiring layer. Two forced design decisions: (1) the `submit_analyst_goal` proxy must build a `multipart/form-data` request (`goal` + `import_path`), which the JSON-only `sandboxclient.go` template does not cover — model the client on `sandboxclient.go`'s shape but swap `json.Marshal`/`application/json` for a `mime/multipart.Writer` body; and (2) `internal/config` must gain an `MCPConfig{Port, OrchestratorURL}` sub-struct with a `Load` block and `.env.example`/compose port+env additions.

## Implementation Steps

1. **Add the Go MCP SDK to the module**
   - `go get github.com/modelcontextprotocol/go-sdk@v0.8.0` then `go mod tidy`, moving it (and its `github.com/google/jsonschema-go` transitive dep) into `go.mod`/`go.sum`. The SDK is pure-Go; confirm the mcpserver still builds under `CGO_ENABLED=0` (Verification).

2. **Extend `internal/config` with `MCPConfig`**
   - Add `MCPConfig struct { Port string; OrchestratorURL string }` to `config.go` and an `MCP MCPConfig` field on `Config` (config.go:16-25).
   - In `Load` (config.go:153) add an `MCP: MCPConfig{ Port: env("MCP_PORT", "8082"), OrchestratorURL: env("MCP_ORCHESTRATOR_URL", "http://orchestrator:8080") }` block. Document both in `.env.example` alongside the existing service blocks (env.example:41-47 pattern). The `authorization_token` secret is intentionally *not* added here — arborette-09 introduces it when it gates the endpoint.

3. **Orchestrator proxy client (`internal/mcpserver/orchestratorclient.go`)**
   - New package `internal/mcpserver`. Define `OrchestratorClient{ baseURL string; client *http.Client }` and `NewOrchestratorClient(baseURL string, httpClient *http.Client) *OrchestratorClient` — same shape as `NewSandboxClient` (sandboxclient.go:82), nil client → `http.Client{Timeout: ...}` with a named default timeout const.
   - `SubmitGoal(ctx, goal, importPath string) (optimizationFunctionID string, err error)`: build a `multipart/form-data` body with `mime/multipart.NewWriter` — a `goal` form field and an `import_path` form field — POST to `baseURL + "/goals"` with `Content-Type: w.FormDataContentType()`. On `201`, decode `{"optimization_function_id": ...}`; on non-201, read the orchestrator's `{"error": ...}` body and return it as the error message so the analyst sees the real validation reason (e.g. missing/escaping import path).
   - MVP scope decision (record in a code comment): the MCP `submit_analyst_goal` tool accepts a `goal` plus an `import_path` (on-disk path under the orchestrator's read-only import mount, submit.go:133-165), **not** a raw file upload — an MCP tool call carries structured JSON args, not a multipart file part, and the orchestrator's `import_path` ingestion path is the natural fit. The proxy sends exactly the `import_path` branch of `ingest` (submit.go:122).

4. **Tool DTOs + handlers (`internal/mcpserver/tools.go`)**
   - Define narrow consumer interfaces in this package: `heuristicsQuerier` with `Query(ctx, string, int) ([]heuristics.Match, error)` and `Trace(ctx, string) ([]graph.CausalTriplet, error)`; `goalSubmitter` with `SubmitGoal(ctx, goal, importPath string) (string, error)`. `*heuristics.Service` and `*OrchestratorClient` satisfy them; fakes satisfy them in tests (mirror `fakeHeur`, server_test.go:66).
   - Define input/output DTO structs with `json` + `jsonschema` tags for schema inference. **Every output DTO is an object** (never a bare slice — see the SDK-constraints note in the Pattern Survey; a slice `Out` panics `AddTool`), and optional input fields carry `omitempty`:
     - `get_optimized_heuristics`: input `{ operational_state string (required), k int (optional, tagged json:"k,omitempty") }`; output `{ heuristics []{ id, definition } }` — the inner element reuses the shape of `heuristicMatchDTO` (heuristics.go:23), wrapped in a `heuristics` field so the output schema is an object. Clamp `k` with `defaultSearchK`/`maxSearchK` constants (heuristics.go:13-16) — default when 0/negative, cap at max.
     - `trace_causal_chain`: input `{ meta_heuristic_id string (required) }`; output `{ triplets []{ state, intervention, outcome } }` — the inner element is `tripletDTO`-shaped with snake_case fields, wrapped in a `triplets` field. Port `toTripletDTO` (heuristics.go:98) into this package.
     - `submit_analyst_goal`: input `{ goal string (required), import_path string (required) }`; output `{ optimization_function_id string }` (already an object).
   - Implement three `mcp.ToolHandlerFor[In,Out]` handlers (tool.go:55). The SDK enforces the input schema before the handler runs, so an omitted/typewrong required field is already rejected as a `jsonrpc2.ErrInvalidParams` call error (server.go:263-266) — handlers do **not** re-check presence of required fields. Each handler performs any *semantic* validation on present values (e.g. reject an `operational_state` that is empty after trimming), calls the collaborator, and maps the result into the object output DTO. When a handler returns a plain `error`, the SDK copies its `err.Error()` verbatim into the `CallToolResult` text and sets `IsError: true` (`setError`, protocol.go:121) — so error text is analyst-visible. Two distinct error policies follow from that:
     - **The two read tools** (`get_optimized_heuristics`, `trace_causal_chain`) mask genuine Neo4j/pgvector failures: `log.Printf("mcpserver: <tool>: %v", err)` then return an error whose message is a masked `"internal error"` — mirroring the orchestrator handler masking (heuristics.go:70), so store internals never leak to the caller.
     - **`submit_analyst_goal`** does **not** re-mask: it passes the orchestrator's returned error message through (Step 3 already extracts the orchestrator's `{"error": ...}` body, which is analyst-safe because the orchestrator masks its own 5xx internals). This is what lets the Verification spot-check see the orchestrator's real 400 (e.g. an escaping `import_path`) instead of a generic `"internal error"`. It may still `log.Printf` the failure server-side for observability.
   - A registration helper `RegisterTools(s *mcp.Server, heur heuristicsQuerier, goals goalSubmitter)` calls `mcp.AddTool` three times with each `mcp.Tool{Name, Description}` and its handler.

5. **Serve the MCP server in `cmd/mcpserver/main.go`**
   - Keep the existing read-stack wiring (main.go:25-45). Replace `_ = queries; service.WaitForShutdown(...)` (main.go:46-48) with: build `orchClient := mcpserver.NewOrchestratorClient(cfg.MCP.OrchestratorURL, nil)`; `srv := mcp.NewServer(&mcp.Implementation{Name: "arborette-mcp", Version: ...}, nil)`; `mcpserver.RegisterTools(srv, queries, orchClient)`; `handler := mcp.NewStreamableHTTPHandler(func(*http.Request) *mcp.Server { return srv }, nil)`; `service.RunHTTPServer("mcpserver", ":"+cfg.MCP.Port, handler)` (httpserver.go:27). Log the listen line as the other services do (main.go:45 style). Keep `handler` as a single `http.Handler` value so arborette-09 can wrap it with bearer-token middleware in one place without restructuring this main.

6. **Compose + env wiring**
   - In `docker-compose.yml` `mcpserver` service: add a `ports: ["8082:8082"]` mapping (it currently publishes none) so the server is reachable for local testing, and ensure `MCP_PORT`/`MCP_ORCHESTRATOR_URL` reach the container (they load from `env_file: [.env]`). Add `orchestrator: { condition: service_started }` to the mcpserver `depends_on` so the proxy target exists (orchestrator defines no healthcheck — gate on start, matching how the orchestrator gates on the sandbox). Add the two `MCP_*` vars to `.env.example`. Public exposure + `authorization_token` protection is arborette-09's step, not this one.

7. **Tests**
   - Unit (`internal/mcpserver/tools_test.go`, no build tag): construct the three handlers with in-package fakes for `heuristicsQuerier`/`goalSubmitter`, exercise each via an in-memory `mcp.NewInMemoryTransports()` client + `mcp.NewClient` (per `server_example_test.go`), and assert: `get_optimized_heuristics` maps matches → `{ heuristics: [{id,definition}] }` and clamps `k`; `trace_causal_chain` maps triplets → `{ triplets: [snake_case DTOs] }`; `submit_analyst_goal` returns the fake's id. For the error paths, distinguish the two SDK surfaces: a **collaborator error** yields a `CallToolResult{IsError:true}` with a masked message (assert on the returned result), while an **omitted required arg** (e.g. missing `operational_state`) is rejected by SDK schema validation and surfaces as a non-nil `error` from `client.CallTool` (`jsonrpc2.ErrInvalidParams`), not an `IsError` result — assert the call returns an error. Also assert a call that omits the optional `k` succeeds (guards the `omitempty` tag).
   - Orchestrator-proxy unit (`orchestratorclient_test.go`): stand up an `httptest.Server` that asserts the request is `multipart/form-data` carrying `goal` + `import_path` (parse with `r.ParseMultipartForm`) and returns `201 {"optimization_function_id":"opt-x"}`; assert `SubmitGoal` returns `"opt-x"`. Add a non-201 case returning `{"error":"..."}` and assert the error surfaces that message.
   - Integration (runtime-skip gated via `testutil.RequireIntegration(t)` as the test's first line — **no** `//go:build` tag, exactly mirroring `heuristics_test.go:17`; there are no build tags anywhere under `internal/`, and adding one would make the `-run Integration` command below silently run zero tests): seed a triplet + Meta-Heuristic + embedding as in `heuristics_test.go:38-63`, start the real `heuristics.Service`, register tools on an `mcp.Server`, connect an in-memory `mcp.Client`, and call `get_optimized_heuristics` / `trace_causal_chain` end-to-end against live Neo4j + pgvector.

## Verification

- `go build ./...` and `CGO_ENABLED=0 GOOS=linux go build ./cmd/mcpserver` both succeed (the SDK must not break the static build).
- `go vet ./...` and `go test ./internal/mcpserver/...` pass (unit tests, no live stack).

- Manual smoke against the running compose stack: an MCP `initialize` + `tools/list` POST to `http://localhost:8082` lists exactly `get_optimized_heuristics`, `trace_causal_chain`, `submit_analyst_goal`. A `submit_analyst_goal` call with a `goal` + a valid `import_path` returns an `optimization_function_id` and the same goal appears via the orchestrator's registry, confirming the proxy wrote through the Orchestrator and the MCP server performed no direct write.
- Edge cases to spot-check: `get_optimized_heuristics` with a huge `k` is clamped to `maxSearchK`; `trace_causal_chain` on an unknown id returns an empty-triplet result (not an error); `submit_analyst_goal` with an `import_path` that escapes the import mount surfaces the orchestrator's real 400 message rather than a masked 500.
- Note: the server is intentionally unauthenticated at this shell's boundary. The 401-without-token / 200-with-token behavior and public reachability are added and verified by arborette-09 (Agent Chat Backend); do not treat their absence here as a gap.
