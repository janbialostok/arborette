# Arborette V2 — Dual-Engine Causal Layer

## Overview

Arborette V1 is a purely observational engine: an Active Hypothesis Loop (Engine A) measures LLM-proposed data segments as correlational findings, and a beam-search Sleep Cycle abstracts high-value macro-segments into domain-agnostic Meta-Heuristics. Every empirical edge carries `epistemic_source: observational`, and V1's design (R25 of `.turbo/specs/arborette.md`) reserved the seams — the epistemic discriminator, the `SearchPolicy` interface, the pluggable execution surface — so a causal layer could land additively.

V2 builds that layer, with one deliberate upgrade over the original roadmap: instead of requiring an analyst-wired experimental sandbox, **the system infers causality from the source data autonomously**. A new verification engine (Engine B) discovers a causal graph over the dataset's columns (conditional-independence testing grounded in the data, with an LLM resolving edge directions statistics cannot), then verifies observational findings by computing confounder-adjusted do-calculus effects and stress-testing them with a refutation battery — all as read-only sandbox queries, no human in the loop. Verified findings gain `causal_inferred` edges; claims the data cannot support are reported as *confounded* or *not identifiable*, which are first-class answers an analyst could not produce themselves. A Control Plane Router directs work between the engines: intent classification at intake, an explicit per-finding verify affordance, and budgeted auto-promotion of top findings. The Sleep Cycle's search policy swaps from the level-wise beam to **knowledge-guided UCT-MCTS**: the conjunction lattice (now fed by schema-derived atoms) remains the measurable state space, but the ever-growing Meta-Heuristic graph supplies expansion proposals (grounded heuristics — the deferred Cold-Start reuse path) and selection priors, and causal evidence multiplies value estimates — so search quality compounds as knowledge accumulates.

The spec also folds in the improvement-backlog items V2 touches, mitigates, or depends on: schema-derived atoms, sandbox staging amortization, sandbox boundary hardening, the real job launcher, heuristic-retrieval integrity (relevance floor + embedding reconcile), stored-prompt-injection hardening, audit-write authentication, the Meta-Heuristic N+1, Phase-1 value grounding, windowed objectives, service-seam consolidation, and a bundled causal-ground-truth dataset.

## Users

- **Business/data analyst (primary, non-technical).** Registers goals in plain English; in V2 additionally sees *why* a segment matters (causal vs merely correlated), can trigger verification of any finding, and can correct the discovered causal graph without being required to review it.
- **Downstream AI agents (via MCP).** Consume Meta-Heuristics and traces; in V2 they can distinguish correlation from inferred causation per edge and request verification of a finding.
- **Operator/developer.** Runs the local stack; V2 must be end-to-end demoable locally (real launcher, bundled dataset that exercises both engines at defaults).

## Requirements

### Control Plane Router

- **R1.** When an analyst registers a goal, the system shall classify the goal's intent (`explore` — populate the graph observationally — vs `verify` — test a specific causal claim) via a Claude call against the goal text and introspected schema, record the track on the goal, and dispatch accordingly: `explore` runs Engine A as today; `verify` runs Engine A to establish baseline findings and then dispatches Engine B on the findings that match the claim.
  - Acceptance: on the `verify` track the classifier additionally extracts the claim — the segment description (columns/values implicated) and the direction of the claimed effect — as structured output alongside `{track, rationale}`.
  - Acceptance: the Verifier constructs the claimed segment directly from the extracted claim (a filter conjunction, validated by the same deterministic column/value checks as Phase-1 proposals), measures its naive effect, and verifies it — the claim is never gated on Phase 1 happening to rediscover it.
  - Acceptance: before verification, the constructed claim is **reified as a full observational triplet** — State = the goal's global baseline, Intervention with a deterministic id (goal id + canonicalized claim filter, mirroring the sleep-derived id scheme), `sleep_derived: false`, a `claim_derived` provenance flag in properties, Outcome = the measured naive effect. This gives R11 an Intervention to attach to and R12 its idempotency key, makes the claim visible in `trace_causal_chain`, and lets it participate in the lattice as an ordinary measured finding. Phase-1 findings that match the claim (deterministic filter-overlap scoring) are additionally verified under the R3 budget. Only a claim that fails schema validation produces the first-class cannot-construct outcome (SSE + goal status), which reports the validation reason rather than implying the claim was tested and unsupported.
- **R2.** As an analyst or downstream agent, I want an explicit "verify this finding" affordance so that any observational finding can be causally tested on demand.
  - Acceptance: exposed as a REST endpoint on the orchestrator, a button on the web finding/triplet surface, and an MCP tool (`verify_finding`).
  - Acceptance: dispatch is asynchronous; result delivery reuses the existing SSE/audit patterns.
  - Acceptance: explicit verifies are analyst/agent-initiated and therefore exempt from the R3 auto-promotion budget — they are bounded instead by the per-goal in-flight concurrency cap (R12), so a human request is never refused because automation already spent the budget.
- **R3.** When a Phase-1 run completes on an `explore` goal, the router shall auto-promote the top-N findings (ranked by the support-shrunk score already used for publication selection) to Engine B verification, bounded by a per-goal verification budget; N, the budget, and a global kill-switch are config. Auto-promotion failures never fail the Phase-1 run.
  - Acceptance: the per-goal verification budget governs **autonomous** spend only (R3 auto-promotion and R1 claim-match extras). Analyst-initiated dispatches — R1's primary constructed-claim verification (always runs), R2 explicit verifies, and R7 correction-triggered re-verification — are exempt from it and bounded instead by the per-goal in-flight cap (R12) plus, for R7, the staleness re-verification cap; so automation can never starve a human action.

### Causal Discovery (Engine B, stage 1)

- **R4.** The system shall discover a causal skeleton over the dataset's columns algorithmically, from the data: pairwise and conditional-independence tests (chi-square / G-test on categorical pairs, partial correlation on numeric pairs, binned hybrid for mixed pairs) executed as read-only aggregation queries through the Sandbox Execution service, PC-style with a bounded conditioning-set size. No edge exists unless the data supports dependence.
  - Acceptance: discovery is single-flighted per (goal, data-source) with a **cross-process lock** — a Postgres advisory lock on the (goal, data-source) key, since the Verifier's serve mode (R2 dispatches) and job mode (R3 batches) are separate processes an in-process singleflight cannot coordinate. Exactly one discovery runs even when R3 fans out N concurrent verifications on first need; concurrent requesters wait on the one result. Graph writes are keyed on (goal, data-source, version) so a crashed discovery re-runs idempotently.
  - Acceptance: a CI test that errors or times out fails **closed**: the pair's status becomes unknown, the edge is retained unoriented, and effects whose identifiability depends on it report not-identifiable (R10) — a failed test never silently drops or directs an edge.
  - Acceptance: discovery is bounded on wide datasets by a configurable column cap; when the dataset exceeds it, columns are selected deterministically — objective columns and finding-referenced columns first, then by pairwise association strength with the objective columns — and excluded columns are recorded on the graph so verification can report that identifiability was assessed against a column subset.
- **R5.** Where the equivalence class leaves an edge unoriented, the system shall ask Claude to orient it using column semantics (names, types, sample values) as a domain prior. Claude may only orient or abstain on edges the statistics produced — it shall never add or delete an edge. Edges Claude abstains on remain unoriented and identifiability suffers accordingly (see R10).
- **R6.** The system shall persist the discovered causal graph per (goal, data-source) pair, with per-edge provenance (`statistical`, `llm_prior`, or `analyst`) and orientation confidence, and expose it via the orchestrator API.
  - Acceptance: a goal's data source is immutable after registration (as in V1 — `data_source_ref` binds at submit); new data means a new goal. The (goal, data-source) key therefore never churns underneath a graph, its corrections, or its verification records. Migrating analyst corrections across datasets/goals is explicitly deferred.
- **R7.** As an analyst, I want to correct the discovered graph — flip an edge direction, delete an edge, add a known confounder edge — without my review gating anything, so that domain knowledge improves the model when I have it and is not a bottleneck when I don't.
  - Acceptance: corrections are recorded with `analyst` provenance and never overwritten by re-discovery.
  - Acceptance: a correction marks the verification results of affected findings stale and triggers their re-verification, bounded by a dedicated staleness re-verification cap (analyst-initiated — exempt from the R3 autonomous budget, per R3's accounting rule).

### Verification & Refutation (Engine B, stage 2)

- **R8.** When a finding (segment → outcome) is dispatched for verification, the system shall identify the adjustment set from the causal graph (backdoor criterion), compute the confounder-adjusted effect P(outcome | do(segment)) via stratified, reweighted aggregation in the sandbox, and report it alongside the naive observational effect. The adjusted effect is exactly computed from the data — the V1 non-hallucination guarantee (V1 R7) extends unchanged.
  - Acceptance: the mapping from finding to graph is defined as: **treatment** = the segment-membership indicator (the filter conjunction set jointly, do(S=1)), with treatment columns T = the columns the segment's filters reference; **outcome columns** O = the columns the objective's value expression (or bare target) references; **adjustment set** Z = the union of the graph's parents of T, excluding members of T and O. Because the conjunction is intervened on jointly, causal ordering among T's own columns does not enter the adjustment.
  - Acceptance: MVP verification supports plain aggregate objectives only. A finding whose goal uses an entity-relative/windowed objective (R21) receives a first-class `unsupported_objective` verification outcome rather than an unsound adjustment; causal semantics for windowed outcomes are deferred.
- **R9.** The system shall subject every adjusted effect to a refutation battery — at minimum: placebo-treatment (a random pseudo-segment of matched support must show ~zero adjusted effect), subsample stability, and random-confounder insertion — and combine the outcomes into a refutation score in [0,1].
- **R10.** If the causal graph does not identify the effect — an unoriented edge incident to the treatment or adjustment columns on a path to the outcome, or adjustment strata too sparse to estimate (below the support floor) — the system shall record **not identifiable** as a first-class verification outcome; if the adjusted effect collapses relative to the naive effect, it shall record **confounded**, naming the adjusting columns. Neither outcome writes a `causal_inferred` edge; both are surfaced to the analyst with the same prominence as a confirmation. (Latent-confounder detection is out of scope — PC-style discovery assumes causal sufficiency; FCI-class algorithms are deferred, so identifiability failures are graph- and support-based only.)
- **R11.** A verification that survives refutation shall be written additively to the graph: a new Outcome node holding the adjusted effect, linked from the finding's existing Intervention node by a `PRODUCED` edge carrying `epistemic_source: causal_inferred` and a confidence derived from the refutation score. Observational edges are never modified or removed; `trace_causal_chain` shows both.
  - Acceptance: the causal Outcome carries `verification_status: verified` (it is exactly computed, the query-type analog), and **additivity is enforced at the read paths**: every consumer that collects observational findings — `ListEligibleFindings` (which currently matches `PRODUCED` with no epistemic clause, `internal/graph/neo4j.go:342`), Phase-2 atom building, and any future collection query — shall filter on the edge with `coalesce(epistemic_source, 'observational') = 'observational'`, so causal Outcomes never re-enter the lattice as findings or double-count their Intervention's atoms. `TraceCausalChain` intentionally returns both, labeled. The **causal-evidence lookup** that serves R16's multiplier and R33's weighting is a distinct read path explicitly exempt from this filter — it reads only `causal_inferred` edges, latest non-superseded per intervention.
  - Acceptance: the causal Outcome takes a **deterministic id** (intervention id + causal-graph version), so re-runs MERGE idempotently. When a verification at a newer graph version **completes with any outcome** for the same intervention, prior causal edges for that intervention are marked `superseded: true` — a `causally_verified` result carries the supersession in the same write as its new edge, and a confounded / not-identifiable / unsupported result performs the supersession as a standalone retraction write, so a correction that invalidates a causal claim actually removes it from serving. All serving paths (R16 multiplier, R25 retrieval weighting, R33 MCP output, R32 badges) read only the latest non-superseded causal edge per intervention, while `trace_causal_chain` may show superseded ones labeled as historical. The V1 rule "observational edges are never modified" is unchanged — supersession is the causal-edge lifecycle only.
- **R12.** Every verification (dispatch, outcome, refutation detail) shall be persisted, streamed on the goal's SSE channel, and reported to the audit trail through the authenticated internal audit API (R27).
  - Acceptance: verification dispatch is idempotent on the key (goal id, intervention id, causal-graph version): the verification-records table enforces uniqueness on that key, and a duplicate dispatch — from any of the three sources (R1/R2 explicit, R3 auto-promotion, R7 staleness) — coalesces to the existing in-flight or completed record instead of re-running. A graph correction bumps the graph version, which is what makes R7 re-verification a new record rather than a duplicate.
  - Acceptance: the per-goal verification budget is decremented transactionally at record insertion (dispatch-accept), so concurrent dispatches cannot overspend; the Verifier bounds its own concurrency with a worker pool sized within the sandbox's per-request concurrency cap (R28).
  - Acceptance: `pending` records carry a lease deadline the Verifier heartbeats; a record whose lease has expired (Verifier crash mid-verification) is transitioned to `failed` — by a reaper or lazily at the next dispatch touching its key — refunding its budget spend when it was budgeted and releasing its in-flight-cap slot. Duplicate-dispatch coalescing applies only to live in-flight (leased) or completed records.
  - Acceptance: because a crash does not change the (goal, intervention, graph-version) key, re-dispatching a `failed` record is a **re-lease** — an UPDATE transitioning `failed` → `pending` with a fresh lease — not a new insert. Budget/cap charging applies uniformly at **dispatch-accept** (whether that is the initial insert or a re-lease), so each live attempt is charged exactly once: charge at accept, refund at reap.
  - Acceptance: a **per-goal in-flight verification cap** (config) bounds how many verifications may hold live leases for one goal at a time; it is the bound R1/R2/R7's analyst-initiated dispatches rely on, and it sits inside the Verifier's global worker pool.

### Epistemic Contract

- **R13.** The `EpistemicSource` domain adds a third value, `causal_inferred`, ordered between `observational` and the still-reserved `interventional` (physical execution, deferred). All consumers — Sleep-Cycle scoring, `trace_causal_chain`, `get_optimized_heuristics`, the web UI — shall treat an unknown/missing value as `observational` (preserving V1 R25's forward-compatibility rule) and shall expose the label wherever an edge is rendered or served.
  - Acceptance: `causal_inferred` is presented with its assumptions attached, not as established causation: every surface that renders or serves it (R32 web views, R33 MCP output) carries the caveat that the inference is conditional on the discovered causal graph and its no-latent-confounder (causal sufficiency) assumption — the refutation battery cannot detect unmeasured confounding. Analyst-facing copy says "causally supported (given the discovered model)", not "proven".

### Knowledge-Guided Sleep Cycle (V2 Phase 2)

- **R14.** The system shall provide a UCT-MCTS implementation of the existing `SearchPolicy` interface (`internal/sleepcycle/search.go`), selected by config (`SLEEPCYCLE_POLICY=beam|uct`); the shipped default is `beam` until the calibration gate below passes, after which the default flips to `uct`. The driver, measurement path, budgets, and write-back are unchanged.
  - Acceptance (calibration gate): the default flips to `uct` only once its constants are calibrated against the R30 ground-truth dataset and a regression assertion shows UCT matching or beating the beam's winners there at the default measurement budget.
- **R15.** The UCT policy's expansion shall draw candidates from two sources: (a) **schema-derived atoms** (R18), and (b) **grounded Meta-Heuristics** — heuristics retrieved by similarity from the pgvector corpus and instantiated into concrete filter conjunctions: via the persisted ontology-term mapping (see below) when the heuristic originated from the same dataset, via a Claude grounding call otherwise, with every grounded candidate deterministically validated against the introspected schema (columns per `UnknownFilterColumns`, values per R20) before measurement. This realizes the Cold-Start reuse path V1 deferred.
  - Acceptance: the abstraction stage is extended to persist, on the Meta-Heuristic node, the `OntologyTerms` concrete↔ontological pairs the abstraction call already produces (today they exist only transiently on `llm.Abstraction` and are dropped by `CreateMetaHeuristic`) plus the heuristic's origin (goal id + data-source ref). Node properties ride the existing open properties map, so this is additive.
  - Acceptance: pre-V2 heuristics lacking persisted terms ground through the Claude path; a grounding that fails validation is dropped, not repaired.
- **R16.** UCT selection priors shall incorporate heuristic-similarity scores; value backpropagation shall weight measured values by supporting evidence, applying a configurable multiplier when a candidate's constituent findings carry `causal_inferred` edges — so search preferentially extends causally validated structure. The multiplier reads causal evidence through R11's dedicated causal-evidence lookup (latest non-superseded edge per intervention), which is exempt from the observational-only collection filter.
- **R17.** The `SearchPolicy` contract shall require (documented on the interface, tested per implementation) that no generated candidate conjoins two atoms sharing a `(field, op)` pair — the degeneracy fix applies to every policy, beam included, not as a beam patch.
- **R18.** The system shall augment `buildAtoms` with schema-enumerated atoms behind a flag: enum/low-cardinality values directly, equal-frequency (quantile) cuts for numerics; one Claude critic call flags leakage/tautology columns (IDs, post-outcome columns, objective correlates) for exclusion and optionally ranks atoms for the first expansion level. Sleep-derived triplets from enumerated atoms carry their own provenance (no fabricated Phase-1 `sourceIDs`).
- **R19.** Macro-segments whose winning path used grounded-heuristic proposals shall record which Meta-Heuristic proposed them, so `trace_causal_chain` can show knowledge reuse.

### Engine A Hardening

- **R20.** Introspection shall return distinct values (capped) for low-cardinality columns; the tree-proposal prompt shall be grounded on them; and a deterministic post-check (the value analogue of `UnknownFilterColumns`) shall reject proposals naming nonexistent values, feeding the existing repair loop. A zero-row segment at measurement time becomes a distinct, non-fatal candidate outcome so the loop can retry rather than silently burning the branch.
- **R21.** The objective surface shall support entity-relative and windowed value expressions: goal registration may bind an entity-key column and a time/order column; the expression AST gains windowed constructs (lag, trailing aggregate over a partition) compiled to `PARTITION BY entity ORDER BY ts` window SQL in the sandbox. The widened grammar gets its own threat pass (identifier quoting, value binding, and allowlists extended to the window surface) before it ships — the narrowness of the current compiler is a load-bearing injection defense.

### Substrate & Performance

- **R22.** The sandbox shall amortize dataset staging within a run: staged datasets are cached keyed by `data_source_ref` (content-addressed, immutable) with a bounded cache size and eviction, so a multi-measurement run (MCTS rollouts, CI-test sweeps, refutation batteries) pays the download/parse cost once. Cache sizing and eviction are designed together with R26's disk-cap concerns.
- **R23.** `heuristics.Query` shall fetch Meta-Heuristics in one batched graph call (`GetMetaHeuristics(ctx, ids)`) instead of one session per similarity hit.
- **R24.** The Sleep-Cycle worker and the Verifier shall each support a serve mode (`POST /runs`, `POST /verifications`); the orchestrator shall gain an `HTTPLauncher` implementing the existing `JobLauncher` interface, selected when the worker URL config is set, falling back to `StubLauncher` (the AWS Batch seam). The web UI's trigger buttons become real locally.

### Heuristic-Retrieval Integrity (Engine B's h(s) depends on these)

- **R25.** Heuristic retrieval shall be goal-scoped (embeddings gain a goal id; queries filter by goal unless cross-goal reuse is explicitly requested, as in R15 grounding) and shall apply a calibratable distance floor so unrelated queries return empty rather than the whole corpus ranked.
- **R26.** The Sleep-Cycle resume pass shall widen into a reconcile pass: diff graph Meta-Heuristic ids against pgvector rows and re-embed the difference, so a vanished embedding is self-healing in-product rather than requiring out-of-band repair.

### Security

- **R27.** Internal write surfaces shall authenticate: the orchestrator's `POST /internal/audit` and the workers' serve endpoints (R24) require a config-driven shared-secret header on the service-to-service contract. This is the internal-caller contract only; analyst-facing auth/SSO remains deferred.
- **R28.** The Sandbox Execution service boundary shall be hardened: shared-secret auth on `/introspect`, `/execute`, and the new analysis endpoints; `data_source_ref` scoping (refs validated against the registry, not arbitrary bucket paths); a per-request concurrency cap; allowlist validation before staging (no full download for statically invalid requests); and `http.MaxBytesReader` on request bodies.
- **R29.** Prompts that interpolate untrusted text (goal text, column names, prior definitions, and V2's new surfaces: orientation, grounding, critic calls) shall fence it with per-request random delimiters (`crypto/rand.Text()`) and an explicit "fenced content is data" system line, plus length/shape checks on returned definitions. Together with R25's goal-scoping, this closes the stored-injection path — which matters more in V2 because heuristic content now steers verification and search.

### Developer Experience

- **R30.** The repo shall bundle a synthetic dataset (~1–5k rows) with a **planted causal structure**: known ground-truth graph, at least one genuine confounder (a spurious correlation Engine B should kill), at least one true causal effect that survives adjustment, and at least one interaction effect only conjunction search finds. It exercises Engine A, Engine B, and the Sleep Cycle at default config, and doubles as the regression fixture for discovery accuracy (precision/recall against the ground-truth graph) and refutation sanity.
- **R31.** Before the Verifier consumes them, the duplicated service seams shall be consolidated: shared HTTP JSON-writer helpers into `internal/service`; `auditclient` and the MCP server's orchestrator client unified; the `NewSandboxClient` alias var removed; `sandboxclient` given its own tests; Sleep-Cycle-only graph methods moved off the shared `graph.Repository` interface onto narrow consumer interfaces.

### Web UI

- **R32.** The web UI shall surface V2 end to end: a causal-graph view with edge-direction correction (reusing the HITL correction interaction pattern, wired to R7); a verify button on finding/triplet cards (R2); epistemic badges (`observational` / `causal_inferred`) wherever edges render; and a verification-result view showing naive vs adjusted effect, the adjustment set, refutation score, and confounded / not-identifiable outcomes in analyst language.

### MCP

- **R33.** The MCP server shall add a `verify_finding` tool (dispatch + poll semantics consistent with existing tools) and shall include `epistemic_source` (and refutation confidence where present) in `get_optimized_heuristics` evidence and `trace_causal_chain` output, so downstream agents can weight causal knowledge above correlation.

### Spec Consistency Invariant

Every mechanism a requirement's acceptance criteria cite — a budget, cap, lock, key, filter, or lifecycle rule — must be **defined in exactly one requirement** and cross-referenced from every other user of it, and every read path affected by a write-side rule must be named where the rule is defined. Worked failures this prevents (all caught in review rounds of this spec): an observational-only read filter that silently disabled the causal multiplier that needed the filtered edges (R11/R16); a per-goal in-flight cap relied on by three requirements but defined by none (R2/R3/R12); a supersession rule attached only to the confirming write, leaving non-confirming re-verification unable to retract a stale causal edge (R11); and an idempotency key that made crashed records permanently un-redispatchable because the re-dispatch transition wasn't specified (R12). Future edits to this spec must check new criteria against this invariant.

## Design

### Architecture

Four deployables, one new:

- **Orchestrator** (existing): gains the Router (intake intent classification in the submit path; auto-promotion hook at Phase-1 completion; `POST /goals/{id}/findings/{fid}/verify`), causal-graph read/correction endpoints, causal-verification result endpoints under `/goals/{id}/causal-verifications` (deliberately distinct from the existing HITL surface at `GET|POST /goals/{id}/verifications`), and `HTTPLauncher`.
- **Sandbox Execution** (existing): gains the analysis compile surface (below), staging cache (R22), and boundary hardening (R28). Stays stateless in semantics — the cache is a pure performance layer keyed on immutable content-addressed refs.
- **Sleep-Cycle Worker** (existing): gains serve mode, the UCT policy, schema atoms, grounding, reconcile pass.
- **Verifier** (new, `cmd/verifier` + `internal/verifier`): owns causal discovery, adjustment computation, and refutation. Serve mode (`POST /verifications`, one goroutine per verification with a per-verification deadline) plus one-shot job mode, launched via `JobLauncher` for batch auto-promotion. Consumes the consolidated `sandboxclient`, `auditclient`, and `graph.Repository` seams (R31 lands first). CGO-free like all non-sandbox services.

Routing flow: `POST /goals` → intent classification (one Claude call, structured output: `{track, rationale}`) → Engine A runs in both tracks → on `verify` track or explicit R2 dispatch or R3 auto-promotion, orchestrator calls the Verifier; Verifier ensures a causal graph exists for the (goal, data-source) (discovering on first need behind a per-(goal, data-source) single-flight, cached thereafter — R4), runs adjustment + refutation, writes results (leased records, deterministic causal-Outcome ids, supersession — R11/R12), reports audit events.

### Causal discovery pipeline

1. **Skeleton:** PC-style CI testing with conditioning sets bounded at size ≤ 2 (config). Tests compile to sandbox aggregation queries: contingency tables (`GROUP BY a, b [, c]` counts) for categorical pairs, moment aggregates for partial correlation on numerics, quantile-binned hybrids for mixed pairs. Test count at ≤ 20 columns and depth 2 is bounded and each test is one cheap query against the cached staging (R22).
2. **Orientation:** collider orientation and Meek rules run deterministically; remaining undirected edges go to Claude in one batched call (Opus 4.8, structured output listing per-edge `{direction | abstain, rationale}`). The statistics own edge existence; Claude owns only direction. Grammar-ceiling lesson applies: the edge list is data in the prompt, the strict schema stays flat and static.
3. **Persistence:** Neo4j, additive: `DataColumn` nodes per (goal, data-source, column) and `CAUSES` edges carrying direction, provenance (`statistical|llm_prior|analyst`), confidence, and test statistics. Node properties ride the existing open `properties` map; `CAUSES` is a new typed edge writer alongside `CreateProduced`. Analyst corrections (R7) update edges with `analyst` provenance, which re-discovery never overwrites.

### Verification math

Per R8's mapping: treatment = do(S=1) on the segment's filter conjunction jointly (treatment columns T), outcome columns O = the objective expression's referenced columns, Z = parents(T) \ (T ∪ O). Adjusted effect = Σ_z [agg(O | S, Z=z) · P(Z=z)] — one stratified aggregation query (`GROUP BY` over Z with the segment predicate, reweighted by stratum mass) plus one for the baseline; strata below the support floor trigger R10's not-identifiable outcome. Windowed objectives short-circuit to `unsupported_objective` (R8). Refutations re-run the same computation under perturbation: placebo segment (random predicate of matched support), K subsamples (`USING SAMPLE`), and a synthetic random column inserted into Z. Everything is a read-only SELECT; the non-hallucination guarantee holds because nothing is estimated off-data.

**Sandbox analysis surface:** a new `POST /analyze` endpoint (same hardening as `/execute`) with typed request kinds — `contingency`, `moments`, `stratified_effect`, `sampled_effect` — reusing the existing filter/expression compilers, identifier quoting, and value binding. Grouped aggregation is the only genuinely new SQL shape (plus R21's window surface, which gets its own threat pass).

### Knowledge-guided MCTS

Behind the existing seam: `uctPolicy` implements `Select/Update/Done`. State = filter-conjunction `Node` (unchanged). Expansion actions: extend-with-atom (from R18's vocabulary) or jump-to-grounded-heuristic (R15). Selection: UCT with priors — atom candidates prior-weighted by the critic ranking, grounded candidates by retrieval similarity. Update: standard UCT backprop of the measured objective (normalized against baseline), multiplied by the causal factor when constituent findings carry `causal_inferred` edges. Done: measurement budget or frontier exhaustion. The R17 invariant and existing subset-pruning live in candidate generation. Grounding: same-dataset heuristics instantiate via the ontology-term mapping R15 persists; cross-dataset (or terms-less pre-V2 heuristics) via one Claude call returning candidate filters as a JSON-encoded string field (grammar-ceiling pattern), validated by the same column/value checks as Phase-1 proposals; invalid groundings are dropped, not repaired (search has other candidates).

### LLM surface

Four new methods on `llm.Client`, each following the existing generate(+repair) pattern against the `completer` seam, all on Opus 4.8 with adaptive thinking, all strict-schema-flat with variable-size content prompt-grounded (the two grammar-ceiling axes — enum cardinality and recursive depth — stay out of strict schemas): `ClassifyGoalIntent`, `OrientCausalEdges`, `CritiqueAtoms`, `GroundHeuristic`. All prompt interpolation of goal text/column names/heuristic definitions uses R29 fencing.

### Data model summary

- New: `DataColumn` nodes, `CAUSES` edges (with a per-(goal, data-source) graph version, bumped by re-discovery or correction), `causal_inferred` epistemic value, causal-verification records (Postgres table `causal_verifications` — named to avoid the existing HITL `verification_queue`: id, goal, intervention id, causal-graph version, status ∈ pending|causally_verified|confounded|not_identifiable|unsupported_objective|failed (success is `causally_verified`, deliberately distinct from V1's HITL `confirmed` Outcome status), naive/adjusted effects, adjustment set, refutation score, staleness flag, lease deadline for R12 crash reaping; **unique on (goal, intervention, graph version)** for R12 idempotency), goal `track` + extracted-claim + verification-budget columns on the goal registry, embedding rows gain `goal_id` (R25).
- Extended: `ProducedEdge.EpistemicSource` domain; observational collection reads gain the `coalesce(epistemic_source,'observational')` edge filter (R11); `Intervention.Properties` records grounding provenance (R19); Meta-Heuristic nodes persist `OntologyTerms` + origin (R15); introspection response gains distinct-values (R20); goal registration gains entity/time column bindings (R21).
- Unchanged: triplet shape, publication selection, HITL extract path. (The abstraction stage's prompt/definition contract is unchanged; it additionally persists the term map + origin per R15.)

### Key flows

1. **Correction → invalidation (R7):** analyst flips an edge → orchestrator updates `CAUSES` edge (`analyst` provenance) → verification records whose adjustment set touched that edge are marked stale → re-verification dispatched under budget → SSE + audit events; web shows stale badge until re-verified.
2. **Auto-promotion (R3):** hypothesis loop completion hook ranks findings (support-shrunk score), takes top-N under budget, dispatches to Verifier; failures log + audit, never fail the run.
3. **Grounded proposal provenance (R19):** UCT winner via grounding move → write-back records heuristic id in the derived Intervention's properties → trace renders "proposed by [heuristic]".

## MVP Scope

**In:** everything in Requirements — Router (all three routing points), autonomous discovery + correction surface, adjustment + refutation with confounded/not-identifiable outcomes, `causal_inferred`, knowledge-guided UCT (same- and cross-dataset grounding within the single-tenant corpus), schema atoms, value grounding, windowed objectives with threat pass, staging cache, serve modes + HTTPLauncher, retrieval goal-scoping + floor + reconcile, sandbox/audit/prompt hardening, seam consolidation, causal ground-truth dataset, full web surface, MCP verify tool.

**Explicitly deferred:** physically-executed interventions and the container `ExecutionAdapter` (the `interventional` epistemic value stays reserved; `causal_inferred` is deliberately distinct so physical execution lands additively later); A*-guided experiment selection (meaningful only when executions are expensive); latent-confounder discovery (FCI-class algorithms — MVP reports not-identifiable rather than modeling latents); causal verification of windowed/entity-relative objectives (MVP returns `unsupported_objective`, R8); migration of analyst graph corrections across goals/datasets (R6); analyst-facing auth/SSO and per-division access control (R27's shared secrets are service-to-service only); cross-*tenant* heuristic reuse; Neptune migration; Message Batches; everything V1 already deferred that V2 doesn't name.
