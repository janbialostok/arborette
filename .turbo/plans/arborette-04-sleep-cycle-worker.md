# Plan: Sleep-Cycle Worker (Conjunction-Lattice Beam Search + Ontological Abstraction)

## Context

The Sleep Cycle turns a pile of individually-true observational segment findings into reusable expert knowledge. Phase 1 is a greedy, myopic search: an LLM proposes one data-segment at a time and its tree prunes past feature *combinations* whose value only emerges when conjoined. The Sleep Cycle compensates for that with a **budget-bounded search over the conjunction lattice** of the accumulated findings: it searches the space of segment conjunctions for high-value **macro-segments** that beat any single Phase-1 segment against the goal's objective, then has an offline LLM abstract each winning path into a generalized, domain-agnostic `Meta-Heuristic`. (This replaces the earlier Louvain-clustering design; Louvain is deferred to a future cross-dataset heuristic-grouping optimization — see spec R9 / MVP Scope / V2 Roadmap.)

The search is structured as a **policy-independent driver behind a `SearchPolicy` seam**. The V1 policy is a **level-wise beam search with anti-monotone (Apriori) minimum-support pruning**; UCT-MCTS — the previous design for this shell — is deferred to V2, where the mixed observational/interventional graph grows unboundedly and rollouts cost a container spin-up, i.e. where a budget-*allocation* algorithm actually has budget pressure to manage. V1 has none: with `MaxOrder = 3` the lattice is `C(n,1)+C(n,2)+C(n,3)` — 175 nodes at n=10 — and Phase 1 routinely yields under a dozen distinct predicates, so any sound search exhausts the lattice and selection order cannot change the result set. (This revision implements the improvements-backlog item "Replace Sleep-Cycle MCTS with a search-policy seam", noted 2026-07-25, and carries the corresponding spec edit — Step 1.)

It is a manually-triggered, ephemeral batch job (not a continuous service). Two crash-prone properties make its internal contract load-bearing: (1) search candidates are **empirically measured** by calling the Sandbox Execution service to run each candidate macro-segment's conjoined read-only query — the search never estimates a combination's value from single-segment stats — so the worker depends on Sandbox Execution, not just the graph; and (2) both the macro-segment write-back and the `Meta-Heuristic`/embedding write must be idempotent and crash-safe, since re-runs accumulate rather than replace.

Because Phase 1 can now produce `extract`-type outcomes with unverified, model-self-reported confidence, the search space must draw only on **verified** evidence — `query`-type findings (always verified) and HITL-confirmed `extract`-type findings — gated on `Outcome.verification_status`, never the confidence weight. It must also exclude its own prior-run **sleep-derived** macro-segments (they are search *outputs*, not atomic inputs) so higher-order conjunctions are never double-counted.

**Scope note on `extract` findings.** The eligibility gate is written to admit `confirmed`/`corrected` `extract` outcomes because that is the spec's stated rule (R9) and the gate must not have to change when extraction and the lattice search meet. But **no `extract` finding can reach the search in this shell**, and the plan does not try to make one: `extract` triplets are written only by `runDocumentLoop` (`internal/orchestrator/hypothesis.go:252-282`), which runs only when `goal.IsDocument()`, and Step 11 rejects document goals outright (they have no objective to pin, so there is nothing to optimize). Even on a hypothetical mixed goal, `writeExtractionTriplet` (`:441-455`) stores `Properties: {"field", "method"}` with no `new_filters` to contribute an atom, and keys `Outcome.Value` by field name rather than `obj.Label` so it yields no value comparable against `S*`. Making extract findings conjoinable would require a filter representation for extracted fields and is out of scope here. `SearchEligible` therefore stays forward-looking by design; treat its `confirmed`/`corrected` arms as currently unreachable rather than as a behavior to test end-to-end.

### Decisions settled at expansion

- **`SearchPolicy` seam, beam-only V1 (user-approved).** One policy-independent driver — `select → measure (sandbox, memoized) → record → expand` — with the strategy behind a narrow `SearchPolicy` interface (`Select`/`Update`/`Done`) declared at the driver per the consumer-defined-interface convention (`internal/orchestrator/server.go:37-90`). The V1 policy is the level-wise beam below; **no UCT code ships in V1** — V2 adds UCT as a second policy behind the same seam when the mixed graph exists. Rationale: across four review rounds of the prior UCT plan, the driver/write-back/abstraction steps were stable while nearly every finding landed inside the UCT internals (exploration constant, reward normalization, visit counts, selectability rule, reward floor, three interacting stopping rules) — that defect concentration is where the interface belongs, and all of that machinery existed to manage UCT's degenerate behavior on a lattice it exhausts anyway.
- **Search tuning (conservative).** Measurement budget 200 *distinct sandbox measurements* (a safety bound — the beam is finite by construction), beam width 10, maximum conjunction order 3, materially-better threshold 5% relative lift, minimum support 30 rows (absolute). All env-overridable via a new `SleepCycleConfig` (`SLEEPCYCLE_SEARCH_*` — the `_MCTS_` prefix is gone with the algorithm). Because candidates are Sandbox-measured, budget × order trades directly against sandbox query volume; 200 bounds a run at ~200 `/execute` calls.
- **Anti-monotone support pruning, measured in the same query (user-approved).** Conjoining predicates can only shrink the row set, so support is anti-monotone (the Apriori property): if a node falls below `MinSupport`, every superset provably falls below it too. Two mechanisms enforce this — prefix-only generation (a pruned node generates no children) **and** an explicit Apriori prune step on memo evidence (a candidate is dropped unmeasured if *any* of its (k−1)-subsets was measured below floor — not just its generating prefix; see Step 10). Both are required: generation alone only prunes supersets the below-floor node *prefixes*, while a superset like `{1,2,3}` reached via frequent prefix `{1,2}` still contains below-floor `{1,3}` and must be caught by the subset check. This also structurally kills the thin-support deep conjunctions that drive the uncorrected-multiple-testing risk, rather than correcting for them statistically. The support count comes back **in the same sandbox request as the objective** — an opt-in `IncludeRowCount` field on `ExecuteRequest` returning a reserved `row_count` key in the existing `map[string]any` `Value` (Step 3) — not a second round-trip. The floor also gates winners: a measured order-2 node below `MinSupport` cannot win regardless of its lift.
- **A failed measurement prunes (user-approved — deliberate reversal of the prior UCT plan).** A node whose `Execute` errors, times out, or returns a non-numeric value is recorded as a non-improving miss (audited, memoized, budget-consuming) and treated as below the support floor: never expanded, never a winner. Its supersets go unmeasured — accepted, and Apriori-consistent (unknown support ≡ insufficient support); expanding it would mean conjoining supersets of a filter that already failed once. The prior plan's completeness machinery (keeping failed nodes selectable as routes to children) is deleted with UCT, and its old `completeness_test.go` guard is *inverted*: the new test asserts the superset of a failed node is **not** measured.
- **Non-improving nodes stay in the frontier; only support prunes, delta only ranks (user-approved).** A predicate that underperforms the baseline alone may still form an improving conjunction — interaction effects are the entire reason the Sleep Cycle exists — so the beam ranks by directional delta but never excludes a node for being non-improving. Exclusion happens on exactly two grounds: support below floor (including failed measurements) and falling outside the top-`BeamWidth` at its level.
- **Termination is by construction, not by rule-set.** The beam enumerates finite candidate sets level-by-level (level k candidates ≤ `BeamWidth × atoms`; levels ≤ `MaxOrder`), so the loop is finite without any stopping-rule machinery. Exactly two bounds can end a run early or on time: the measurement budget (checked by the driver before each sandbox call; exhaustion mid-level stops the search immediately, winners drawn from what was measured) and the policy reporting `Done` (frontier empty, or level `MaxOrder` fully processed). Log which one ended the run. The prior plan's three stopping rules, `maxIterations` backstop, and failed-measurement visit-accounting exist only for a re-selecting policy and are deleted.
- **A winning macro-segment must have at least two atoms.** R9 defines the output as *conjunctions* that beat any single Phase-1 segment, so an order-1 node can never be a winner even though the search must traverse order-1 nodes to reach order-2. This is not hypothetical: `S*` is computed over eligible findings' measured values, so a predicate that only ever appeared as `new_filters` on a depth-≥2 Phase-1 node was never measured in isolation and its standalone value can exceed `S*` by more than `MinLift`. Without the guard, a single predicate would be persisted as a `sleep_derived` triplet and abstracted into a `Meta-Heuristic`.
- **Deterministic id scheme — structural, not rendered.** `domain.RenderConstraint` is a *display* renderer and must **not** key the id: it renders a bool `true` and the string `"True"` identically (`internal/domain/domain.go:255-271`), preserves membership-member slice order (`:313-319`), and leaves `Field` case-sensitive even though the sandbox compiler matches columns with `strings.EqualFold` (see `UnknownFilterColumns`, `:440-464`). The first defect fuses two structurally distinct macro-segments onto one node id; the latter two split one macro-segment across two ids on re-run, which is exactly the duplicate-accumulation R9 acceptance (d) forbids. The canonical key is instead a **structural encoding** of the normalized `[]domain.Constraint` (Step 6), and ids are UUIDv5 (`uuid.NewSHA1`) over a per-goal namespace plus a role-tagged canonical string — keeping the graph package's "application-assigned UUID id" convention intact while making the id a pure function of `(goal id, conjoined filter)`.
- **Naming sweep: `sleep_derived`, not `mcts_derived` (user-approved).** The derived-output discriminator names the *stage that produced it*, not the algorithm — the property is `sleep_derived` (domain field `SleepDerived`), and the spec's V1 prose drops "MCTS" everywhere in favor of "the Sleep-Cycle lattice search" (Step 1 enumerates the sweep). The V2 Roadmap keeps naming MCTS/UCT — that is where the algorithm now lives. Nothing is implemented yet, so the rename costs nothing now and prevents a misnomer being baked into the graph schema. Completed plan files (`arborette-07`, `arborette-11`) are historical records of shipped work and stay untouched.
- **Meta-Heuristic staleness sweep (user-approved extension beyond R9/R10's stated outputs), triggered by `rejected` only.** The spec's Open Questions record a known gap: a `Meta-Heuristic` already abstracted from a triplet whose `Outcome` is later corrected or rejected via HITL has no invalidation path. Rather than defer it entirely, each run begins with a sweep that flags any existing `Meta-Heuristic` whose `ABSTRACTED_FROM` components now resolve to a **`rejected`** `Outcome`. It **marks only** — `get_optimized_heuristics` filtering is deliberately *not* changed here, because that would alter R12 read-side behavior and belongs with the HITL and web work (`arborette-08-hitl-verification-backend`, `arborette-10-web-ui-hitl-confidence-agent-chat`).
  - **`corrected` deliberately does *not* trigger staleness**, even though it is one of the two statuses the spec's gap language names. R9 makes `corrected` outcomes *search-eligible* — an analyst who corrected a value affirmed it as evidence — and Step 13's `abstractedFrom` always includes the component Outcome ids. So a `corrected`-triggering sweep would flag every heuristic abstracted from a corrected component at the start of the very next run: the worker would systematically invalidate its own fresh, spec-sanctioned output, every time, not occasionally. `rejected` is the unambiguous invalidation signal and the only one used here. `domain.SearchEligibleStatuses` and the stale predicate are therefore deliberate complements, and their doc comments must each cite the other so a future edit cannot re-introduce the overlap.
  - Residual imprecision, accepted: with no abstraction timestamp the sweep cannot distinguish "rejected after abstraction" from "abstracted from an already-rejected outcome". The latter cannot occur through this worker (rejected outcomes are never search-eligible), so the imprecision is theoretical rather than routine.

### Plan risks

- **Two enabling refactors of existing code.** The sandbox client and the objective-pinning helpers are currently trapped in package `orchestrator` (the client exported, the helpers not), and the worker needs both. Steps 2 and 4 lift them into shared CGO-free packages behind type aliases so orchestrator behavior and its tests are unchanged. This is enabling work, not new responsibility: the alternative — duplicating `pinObjective`/`numericValue` in the worker — risks the objective label drifting between the two, which would silently break value lookup. The existing comment at `internal/orchestrator/sandboxclient.go:19-25` documents why `internal/sandbox` must not be imported (CGO), not that the client must live in `orchestrator`.
- **The `objective` refactor cannot use an alias shim.** Package `orchestrator` declares `type objective struct` in its package block (`internal/orchestrator/hypothesis.go:54`). Go forbids one identifier in both the file block (an import name) and the package block, so any file importing `internal/objective` while that type still exists fails to compile — and `hypothesis.go` is exactly the file that needs both. Step 4 therefore **deletes** the local type and rewrites call sites against `objective.Objective`, rather than delegating through a same-named local shim. This is the one place the two refactors differ: Step 2's sandbox client keeps alias shims (no name collision), Step 4's does not.
- **The row-count seam reopens shipped shell-03 sandbox code.** Step 3 touches `internal/sandbox` (`compile.go`, `filesource.go`, `server.go`) — a CGO service with exact-SQL and exact-scalar test assertions (`compile_test.go`, `filesource_test.go:205,254`). The change is deliberately **opt-in** (`IncludeRowCount`, mirroring how `ValueExpression`/`ObjectiveLabel` were added additively at `internal/sandbox/server.go:88-103`) so the legacy single-column path stays byte-identical and every existing sandbox test passes untouched; a changed existing sandbox assertion means the seam leaked into the default path.
- **Graph nodes are not goal-scoped today.** `writeTriplet` (`internal/orchestrator/hypothesis.go:353`) writes no `optimization_function_id`, and node `properties` are stored as an opaque JSON string (`internal/graph/neo4j.go:413` `marshalProps`) that the Neptune-portable Cypher subset cannot filter on. Step 5 promotes `goal_id` and `sleep_derived` to top-level node properties. **Findings written before this change carry no `goal_id` and are therefore invisible to the eligible-finding query** — pre-existing local data must be re-generated (re-run the Phase-1 loop) rather than migrated. Call this out in verification.
- **`CreateMetaHeuristic` is non-idempotent** (`CREATE`, not `MERGE`, at `internal/graph/neo4j.go:236`) under the `MetaHeuristic_id_unique` constraint. Step 5 converts it to `MERGE` with `ON CREATE`/`ON MATCH` so a re-run cannot resurrect an already-cleared `embedding_pending`. Its only current callers are tests.
- **Downstream compatibility (advisory).** The `arborette-08-hitl-verification-backend` and `arborette-10-web-ui-hitl-confidence-agent-chat` work consumes `Outcome.verification_status` and the `Meta-Heuristic` read path. This plan adds fields (`goal_id`, `sleep_derived`, `stale`) additively and leaves the `heuristics.Service.Query`/`Trace` signatures and the `UpdateOutcomeVerification` HITL resolution path untouched, so both keep a stable seam rather than needing a schema or API redesign. One decision is deliberately left to them: whether `get_optimized_heuristics` should filter `stale` heuristics.

### Convention Anchors

- **Service wiring**: `cmd/<svc>/main.go` calls `config.Load()`, builds infra clients from primitive args, `log.Fatalf("<svc>: <op>: %v", err)` on any startup failure, then blocks. `cmd/sleepcycle/main.go` already wires Neo4j (+`InitSchema`), a `ServiceDSN` pool, `ValidateEmbeddingDimension`, and an Ollama provider — but wires **no** Claude client, **no** sandbox client, **no** goal registry, and reads **no** job parameters.
- **Config**: all env, all in `internal/config/config.go`, one struct per service (`OrchestratorConfig:93`, `SandboxConfig:81`, …). There is **no `SleepCycleConfig`**; `SANDBOX_URL` lives on `OrchestratorConfig.SandboxURL` (`:204`), `SLEEPCYCLE_JOB_NAME` on `:206`, `ORCHESTRATOR_URL` on `MCPConfig` (`:211`, already in `.env.example:52`). Helpers `env`/`intEnv`/`int64Env`/`boolEnv` (`:221-253`) are strconv-parse-or-fallback; **there is no `floatEnv`** — `MinLift` needs one.
- **Strategy-seam placement**: two live conventions — consumer-defined narrow interfaces at the consumer, named for the collaborator (`internal/orchestrator/server.go:37-90`, concrete types injected from `cmd/`), and standalone behavior interfaces in their own package (`embedding.Provider`). `SearchPolicy` is consumed only by the sleep-cycle driver, so it is declared **in `internal/sleepcycle` next to the driver** (convention a), named for behavior — not for beam or MCTS — so the V2 UCT policy drops in without a rename.
- **Job parameters — does not exist**: `StubLauncher` (`joblauncher.go:19`) logs and returns nil; the compose `sleepcycle` service (`docker-compose.yml:166-179`) is a **long-running container with no `command:` and no per-run env**.
- **Postgres roles**: orchestrator = `OrchestratorDSN`; worker/MCP = `ServiceDSN` (embedding RW, **`SELECT ON goal_registry`** per `0005_grants.up.sql:19`). So the worker legitimately reads the goal directly via `store.NewGoalRegistry(pool).Get(...)`, and audits only over HTTP.

### Proposed Alignment

Follow the existing patterns closely, with three deliberate deviations. Model the search driver on `runLoop`/`processCandidate`'s terminal-vs-branch failure split and its detached terminal-write defer; model the write-back verbatim on `writeTriplet` but swap random UUIDs for deterministic ids (MERGE-on-id already makes that idempotent) and swap the parent baseline for the shared per-goal global baseline; use `ListEmbeddingPending` → `EmbedDocument` → `Upsert` → `ClearEmbeddingPending` as the crash-safe resume loop the tests already demonstrate; write audits through a new `/internal/audit` client shaped like `mcpserver.OrchestratorClient`, with long-name-as-`action` / short-name-as-`event_type`.

The three deviations: (1) the sandbox client and objective-pinning helpers are lifted out of package `orchestrator` into shared CGO-free packages rather than having `cmd/sleepcycle` import the whole orchestrator; (2) the goal-scoping and sleep-derived discriminators become **top-level Neo4j node properties**, not entries in the JSON-string `properties` blob, or the eligible-finding query cannot be expressed in the Neptune-portable Cypher subset the repository package mandates; (3) the beam's level-wise frontier is **new control flow with no codebase precedent** — the plan specifies it fully (Step 10) rather than pointing at `processCandidate`.

## Implementation Steps

> **Reading order.** Steps 1–9 are prerequisites, buildable in order. Steps 10, 12, and 13 define *components*; **Step 11 is the authoritative run order** that sequences them (sweep → resume → introspect → baseline → eligibility → search → write-back → abstraction). Where an earlier step names an input produced by a later one, Step 11 is where the wiring lives — build the components first, then assemble them per Step 11.
>
> **Closure invariant — every named value has a defined producer, and every failure has a defined disposition.** Multiple review rounds of the prior draft each surfaced the same class of defect: a step referring to a value or behavior that no step defines. Before implementing any step, check it against both halves of this invariant; if a step trips it, the plan is wrong and needs the producer or disposition written down, not an improvised local guess.
>
> - **Producer half.** Every input a step names must be produced by a named step, with its concrete type. Worked failures this prevents: the ontology leak guard's `columns` (no step introspected the schema — now Step 11); `new_filters` as `[]domain.Constraint` (the graph returns `[]any` of `map[string]any` — now `decodeConstraints`, Step 6); `abstractedFrom`'s component triplet ids (atom dedup discarded them — now the provenance-carrying atom index, Step 10); the support count (no response field carried it — now Step 3's `row_count` key).
> - **Disposition half.** Every failure and every loop must have a stated disposition — terminal, isolated-and-continue, or a named bound — and every accumulator must state what each outcome writes to it. Worked failures this prevents: budget exhaustion mid-level with no stated disposition (now: stop immediately, winners from measured set); introspection/baseline failures that Verification and the driver disagreed about; resume-pass failures belonging to neither the terminal nor the isolated category.
>
> Its scope is the whole plan, not the steps listed above — a new step added later is subject to it too.

10. **Implement the search: policy-independent driver, `SearchPolicy` seam, level-wise beam policy**
    - Create `internal/sleepcycle/search.go` (driver + seam) and `internal/sleepcycle/beam.go` (the V1 policy).
    - **Atom index (driver input).** Build it from the eligible findings the Step 11 driver passes in: for each, `decodeConstraints(triplet.Intervention.Properties["new_filters"])` (Step 6 — a plain type assertion does **not** work; see that step), then deduplicate the resulting predicates by their normalized structural encoding and sort, giving each atom a stable canonical rank.
    - **The atom index must retain provenance, not just the predicates.** Key it by canonical atom key → `{constraint, sourceTripletIDs}`, accumulating the `State`/`Intervention`/`Outcome` ids of **every** eligible finding that contributed that atom (deduplicated by id). Step 13's `abstractedFrom` needs exactly this to link a `Meta-Heuristic` back to its component single-feature triplets; if the search discards the source `CausalTriplet` after deduplication, that provenance is unrecoverable. Using all contributors rather than one representative gives a richer trace and is safe: every id came from the graph, so each resolves to exactly one node and cannot trip `CreateMetaHeuristic`'s validation (`internal/graph/neo4j.go:216-233`).
    - **The `SearchPolicy` seam.** Declared next to the driver, consumer-defined-interface style (`internal/orchestrator/server.go:37-90`), named for behavior so the V2 UCT policy drops in without a rename:
      ```go
      type Measurement struct { Value float64; Support int64; Failed bool }
      type SearchPolicy interface {
          Select() (node *Node, ok bool) // next unmeasured candidate; ok=false when none remain now
          Update(node *Node, m Measurement)
          Done() bool                    // no candidates remain at any level
      }
      ```
      `Node` carries the atom set (as canonical keys + `[]domain.Constraint`), its order, and its canonical filter string. The policy owns candidate generation and pruning; it never talks to the sandbox.
      **Seam contract (both sides, stated so `Done()` and `Select()` can never disagree):** the driver is strictly sequential — `Update` always completes before the next `Done()`/`Select()` call. The policy must advance levels **eagerly inside `Update`**: the `Update` call that records a level's last outstanding candidate computes the frontier and generates the next level's candidates (running the prune step) before returning, so by the time the driver next calls `Done()` the policy already knows whether anything remains. A policy that advances lazily inside `Select` would let `Done()` return false while the subsequent `Select` finds the next level empty. The driver defends against exactly that: it **breaks the loop when `Select` returns `ok=false`**, treating it as equivalent to `Done()` — never dereferencing a nil `Node`, never spinning.
    - **The driver loop** — policy-independent, mirroring `runLoop`'s failure discipline: while `measured < cfg.MaxMeasurements && !policy.Done()`: `Select` a node (**break on `ok=false`** — see the seam contract); compute its conjoined filters; **measure** via `sandboxclient.Client.Execute` with `objective.ExecuteRequestFor(goal.DataSourceRef, obj, conjoinedFilters)` plus `IncludeRowCount: true`; read the value via `objective.NumericValue(resp.Value, obj.Label)` and the support via `sandboxclient.RowCount(resp)`; hand the `Measurement` to `Update`. Memoize by canonical filter string — the budget counts **distinct sandbox measurements**, and a policy that re-selects a measured key costs nothing (an invariant guard, cheap even though the beam never re-selects by construction). The driver records every measured node (value, support, order, provenance) in a run-local table the winner gate reads.
    - **A failed measurement** (`Execute` error/timeout, or a non-numeric value) is memoized, consumes budget, and is handed to `Update` as `Measurement{Failed: true}` — the policy treats it as below the support floor (per the Decisions section: prune-on-error). It is reported via `auditclient.Append("sleepcycle_measurement_failure", "failure", {...})` including the canonical filter and the error text, and **never aborts the run** — mirror `branchFailure` (`internal/orchestrator/hypothesis.go:518`): log, audit, continue.
    - **Termination.** Exactly two ways a run ends, both logged with which one fired: (a) the policy is `Done` — every level up to `MaxOrder` has been processed or the frontier emptied (the common case; the whole reachable lattice is measured); (b) the measurement budget is exhausted — the driver stops immediately, mid-level, and the winner gate runs over what was measured. No `maxIterations` backstop: the beam generates each candidate exactly once, so driver iterations are bounded by candidate count plus one final `Done` check.
    - **The beam policy** (`beam.go`), level-wise over the subset lattice:
      - **Level 1**: every atom is a candidate. **Level k (2 ≤ k ≤ MaxOrder)**: candidates are `F ∪ {a}` for each frontier node `F` of level k−1 and each atom `a` whose canonical rank exceeds the maximum rank in `F` — the rank-ordered construction means every subset is generated at most once (its only generator is its prefix without its top-ranked atom), the subset lattice not the permutation tree.
      - **Apriori prune step (memo evidence), before a candidate reaches the driver**: drop the candidate unmeasured if **any** of its (k−1)-subsets — not just its generating prefix — is in the memo with `Support < MinSupport` or `Failed`. This is what makes the anti-monotone guarantee hold for non-prefix subsets: `{1,2,3}` generated from frequent prefix `{1,2}` is still dropped when `{1,3}` was measured below floor. Only **measured** evidence prunes — an unmeasured (k−1)-subset (never generated, or discarded by width ranking) says nothing about support and must not prune, or width-pruning would silently masquerade as support-pruning. Cost: ≤ `MaxOrder` memo lookups per candidate, no sandbox calls.
      - **Frontier selection**: after a level's candidates are all measured, the frontier is the top-`cfg.BeamWidth` **surviving** nodes ranked by directional delta `d = value − baseline` (negated when `direction == domain.Minimize`), ties broken deterministically by canonical filter string so runs are reproducible. Surviving = measured successfully **and** `Support >= cfg.MinSupport`. A node outside the top-width is discarded; a below-floor or failed node is discarded *provably* (anti-monotone: every superset's support is ≤ its own; a failed node's support is unknown, treated as insufficient — see Decisions).
      - **Non-improving nodes are not pruned** — a negative delta only ranks; if it is within the top-width it stays, because its conjunctions may improve (interaction effects are the point of this search). Only support (and width) prune.
      - **Degeneration to full enumeration**: when a level has ≤ `BeamWidth` survivors, the beam keeps them all — with V1's small lattices the search is usually exhaustive, and the width only binds on unusually wide Phase-1 harvests.
      - `Done()` is true when the current level produced no candidates (empty frontier or rank exhaustion) or level `MaxOrder` has been processed. No visit counts, no exploration constant, no reward normalization, no reward floor — none of that machinery exists in this design.
    - **Winner collection (driver, not policy).** From the run-local measured table: every node with `order >= 2`, successful measurement, and `Support >= cfg.MinSupport` is a winner *candidate*; Step 11's materially-better gate (`MinLift` vs `S*`) makes the final cut. Order-1 nodes are traversed (they are the only route to order-2) but can never be surfaced as macro-segments — R9 defines the output as conjunctions. Apply the `order >= 2` constraint here, in the search's collection, not only in Step 11's gate, so an order-1 node never reaches write-back.

[]winner` — it returns the winners whose triplet was fully written**, and that returned slice, not the search's original winner list, is what Step 13 iterates. Naming this return value is what makes the failure isolation below actually enforceable.

Writing it per segment is what brings it under the per-segment failure isolation below — and that matters more than it looks: `CreatePreConditionFor` is `MATCH (s:State {id}) MATCH (i:Intervention {id}) MERGE …` (`internal/graph/neo4j.go:175-183`) and **a zero-row MATCH is not an error in Cypher**, so `writeOp` (`:50-56`) returns nil. - **Edge cases to spot-check:** a goal with zero eligible findings (degenerate, exits 0); a document goal (rejected with a clear terminal error, not a panic); a sandbox down *before* the baseline (clean **terminal** error and non-zero exit — not degenerate detection; the baseline is a hard prerequisite per Step 11); a sandbox that starts failing *after* a successful baseline (level 1 all fails → empty frontier → degenerate detection, exit 0); an atom count small enough that the lattice is narrower than the beam at every level (full enumeration, terminates by policy-`Done`); an objective whose baseline measures 0 (the `MinLift` epsilon guard must not divide by zero); `MaxOrder = 1` (no conjunction formable → degenerate); a conjunction whose filtered set is empty (NULL objective, count 0 → pruned as below-floor, not crashed).
- **Concurrency caveat (documented, not defended against):** two Sleep-Cycle runs for the same goal executing at once will duplicate sandbox work and race on the same deterministic node ids. Because every write is a MERGE on a deterministic id and every written value is a function of the filter, the races converge rather than corrupt — but the runs waste effort. The trigger endpoint does not serialize runs today; note it and leave locking to the production job launcher (AWS Batch job-level concurrency control).
