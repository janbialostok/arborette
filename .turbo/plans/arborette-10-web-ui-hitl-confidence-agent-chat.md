# Plan: Web UI — HITL, Confidence & Agent Chat

## Context

This plan covers the analyst-facing surface for all three new backend features at once, since they share the same React/Next.js conventions established by the existing `web/` app and are worth building together rather than in three separate sessions: a HITL verification interface (with source-excerpt rendering), a live confidence-bin histogram, and an agent preview tab built on arborette's default iMessage-style chat styling. The chat component itself is a reusable piece — the same default styling every arborette-produced agent uses, not something rebuilt per analyst.

The backend contracts already exist in `internal/orchestrator`: the verification queue/resolution/excerpt endpoints and confidence histogram (`verification.go`), the streamed chat endpoint (`chat.go`), and the shared run SSE stream (`stream.go`). The work here is UI, thin BFF proxy routes, and typed client functions — no new architecture.

## Pattern Survey

### Analogous Features

- `web/components/LiveRun.tsx:221-262` — The canonical SSE-consuming client component: `fetch(streamUrl(id))` → `consumeStream(res.body, handleEvent, signal)`, with a `switch (ev.type)` over the discriminated `OrchestratorEvent` union, an `AbortController` cleanup, idle/reconnect timers, and localStorage-backed run lifecycle. Direct template for the confidence-bin histogram (it rides the **same** `/goals/{id}/stream` endpoint) and for the chat streaming UI.
- `web/components/HeuristicBrowser.tsx:22-88` — Two-pane "list + selected detail" master/detail layout (`ResultList` + keyed `TracePanel` that remounts per selection and fetches in a `useEffect`). Closest analog to the HITL queue-list/browse + detail-view feature.
- `web/components/ObjectivesList.tsx:20-36` — The standard one-shot fetch-on-mount pattern (`useEffect` + `cancelled` guard + loading/error/empty states via `Panel`/`Spinner`/`Callout`). Template for the HITL queue list load.
- `web/components/GoalForm.tsx:24-64` — The form/action pattern: local state, client-side validation to pre-empt backend 400s, `try/catch` calling a typed client fn, `errorMessage(err, fallback)` for surface-vs-mask, then `router.push`. Template for the confirm/correct/reject resolution actions.
- `web/components/EffectReadout.tsx:30-91` — A presentational (non-`"use client"`) bar/readout card driven purely by props, normalized against a `scale`, with `animate-bar`/`animate-rise` and tabular numerics. Direct precedent for rendering histogram bars.
- `internal/orchestrator/verification.go:100-277` — The backend HITL handlers the UI consumes: `handleListVerifications` (returns `verificationListDTO{effective_threshold, epoch_mode, entries[]}`), `handleListOutcomes`, `handleOutcomeExcerpt` (returns `excerptDTO`), and `handleResolveVerification` (POST body `{action, corrected_value}`; `action` ∈ confirm/correct/reject; 200 returns `{outcome_id, resolution, verification_status, confidence}`, 409 on already-resolved, 422 on bad action / missing corrected_value).
- `internal/orchestrator/verification.go:597-732` — `confidenceHistogram` and `distributionEvent`: the histogram frame the UI must render. Wire shape is `{"type":"confidence_distribution", "payload":{"bins":[10 ints], "total":n}}` — the hub's `Event` struct (`internal/orchestrator/hub.go`) marshals its payload under a top-level `payload` key, the same envelope the existing `triplet` frame uses — published through the run stream (hub keyed by goalID). **10 equal-width bins** (`confidenceBinCount = 10`).
- `internal/orchestrator/chat.go:66-176` — `handleChat`: **POST** `/goals/{id}/chat` with body `{messages:[{role,content}]}`, streams SSE frames of `{type,text?,tool?,is_error?,message?}` where type ∈ `chat_text`/`chat_tool_use`/`chat_tool_result`/`chat_done`/`chat_error`. Note the lazy-200: it may return a JSON error (400/503/502) before the first frame, then only in-band `chat_error` frames after streaming starts. Transcript must start and end on a `user` turn (else 400).

### Reusable Utilities

- `web/lib/sse.ts:8` — `consumeStream(body, onEvent, signal?)` — parses `data: <json>\n\n` frames (no `event:` lines), discriminating on top-level `type`. Reusable as-is for the histogram (same stream, same `OrchestratorEvent` union). For chat, its callback is hard-typed `(ev: OrchestratorEvent) => void`, so reuse requires generalizing the signature to `consumeStream<T = OrchestratorEvent>(body, onEvent: (ev: T) => void, signal?)` — a type-only change, no runtime behavior difference, existing callers unchanged by the default type parameter. Swallows malformed frames; resolves on stream end.
- `web/lib/orchestrator.ts:111` — `requestJSON<T>(input, init)` — the private same-origin BFF fetch helper wrapping error surfacing; every typed client fn (`submitGoal`, `listGoals`, `triggerHypothesisLoop`, etc.) is a thin wrapper. New verification/outcome/excerpt/chat client fns belong here following this shape.
- `web/lib/orchestrator.ts:79-107` — `OrchestratorError`, `errorFrom`, `errorMessage(err, fallback)` — the surface-vs-mask policy; reuse verbatim for all new call sites.
- `web/lib/orchestrator.ts:14-17` — `OrchestratorEvent` union — **must be extended**: it currently has only `triplet`/`branch_failure`/`loop_complete` and no `confidence_distribution` member, so the histogram frame is presently parsed-and-ignored by `LiveRun`'s switch. Adding the member is the seam for the histogram feature.
- `web/lib/orchestrator.ts:159` — `streamUrl(id)` — builds `/api/orchestrator/goals/{id}/stream`; the histogram consumes this same URL, so the histogram shares `LiveRun`'s existing single connection rather than opening a second one.
- `web/lib/proxy.ts:53-113` — `forward` / `forwardSubmit` / `forwardStream` — the BFF proxy primitives. `forwardStream` is **GET-only** (no body) and applies the no-timeout `streamDispatcher` + SSE response headers. `forward` streams a request body through (`duplex:"half"`) but uses default undici timeouts and does **not** set SSE headers. **Gap:** neither fits POST-streaming chat (needs body + the no-timeout dispatcher + SSE headers) — the chat route needs a new proxy helper.
- `web/lib/runState.ts:21-55` — `getRunRecord` / `markTriggered` / `markCompleted` — localStorage per-goal lifecycle; the established pattern for client-persisted per-goal state if the preview tab or HITL view needs it (not required).
- `web/components/ui.tsx` — Primitives: `cn`, `SectionLabel`, `Button` (variants primary/ghost/subtle, `loading`), `Spinner`, `Callout` (error/warn/info), `Badge` (positive/neutral/warn/negative), `Panel`. All new UI composes these; `Badge`/`Callout`/`Button` cover the HITL verdict actions and status pills.
- `internal/orchestrator/verification.go:557` — `excerptFor(pages, locator)` — the backend already renders the excerpt-vs-full-page-fallback decision into `excerptDTO{fallback, page, char_start, char_end, excerpt, page_text, pages[]}`; the UI just branches on `fallback`. No client-side locator math needed.

### Convention Anchors

- Client vs presentational split: interactive/stateful components are `"use client"` with hooks (`LiveRun`, `HeuristicBrowser`, `GoalForm`, `ObjectivesList`); pure readouts omit it (`EffectReadout`). Page files under `web/app/**/page.tsx` are thin server components delegating to one client component (`goals/[id]/page.tsx` → `<LiveRun id={id}/>`). New HITL/chat surfaces follow this: a `page.tsx` shell + a client component in `web/components/`.
- BFF proxy routing: every browser call goes to same-origin `/api/orchestrator/*`; each `web/app/api/orchestrator/**/route.ts` is a ~10-line handler exporting `runtime="nodejs"`, `dynamic="force-dynamic"`, `await params`, and delegating to a `proxy.ts` helper with `encodeURIComponent(id)`. New routes needed (none exist yet): `.../verifications`, `.../verifications/[outcomeID]`, `.../outcomes`, `.../outcomes/[outcomeID]/excerpt`, `.../chat`. The client `orchestrator.ts` never sees `ORCHESTRATOR_URL`.
- SSE wire contract: frames are `data: <json>\n\n` with **no `event:` line**; consumers discriminate on the JSON top-level `type` (enforced server-side by `writeSSEFrame` at `internal/orchestrator/stream.go:83` and client-side by `consumeStream`). Any new streamed feature uses this framing, not `EventSource`/`event:`-typed frames.
- DTO discipline: store/graph types carry no json tags, so handlers define snake_case `*DTO` structs (`internal/orchestrator/verification.go:42-96`). The UI's TS interfaces mirror these snake_case shapes exactly (see `GoalListItem`, `TripletPayload`).
- Error policy: orchestrator `{error}` bodies are analyst-safe and surfaced verbatim; transport/parse failures are masked to a generic fallback — enforced identically in Go, `proxy.ts`, and `orchestrator.ts`/`errorMessage`. Client-side validation pre-empts known backend 4xx (GoalForm exactly-one-source, HeuristicBrowser empty-q).
- Styling: Tailwind v4 CSS-first (`@theme` tokens in `web/app/globals.css`, no `tailwind.config`), instrument-panel dark palette (`signal` green accent, `neg`/`warn` semantic), fonts via `next/font` CSS vars, `.tabular` for streaming numerics, keyframe utilities (`animate-rise`/`animate-bar`/`pulse-live`) gated on `prefers-reduced-motion`. No component library.
- Navigation: `web/components/AppNav.tsx:7-11` — nav is a static `LINKS` array with `usePathname`-based active state. The "Preview agent" tab is scoped to the current goal, so it belongs as an in-page tab on `goals/[id]` (which currently renders only `LiveRun`) rather than a global nav link — the goal page grows a tab switcher.
- Testing: **Vitest** (`vitest run`), tests colocated as `web/lib/*.test.ts`. API/client tested via `vi.stubGlobal("fetch", ...)` returning real `Response` objects (`orchestrator.test.ts`); SSE tested by hand-built `ReadableStream` chunked to force frame/chunk-boundary splits (`sse.test.ts`). No component-render tests exist — the testing convention is at the lib/client layer.

### Proposed Alignment

This feature set is almost entirely a recombination of what `LiveRun` (SSE consumption), `HeuristicBrowser` (master/detail), `GoalForm` (form actions), and the `orchestrator.ts`/`proxy.ts`/`ui.tsx` layers already establish; the backend HITL/chat/histogram handlers already exist and expose stable snake_case DTO contracts, so the work is UI + thin BFF routes + typed client fns. Three deliberate deviations are warranted: (1) extend the `OrchestratorEvent` union with a `confidence_distribution` member so the histogram frame (already published on the shared `/stream`) stops being silently ignored, sourcing the histogram from `LiveRun`'s existing single stream connection rather than a second subscription; (2) add a POST-streaming proxy helper for chat, since neither `forwardStream` (GET-only) nor `forward` (default timeouts, no SSE headers) fits a POST body + quiet-SSE + lazy-200 endpoint; and (3) generalize `consumeStream` to a default type parameter (`consumeStream<T = OrchestratorEvent>`) so the chat consumer types its handler against the separate `ChatFrame` union without casts or polluting the run-stream union. Everything else mirrors the established conventions verbatim.

## Implementation Steps

1. **BFF proxy routes and typed client functions**
   - Add `forwardStreamSubmit(req, path)` (name to taste) to `web/lib/proxy.ts`: POST with streamed request body (`duplex: "half"` like `forward`), the no-timeout `streamDispatcher` + SSE response headers like `forwardStream`, and the same error-masking policy. Preserve non-200 JSON error passthrough so the chat endpoint's pre-stream 400/502/503 bodies surface via `errorFrom`.
   - Add BFF routes under `web/app/api/orchestrator/goals/[id]/`, each following the existing ~10-line `route.ts` convention (`runtime = "nodejs"`, `dynamic = "force-dynamic"`, `await params`, `encodeURIComponent`):
     - `verifications/route.ts` — GET → `forward`
     - `verifications/[outcomeID]/route.ts` — POST → `forwardSubmit`
     - `outcomes/route.ts` — GET → `forward` (pass query string through)
     - `outcomes/[outcomeID]/excerpt/route.ts` — GET → `forward`
     - `chat/route.ts` — POST → the new streaming-submit helper
   - Extend `web/lib/orchestrator.ts`:
     - TS interfaces mirroring the backend DTOs snake_case-exact: `VerificationList` (`effective_threshold`, `epoch_mode`, `entries[]`), `VerificationEntry`, `ExtractionOutcome` (`outcome_id`, `field`, `method`, `value` — a `Record<string, unknown>` keyed by field, not a flat string — `provenance`, `verification_status`, `confidence`; the shape `GET /goals/{id}/outcomes` returns, structurally different from `VerificationEntry`), `OutcomeExcerpt` (`fallback`, `page`, `char_start`, `char_end`, `excerpt`, `page_text`, `pages[]`), `ResolveResult` (`outcome_id`, `resolution`, `verification_status`, `confidence`), and a separate `ChatFrame` union (`chat_text`/`chat_tool_use`/`chat_tool_result`/`chat_done`/`chat_error`) — kept out of `OrchestratorEvent` (chat frames never arrive on the run stream); `consumeStream` is generalized to `consumeStream<T = OrchestratorEvent>` so the chat consumer passes a `(ev: ChatFrame) => void` handler without a cast (see the sse.ts note in Reusable Utilities). Note `chat_tool_result` carries only `is_error` — no tool name on the wire.
     - Client fns via `requestJSON`: `listVerifications(id)`, `listOutcomes(id)`, `getOutcomeExcerpt(id, outcomeID)`, `resolveVerification(id, outcomeID, action, correctedValue?)`.
     - `chatUrl(id)` alongside `streamUrl(id)`; chat POSTs with `fetch` + `consumeStream` from the component (mirroring how `LiveRun` consumes `streamUrl`), surfacing pre-stream JSON errors through `errorFrom` — export `errorFrom` (currently module-private at `orchestrator.ts:88`) so the component can call it.
     - Extend the `OrchestratorEvent` union with `{type: "confidence_distribution", payload: {bins: number[]; total: number}}` (the `payload` envelope matches the existing `triplet`/`branch_failure` members and the hub's wire format).

2. **HITL verification interface**
   - New client component `web/components/VerificationQueue.tsx` modeled on `HeuristicBrowser`'s master/detail split: left pane lists queue entries from `listVerifications` (confidence, extracted value, status via `Badge`; show `effective_threshold`/`epoch_mode` as a `SectionLabel` header), right pane is a keyed detail panel that remounts per selection.
   - Detail panel fetches `getOutcomeExcerpt` on mount (`ObjectivesList`-style `useEffect` + `cancelled` guard). Render the extracted value prominently, then branch on `excerptDTO.fallback`: when `false`, highlighted excerpt in page context (`excerpt` emphasized within `page_text` using `char_start`/`char_end`); when `true`, render the whole-document `pages[]` array (in the fallback shape `page_text` and `excerpt` are empty and only `pages[]` is populated — per `excerptFor` in `internal/orchestrator/verification.go`).
   - Confirm/correct/reject actions following `GoalForm`'s form pattern: `Button` row; "correct" reveals a corrected-value input (client-side require non-empty before submitting, pre-empting the 422); `try/catch` around `resolveVerification` with `errorMessage` fallback; on 409 (already resolved elsewhere) surface the backend message and refresh the entry. On success, update the entry's status in place and advance selection to the next queued item.
   - On-demand selection beyond the queue: a toggle sourcing the list from `listOutcomes` so an analyst can inspect and resolve outcomes that were auto-verified. This is **not** a drop-in source swap — `ExtractionOutcome` and `VerificationEntry` are structurally different DTOs. Define one internal list-item model the component renders (e.g. `{outcome_id, field, display_value, confidence, status}`) with a normalizer per source: queue entries map `extracted_value` → `display_value` and queue `status` → `status`; outcomes map `value[field]` (stringified) → `display_value` and `verification_status` → `status`. Detail-panel actions key off `outcome_id` in both modes (`getOutcomeExcerpt` and `resolveVerification` both take the outcome ID, so the shared detail view works unchanged).

3. **Confidence-bin histogram**
   - New presentational component `web/components/ConfidenceHistogram.tsx` (no `"use client"`, props-driven like `EffectReadout`): renders the 10 bins as bars normalized to the max bin count, x-axis labeled 0.0–1.0, `total` count readout, `animate-bar` + `.tabular` numerics per house style.
   - Wire into `web/components/LiveRun.tsx`: add a `confidence_distribution` case to the existing `switch (ev.type)` storing `ev.payload` (`{bins, total}`) in state (last-write-wins — each frame is a full snapshot, not a delta), and render `ConfidenceHistogram` alongside the existing progress view. No second SSE connection. Clear the histogram state in `runPhase1`'s existing reset block (alongside `setItems([])` etc.) so a re-run starts from an empty distribution instead of showing the prior run's bins until the new run's first frame arrives.

4. **Default agent chat component**
   - New client component `web/components/AgentChat.tsx` — the shared, reusable iMessage-style chat UI and arborette's standard agent styling (documented as such in a header comment): bubbled messages (user right-aligned/accent, agent left-aligned/neutral), minimal chrome, auto-scroll to newest, `textarea` + send button, `Spinner` while streaming.
   - Props: `goalId` (or a pluggable endpoint URL) so the component is reusable by any arborette-produced agent surface, not hardwired to the preview tab.
   - Transcript state as `{role, content}[]`; on send, append the user turn and POST the full transcript to `chatUrl(goalId)` (the endpoint requires the transcript to start and end on a `user` turn, and rejects empty-content messages — maintain both invariants client-side). Consume the response with `consumeStream<ChatFrame>`: accumulate `chat_text` into an in-progress agent bubble held *outside* the transcript state, render `chat_tool_use`/`chat_tool_result` as compact inline activity rows (the tool name comes only from `chat_tool_use` — `chat_tool_result` carries just `is_error`, so pair each result row with the preceding `chat_tool_use` in component state), and surface `chat_error` frames as a `Callout` (in-band errors after the lazy-200). **Transcript commit rule:** append the assistant turn to the transcript only on `chat_done` with non-empty accumulated text; on `chat_error` (or a stream that ends without `chat_done`) discard the in-progress bubble from transcript state — an empty or dangling assistant turn would make the next POST fail the backend's transcript validation with a 400. **Abrupt-end rule:** a stream that ends without `chat_done` — whether `consumeStream` resolves quietly (upstream body closed; `consumeStream` returns on `done` with no error) or rejects with a read error — surfaces an error `Callout` (generic fallback message) in addition to discarding the bubble; only in-band `chat_error` frames carry a backend-authored message. Handle pre-stream JSON errors (400/502/503) before attempting stream consumption via `errorFrom` — note `errorFrom` is currently module-private in `web/lib/orchestrator.ts` (line 88, unexported), so Step 1's orchestrator.ts changes must export it (existing internal call sites unchanged).
   - Disable the composer while a response is streaming (the backend combines consecutive same-role turns rather than rejecting them, but one in-flight exchange at a time keeps the transcript invariant trivially true).

5. **Goal-page tabs and the preview-agent tab**
   - Grow `web/app/goals/[id]/page.tsx` into a tabbed surface (thin server component delegating to a client tab-switcher component): **Run** (existing `LiveRun`, now including the histogram), **Verify** (`VerificationQueue`), **Preview agent** (`AgentChat` scoped to the goal). Tab state via URL (`?tab=` or segment) so tabs are linkable; follow `AppNav`'s active-state styling for the tab row.
   - Keep `LiveRun` mounted (or its stream state lifted/preserved) when switching tabs so the SSE connection and accumulated run state survive tab changes; simplest is render-all-tabs with `hidden` toggling, matching the single-connection decision in Step 3.

6. **Tests**
   - `web/lib/orchestrator.test.ts`: extend with the new client fns — stubbed `fetch` returning real `Response` objects; cover the resolve 409/422 error surfacing and the snake_case DTO parsing (including `excerptDTO.fallback` both ways).
   - `web/lib/sse.test.ts` style coverage for chat frame parsing: hand-built `ReadableStream` chunked across frame boundaries emitting `chat_text`/`chat_tool_use`/`chat_done`/`chat_error` sequences.
   - `web/lib/proxy.test.ts` (new, if proxy helpers are unit-testable in the existing style): the POST-streaming helper forwards body + returns SSE headers, and passes through non-200 JSON error bodies.

## Verification

- `cd web && npx vitest run` — all existing and new lib tests pass.
- `cd web && npm run build` — Next.js production build succeeds (catches route-typing and server/client-component violations).
- `go test ./internal/orchestrator/...` — untouched backend still green (guards against accidental contract drift while reading handlers).
- Manual smoke against the local stack (`make up`; orchestrator :8080, web :8083):
  1. Submit a goal with a document source, trigger the hypothesis loop, open `goals/{id}`: the **Run** tab shows the confidence histogram updating live as outcomes extract (bins shift as `confidence_distribution` frames arrive).
  2. **Verify** tab: queue lists sub-threshold outcomes; selecting one renders the extracted value against its highlighted excerpt; an outcome without a locator renders the whole-document fallback (`pages[]`); confirm/correct/reject each round-trip (correct requires a value; a second resolve of the same outcome surfaces the 409 message), and a resolution visibly re-bins the histogram on the Run tab.
  3. **Preview agent** tab: sending a message streams an iMessage-style reply; tool activity rows appear for `chat_tool_use`/`chat_tool_result`; killing the orchestrator mid-chat surfaces an error `Callout` rather than dead air. (Requires `ANTHROPIC_API_KEY` and a publicly reachable MCP URL for real replies — without them, verify the 503/502 pre-stream error path surfaces cleanly instead.)
- Edge cases to spot-check: empty verification queue (empty-state, not spinner forever); `total: 0` histogram (renders axes without division-by-zero NaN bars); chat transcript after `chat_error` (composer re-enabled, transcript still ends on a valid turn for resubmission).
