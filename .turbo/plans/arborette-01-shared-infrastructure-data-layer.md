# Plan: Shared Infrastructure & Data Layer

## Context

Four independently-deployable Go services (Orchestrator, Sandbox Execution, Sleep-Cycle Worker, MCP Server) all depend on the same underlying data layer: a Neo4j graph, a PostgreSQL instance (goal registry, audit trail, `pgvector` embeddings), an object store for file-based data sources, and an embedding provider. Building this once, as a shared foundation, means every consuming service surveys against a settled interface instead of each re-deriving its own graph/storage access pattern. This shell has no user-facing behavior of its own — its job is to make the rest of the system buildable.

## Pattern Survey

### Analogous Features

None found in code — this is a greenfield repository. There is no `go.mod`, `go.work`, `docker-compose.yml`, SQL migration, or `.go` file anywhere in the tree. The only files present are `.turbo/specs/arborette.md`, `.turbo/shells/*.md`, `context/CONCEPT.md`, and `.claude/` settings. The spec is the sole prior art; its architecture section pre-describes the four services and their shared data-layer touchpoints (`.turbo/specs/arborette.md` §Architecture, lines 108–139).

### Reusable Utilities

None found in code — no shared packages, helpers, interfaces, or base types exist yet. This shell *creates* the reusable utilities (`EmbeddingProvider`, `DataSource`, the Neo4j repository interface, the object-store client, the heuristics-query package) that all downstream shells consume (Orchestrator, Sandbox Execution, Sleep-Cycle Worker, MCP Server, multi-modal extraction, agent-chat backend).

### Convention Anchors

Since there is no code, these are drawn verbatim from the spec/concept docs and are the authoritative conventions the plan aligns to.

- **Language & mandated SDKs** (`.turbo/specs/arborette.md` §Tech Stack, lines 122–139): Go across all backend services. Anthropic Claude via `github.com/anthropics/anthropic-sdk-go` (not used by this shell, but the shared layer must not preclude it). MCP via `github.com/modelcontextprotocol/go-sdk` (consumed by the MCP Server shell; the heuristics-query package must be callable from an MCP tool handler). Neo4j (Cypher) chosen over Neptune for local-Docker parity, Neptune the deferred long-term target — the reason **all** graph access goes through a *single repository interface* (line 130). Postgres + `pgvector`, embeddings keyed by Neo4j node ID (lines 133, 149). Object store: S3 in prod, MinIO local, S3-API-compatible so the *same client code* runs unchanged (line 132). Embeddings default: local Ollama sidecar over HTTP serving `nomic-embed-text`, behind a pluggable `EmbeddingProvider`, swappable to a cloud provider — an explicit non-live swap because different providers yield different-dimension, non-comparable vectors (line 133).
- **Credential-ownership boundary** (lines 59, 135, 160): only the Orchestrator holds credentials to the audit table; all other services write audit records through the Orchestrator's internal audit-write API. This shell builds the audit *table + insert-only access code*; it does not grant other services direct table credentials.
- **Neo4j/`pgvector` write-ordering / `embedding_pending` invariant** (lines 156, 114): creating a `Meta-Heuristic` writes both stores. Neo4j is source of truth. The node, its `ABSTRACTED_FROM` edges, and `embedding_pending: true` are written **together in one Neo4j write**; `embedding_pending` clears to `false` only after the `pgvector` write succeeds; a node still flagged `true` is retried, never treated as done. The repository interface must expose this flag and the single-write-with-flag semantics.
- **Heuristics-query encapsulation** (spec line 53): the package takes a **raw operational-state string**, embeds it internally via `EmbeddingProvider`, runs the `pgvector` similarity search, and does `ABSTRACTED_FROM` traversal. Callers (Orchestrator REST handlers, MCP tool handlers) pass a string in and get matches out — they never call `EmbeddingProvider` directly for this path.
- **Data-model specifics** (`.turbo/specs/arborette.md` §Data Model, lines 141–162): Nodes `State`, `Intervention`, `Outcome`, `Meta-Heuristic`. `Outcome.verification_status` (`verified` | `unverified` | `confirmed` | `corrected` | `rejected`) — this field, not the confidence weight, gates Sleep Cycle clustering; `extract` outcomes also carry a nullable provenance locator (page + char span). `Meta-Heuristic` carries `embedding_pending` and an embedding stored in pgvector keyed by node ID. Edges: `PRE_CONDITION_FOR` (State→Intervention); `PRODUCED` (Intervention→Outcome) carrying effect size + confidence weight 0.0–1.0; `ABSTRACTED_FROM` (Meta-Heuristic→Intervention/State/Outcome).
- **MCP tool schemas** (`context/CONCEPT.md`; spec lines 51–54) the shared layer must be able to answer: `get_optimized_heuristics` (state string → semantic matches via embedding similarity), `trace_causal_chain` (`heuristic_id` → linearized Start/Intervention/Outcome via `ABSTRACTED_FROM` walk).
- **DataSource pluggability** (spec lines 26, 72; R3, partial): `DataSource` is a pluggable Go interface; the file-based implementation ships later (Shell 03), a document/PDF implementation later still (Shell 07) *without changing the interface contract*. This shell defines only the interface contract.

### Proposed Alignment

No in-repo prior art exists, so alignment means fidelity to the spec's mandated tech stack and data model. Follow the spec's explicit technology choices exactly, and encode three details as hard invariants from day one: the `embedding_pending` single-Neo4j-write-then-clear ordering, the `verification_status`-not-confidence clustering gate, and the string-in/matches-out encapsulation of the heuristics-query package.

**Resolved decisions (from expansion escalation):**

- **Go libraries** (the spec names technologies, not libraries): Neo4j → `github.com/neo4j/neo4j-go-driver/v5`; Postgres → `github.com/jackc/pgx/v5` with `github.com/pgvector/pgvector-go` for vector binding; migrations → `github.com/golang-migrate/migrate/v4`; object store → `github.com/aws/aws-sdk-go-v2` (S3 client with a custom endpoint + path-style addressing for MinIO); Ollama → stdlib `net/http` against the sidecar's HTTP API. These are baked into every downstream service.
- **Neptune portability posture** (the deferred Neo4j→Neptune migration, resolved at expansion): invest in portability now. The graph layer uses a deliberately Neptune-portable openCypher subset — no APOC, no Neo4j-only `db.*`/`apoc.*` procedures — and every node carries an **application-assigned UUID `id` property** (never the driver's internal element id) that is both the `pgvector` key and the graph lookup key. This makes a future Neptune swap a new implementation of the same interface rather than a rewrite. No migration work happens in this shell.

## Implementation Steps

1. **Go module & docker-compose scaffolding**
   - Single Go module `github.com/arborette/arborette` at the repo root (`go.mod`), with four service entrypoints under `cmd/` — `cmd/orchestrator/main.go`, `cmd/sandbox/main.go`, `cmd/sleepcycle/main.go`, `cmd/mcpserver/main.go` — and shared code under `internal/`. Each `cmd/<service>` gets its own `Dockerfile` (multi-stage, targeting that one binary) so the services remain independently deployable images despite sharing one module. At this shell each `main` is a stub that wires config + connections and then **blocks on `SIGINT`/`SIGTERM`** (so the container stays up in compose) rather than exiting — real behavior lands in shells 02–05. (Rationale: a single module + `cmd/` + `internal/` gives independent deployables without go.work multi-module version-pinning friction; the alternative go.work-per-service layout is the main scaffolding fork — see the summary gate.)
   - `docker-compose.yml` at the repo root wiring the **four infra services**, each with a healthcheck: `neo4j` (official `neo4j:5` image, bolt on 7687, http on 7474, auth via env, healthcheck via wget on 7474 / `cypher-shell`); `postgres` (`pgvector/pgvector:pg16` so the extension is preinstalled, healthcheck via `pg_isready`); `minio` (console + S3 API, path-style, healthcheck on `/minio/health/live`); `ollama` (`ollama/ollama`, 11434, healthcheck on `/api/tags`). A one-shot `ollama-pull` service `depends_on: {ollama: {condition: service_healthy}}` runs `ollama pull nomic-embed-text` **to completion**, so verification can assert the model is present without a manual step.
   - The stack uses a **completion-gated init chain** so runtime roles, schema, and the model all exist before any service authenticates (see the Data-Layer Bootstrap Invariant below): `db-bootstrap` (owner DSN; idempotently creates the two runtime **LOGIN** roles with passwords read from env by wrapping the shared `store.EnsureRoles` helper — a job/entrypoint, *not* a golang-migrate migration; `depends_on: {postgres: service_healthy}`; runs to completion) → `migrate` (owner DSN; runs `golang-migrate` up, which creates the extension, tables, and grants against the now-existing roles; `depends_on: {db-bootstrap: service_completed_successfully}`; runs to completion). The **four Go services** — `orchestrator`, `sandbox`, `sleepcycle`, `mcpserver`, each built from its `cmd/<service>` Dockerfile per the spec's local-dev topology (`.turbo/specs/arborette.md` line 119) — `depends_on: {migrate: service_completed_successfully}` and their infra healthchecks; the embedding-consuming services (`orchestrator`, `sleepcycle`, `mcpserver`) additionally `depends_on: {ollama-pull: service_completed_successfully}` so no service starts before its model is present. At this shell their stub mains start and idle rather than exit. Named volumes for Neo4j, Postgres, MinIO, and Ollama data; a shared network.
   - `internal/config` — a small shared env-based config loader (Neo4j URI/user/password, S3 endpoint/bucket/region/keys/path-style flag, Ollama URL + model, embedding dimension) reused by all four `cmd/` mains. It exposes **three** Postgres DSNs: an owner/migration DSN (used only by `db-bootstrap` and `migrate`), an orchestrator runtime DSN (authenticates as `arborette_orchestrator`), and a generic service runtime DSN (authenticates as `arborette_service`); all role passwords come from env, never committed. Runtime services use only the two runtime DSNs and never the owner DSN, so the DB-enforced boundary (Step 4 grants) actually binds. Include a `.env.example` documenting every variable and a `Makefile` (or `taskfile`) with `build`, `test`, `up`, `down`, `migrate-up`, `migrate-down` targets. (In production these roles/passwords are provisioned by IaC/secret management, not `db-bootstrap`; the migration grant story is identical.)

2. **Shared domain types** (`internal/domain`)
   - Go structs/enums matching the spec Data Model: `State`, `Intervention`, `Outcome`, `MetaHeuristic`, each with an application-assigned `ID string` (UUID). `InterventionType` enum (`query`, `extract`). `VerificationStatus` enum (`verified`, `unverified`, `confirmed`, `corrected`, `rejected`). `ProvenanceLocator` (page, char-span start/end, nullable). Relationship name constants `PreConditionFor`, `Produced`, `AbstractedFrom`. `ProducedEdge` fields (effect size, confidence weight 0.0–1.0). `EvaluationMatrix` type (targets to max/min + hard-constraint boundaries) for the goal registry. Keep these dependency-free so every package and service can import them.

3. **Neo4j repository interface + Cypher implementation** (`internal/graph`)
   - Define `graph.Repository` interface (the single seam all three graph-touching services share) with methods spanning node/edge CRUD: create/fetch `State`/`Intervention`/`Outcome`/`MetaHeuristic` by UUID `id`; create `PRE_CONDITION_FOR`, `PRODUCED` (with effect size + confidence), and `ABSTRACTED_FROM` edges; `CreateMetaHeuristic(ctx, mh, abstractedFrom []string)` that, **within one transaction, first validates every `abstractedFrom` ID resolves to exactly one existing node — erroring (and committing nothing) on any missing or duplicate reference — then** writes the node + its `ABSTRACTED_FROM` edges + `embedding_pending: true`, so a Meta-Heuristic is never abstracted from incomplete evidence (R10 auditability); a bare `MATCH ... WHERE n.id IN $ids` silently drops nonexistent IDs and must not be relied on for this; `ClearEmbeddingPending(ctx, id)`; `ListEmbeddingPending(ctx)` (crash-window retry); `UpdateOutcomeVerification(ctx, id, status, confidence)`; and an `ABSTRACTED_FROM` traversal `TraceCausalChain(ctx, metaHeuristicID)` returning the underlying State/Intervention/Outcome triplet(s).
   - Implement with `github.com/neo4j/neo4j-go-driver/v5` (`neo4j.DriverWithContext`, `ExecuteWrite`/`ExecuteRead` managed transactions, parameterized Cypher). Every node keyed on the app-assigned `id` property. Cypher restricted to the Neptune-portable openCypher subset (`MERGE`/`MATCH`/`CREATE`/`SET`/parameterized maps) — **no** APOC or `db.*` procedures.
   - A `graph.InitSchema(ctx)` that idempotently creates uniqueness constraints on each node label's `id` and any needed indexes (run at startup by consuming services; portable `CREATE CONSTRAINT IF NOT EXISTS`).

4. **PostgreSQL migrations: pgvector, goal registry, audit trail, grants** (`internal/store/migrations`, embedded via `embed.FS`)
   - `0001_pgvector.up.sql`: `CREATE EXTENSION IF NOT EXISTS vector;`
   - `0002_goal_registry.up.sql`: `goal_registry(optimization_function_id uuid pk, goal_text text, evaluation_matrix jsonb, datasource_ref text, created_at timestamptz)` — exactly the four columns the spec's goal registry defines (spec line 158) plus a timestamp. (The per-goal confidence threshold and speculative/blocking epoch-mode columns the Orchestrator/HITL shells need are **not** added here — they land as additive migrations in those shells; see risks.)
   - `0003_audit.up.sql`: single append-only `audit_log(id bigint generated always as identity primary key, actor text, action text, event_type text, detail jsonb, created_at timestamptz default now())`. **Use `GENERATED ALWAYS AS IDENTITY`, not `bigserial`** — an identity column needs only table-level `INSERT` privilege, avoiding the separate `USAGE ON ...audit_log_id_seq` grant a `bigserial` would require (and would silently fail without). The migration creates only the table; no `CREATE ROLE` lives in any migration (see the Bootstrap Invariant — roles are provisioned by `db-bootstrap`/IaC, which run before `migrate`).
   - `0004_meta_heuristic_embeddings.up.sql`: `meta_heuristic_embeddings(node_id uuid pk, embedding vector(768), updated_at timestamptz)` — `node_id` holds the **application-assigned node UUID** (the same `id` property the graph keys on, *not* Neo4j's internal element id; state this in a DDL comment so no downstream join reintroduces the internal-id coupling). Dimensioned to `nomic-embed-text`'s 768-d output. Index: **`hnsw (embedding vector_cosine_ops)`** — `hnsw` has no training step and builds incrementally, so it is correct for a migration that runs against an empty table; **do not** use `ivfflat` here, since its list centroids are trained from the rows present at build time and yield degraded recall when built on zero rows (defer any `ivfflat` index to a post-load step if ever needed).
   - `0005_grants.up.sql` (runs **after** all tables exist, granting against the roles `db-bootstrap` already created): the least-privilege matrix that enforces the audit boundary and gives each runtime role exactly the non-audit access it needs. `GRANT USAGE ON SCHEMA public` to both runtime roles. `arborette_orchestrator`: `SELECT, INSERT, UPDATE ON goal_registry`; `INSERT ON audit_log` (no `UPDATE`/`DELETE`); `SELECT ON meta_heuristic_embeddings` (its `heuristics.Query` similarity read). `arborette_service`: `SELECT, INSERT, UPDATE ON meta_heuristic_embeddings` (Sleep-Cycle upsert + MCP read) and `SELECT ON goal_registry` (worker goal-context reads); **no privilege of any kind on `audit_log`**. No runtime role ever receives `UPDATE`/`DELETE` on `audit_log`. (This matrix is the minimal starting set for the known consumers; later shells refine it additively as they wire real access.) Each `.up.sql` has a matching `.down.sql` (0005 down `REVOKE`s; roles are dropped by `db-bootstrap`/IaC teardown, never by a migration).
   - Wire `golang-migrate/migrate/v4` (with `iofs` source over the embedded FS + `pgx` database driver) behind a `store.Migrate(ctx, ownerDSN)` helper and the `migrate-up`/`migrate-down` Make targets. `store.Migrate` runs with the **owner** DSN (it must own the tables it grants on); the compose `migrate` init service is this helper.

5. **PostgreSQL access packages** (`internal/store`)
   - `store.Pool` — a `pgxpool` wrapper whose `pgxpool.Config.AfterConnect` calls `pgxvec.RegisterTypes` (`github.com/pgvector/pgvector-go/pgx`) on **every** connection; without this registration pgx cannot encode/decode the PostgreSQL `vector` type and the embedding upsert/search path fails at runtime despite compiling. **`RegisterTypes` looks up the `vector` type's OID, so it fails every connection acquisition (taking the whole pool down) if extension migration 0001 has not yet run** — build `store.Pool` only after `store.Migrate` has applied. The compose init chain guarantees this ordering for the stack (`migrate` completes before services start). A shared idempotent helper `store.EnsureRoles(ctx, ownerDSN, roleSpecs)` creates the two runtime **LOGIN** roles (with configured passwords) — the compose `db-bootstrap` service is a thin wrapper over it, and integration tests call it too, so both paths share one provisioning code path. Integration tests run `store.EnsureRoles(ownerDSN, ...)` **then** `store.Migrate(ownerDSN)` before constructing any runtime pool; this is what lets the `testcontainers-go` path (a bare Postgres container with no preexisting roles) survive `0005_grants` — without pre-created roles, `store.Migrate` fails with `role "arborette_orchestrator" does not exist`. `store.GoalRegistry` — insert/lookup by `optimization_function_id`, marshalling `EvaluationMatrix` to jsonb. `store.AuditLog` — an **insert-only** API (`Append(ctx, record)`) with no update/delete methods exposed; the boundary is enforced primarily by the least-privilege `arborette_orchestrator` role (Step 4 grants), with this insert-only Go API as the second layer. Only the Orchestrator wires this package, using the orchestrator runtime DSN. `store.EmbeddingStore` — upsert an embedding by `node_id` (the application-assigned node UUID) using `pgvector-go`'s `Vector` type, and a `SimilaritySearch(ctx, queryVec, k)` returning nearest `node_id`s by cosine distance.

6. **EmbeddingProvider interface + Ollama default** (`internal/embedding`)
   - `embedding.Provider` interface **distinguishes query from document embedding** — `EmbedQuery(ctx, text) ([]float32, error)`, `EmbedDocument(ctx, text) ([]float32, error)`, and `Dimensions() int` — because `nomic-embed-text` is trained to require task-instruction prefixes (`search_query:` for query text, `search_document:` for stored text) and asymmetric retrieval degrades without them, and Ollama does not apply them automatically. Baking the distinction into the interface now avoids an interface change across every consumer later (this shell exists to freeze that seam). `embedding.OllamaProvider` implements both via stdlib `net/http` POST to `{OLLAMA_URL}/api/embeddings` with `{"model":"nomic-embed-text","prompt": "<prefix> " + text}` — the method-appropriate prefix — returning the 768-d vector. A package doc comment documents the swap cost explicitly: switching providers (e.g. to Voyage AI) yields different-dimension, non-comparable vectors, requiring re-embedding every stored `Meta-Heuristic` and re-dimensioning the `pgvector` column via migration — not a live config toggle.

7. **Object-storage client** (`internal/objectstore`)
   - `objectstore.Client` wrapping `aws-sdk-go-v2` S3 with a custom `BaseEndpoint` + `UsePathStyle: true` (so the identical code runs against MinIO locally and S3 in prod, selected purely by config). Methods: `Put(ctx, key, r io.Reader, contentType) error`, `Get(ctx, key) (io.ReadCloser, error)`, and a `NewKey(...)` helper for deterministic object keys. Bucket bootstrap (`EnsureBucket`) for local MinIO.

8. **Pluggable DataSource interface** (`internal/datasource`)
   - Define the minimal, stable contract concrete sources implement: `datasource.SourceKind` (`tabular`, `document`); `DataSource` interface with `Kind() SourceKind` and `Introspect(ctx) (*Schema, error)`; a `Schema` type that represents **both** tabular columns (`[]Column`) and document candidate-extractable fields (`[]Field`) so the introspection contract (R2/R16) is shape-stable across future implementations. Concrete readers and any execution-facing methods are deliberately left to Shell 03 (file-based) / Shell 07 (document) — this shell ships only the interface + `Schema` types + a compile-checked stub in tests. (See risks re: keeping this seam additive.)

9. **Shared heuristics-query package** (`internal/heuristics`)
   - `heuristics.Service` constructed from an `embedding.Provider`, a `store.EmbeddingStore`, and a `graph.Repository`. `Query(ctx, stateString string, k int) ([]Match, error)`: embeds the string via the provider's **`EmbedQuery`** internally (the `search_query:` path), runs `EmbeddingStore.SimilaritySearch`, fetches the matched `MetaHeuristic` nodes from `graph.Repository` by `node_id`, and returns semantic definitions — callers pass a string and never touch `embedding.Provider` for this path. (Stored `Meta-Heuristic` definitions are embedded via `EmbedDocument` when the Sleep-Cycle shell writes them, keeping the query/document sides consistent.) `Trace(ctx, metaHeuristicID string)`: delegates to the repository's `ABSTRACTED_FROM` traversal for `trace_causal_chain`. This single package is what the Orchestrator's REST handler and the MCP Server's tool handler both call.

## Verification

This shell has no user-facing behavior; verification is build-time correctness plus data-layer round-trips against the compose stack.

- **Compiles clean:** `go build ./...` and `go vet ./...` succeed; `gofmt -l .` reports nothing.
- **Stack comes up (ordered init chain):** `docker compose up -d` runs `db-bootstrap` then `migrate` to successful completion *before* the Go services start; the four infra services (`neo4j`, `postgres`, `minio`, `ollama`) are healthy, the `ollama-pull` one-shot exits 0 (`docker compose exec ollama ollama list` shows `nomic-embed-text`), and the four Go services (`orchestrator`, `sandbox`, `sleepcycle`, `mcpserver`) are running as idle stubs. No Go service enters its idle state before `migrate` and (for embedding-consumers) `ollama-pull` have completed.
- **Migrations apply:** `store.Migrate` (owner DSN) succeeds; `psql "$OWNER_DSN" -c '\dt'` shows `goal_registry`, `audit_log`, `meta_heuristic_embeddings`; `SELECT extname FROM pg_extension WHERE extname='vector';` returns a row; `audit_log.id` is an identity column (`\d audit_log`); the embeddings table's PK is `node_id` and its column is `vector(768)` with an `hnsw` index (`\d meta_heuristic_embeddings`).
- **Audit credential boundary (DB-enforced):** connected as `arborette_orchestrator`, `INSERT INTO audit_log ...` succeeds (identity column — no sequence grant needed) but `UPDATE`/`DELETE` on `audit_log` are rejected; connected as `arborette_service`, any access to `audit_log` (including `INSERT`) is denied.
- **Runtime roles can use their non-audit tables (positive grant checks):** as `arborette_orchestrator`, `SELECT`/`INSERT`/`UPDATE` on `goal_registry` and `SELECT` on `meta_heuristic_embeddings` all succeed; as `arborette_service`, `SELECT`/`INSERT`/`UPDATE` on `meta_heuristic_embeddings` and `SELECT` on `goal_registry` succeed — confirming the grant matrix isn't only a lockout of `audit_log`.
- **Neo4j schema init:** `graph.InitSchema` applied; `cypher-shell "SHOW CONSTRAINTS"` lists the per-label `id` uniqueness constraints.
- **Integration smoke tests** (Go tests, run against the compose stack or `testcontainers-go`; named `internal/graph/graph_test.go`, `internal/store/store_test.go`, `internal/embedding/ollama_test.go`, `internal/objectstore/objectstore_test.go`, `internal/heuristics/heuristics_test.go`). On the `testcontainers-go` path each Postgres-touching test first calls `store.EnsureRoles(ownerDSN, ...)` then `store.Migrate(ownerDSN)` so the runtime roles exist before `0005_grants` and the audit-boundary checks can connect as each role:
  - graph: create `State`/`Intervention`/`Outcome` + `PRE_CONDITION_FOR`/`PRODUCED` edges, read back by `id`; `CreateMetaHeuristic` writes node + `ABSTRACTED_FROM` + `embedding_pending:true` in one tx; `ListEmbeddingPending` returns it; `ClearEmbeddingPending` empties the list. Also assert `CreateMetaHeuristic` with an `abstractedFrom` ID that does not exist (or a duplicate) returns an error and leaves **neither** the node **nor** any partial `ABSTRACTED_FROM` edge behind.
  - store: insert then scan a `pgvector` `Vector` value through `store.Pool` round-trips identical values (proves `pgxvec.RegisterTypes` is wired via `AfterConnect`).
  - embedding: `EmbedQuery(ctx,"hello")` and `EmbedDocument(ctx,"hello")` each return a 768-length vector and send the method-appropriate `search_query:`/`search_document:` prefix; `Dimensions()==768`.
  - objectstore: `Put`→`Get` round-trips identical bytes against MinIO with path-style addressing.
  - heuristics: seed a `MetaHeuristic` node + its embedding, then `Query(ctx,"...")` returns that node by similarity; `Trace` walks `ABSTRACTED_FROM` back to the seeded triplet.
- **Edge cases to spot-check:**
  - The `embedding_pending` crash window: a node created with the flag but no pgvector row is surfaced by `ListEmbeddingPending` (not treated as done).
  - `pgvector` rejects a wrong-dimension insert (guards the swap-cost invariant).
  - `store.AuditLog` exposes no update/delete method (insert-only enforced at the type level) **and** the DB role denies update/delete independently (belt-and-suspenders per the audit-boundary check above).
  - Object-store client works unchanged when only endpoint/credentials config differs (MinIO vs. a real S3 target).

## Risks & Downstream Notes (advisory)

- **Goal registry columns:** this shell ships only the four columns the spec's goal registry defines (spec line 158). The Orchestrator shell (goal intake) and the HITL shell add `confidence_threshold` (default 0.8) and the `speculative`/`blocking` epoch-mode flag as **additive** `golang-migrate` migrations — the migration workflow set up here is exactly what makes that a clean forward step, not a redesign.
- **DataSource seam:** the interface is deliberately minimal (`Kind` + `Introspect`). Shell 03 will add the file-based reader and may need execution-facing methods; those should extend the interface **additively** (or via a companion interface) so R16's "without changing the interface contract other consumers depend on" holds. Flagged so the file-based shell pins method signatures without forcing a document-source redesign later.
- **Embedding dimension is load-bearing:** `vector(768)` is tied to `nomic-embed-text`. Any provider swap is a migration + full re-embed, documented in `internal/embedding` — not a runtime toggle.
- **Stub services in compose:** per the spec's local-dev topology (line 119), all four Go services are wired into compose now, but their mains are behavior-less stubs (block on signal) until shells 02–05 implement them — expect idle containers, not functionality, from this shell. Their real endpoints, workers, and handlers arrive with those shells.
- **Data-Layer Bootstrap Invariant (load-bearing — Steps 1, 4, 5 all depend on it):** the DB-enforced audit boundary is a Postgres role/grant matter, not a Go-API convention, and it only works if provisioning, granting, and connecting happen in a fixed order. The invariant: **(1)** runtime **LOGIN** roles (`arborette_orchestrator`, `arborette_service`) are provisioned *outside* migrations — by `db-bootstrap` (dev/CI) or IaC/secrets (prod), idempotently, with env-supplied passwords; **(2)** migrations only `GRANT`/`REVOKE` against those pre-existing roles, in `0005_grants` which runs *after* every table exists; **(3)** every runtime pool is built only *after* `store.Migrate` has applied (extension + tables + grants); **(4)** runtime services connect with the two runtime DSNs, never the owner DSN. This exists to prevent the concrete failures already worked through: `golang-migrate` static SQL cannot interpolate env passwords (so no `CREATE ROLE ... PASSWORD` in a migration); `CREATE ROLE` defaults to NOLOGIN (runtime DSNs couldn't connect); roles are cluster-global while migration history is per-database (a migration-created role fails "already exists" on a second DB / persisted volume); a `bigserial` audit PK needs a separate sequence `USAGE` grant (avoided by `GENERATED ALWAYS AS IDENTITY`); a freshly created role has zero table privileges (so the grant matrix must positively cover `goal_registry` and `meta_heuristic_embeddings`, not just lock out `audit_log`); and `pgxvec.RegisterTypes` in `AfterConnect` downs the whole pool if the `vector` extension isn't present yet. Downstream services route audit writes through the Orchestrator's audit-write API (a later shell); only the Orchestrator uses the `arborette_orchestrator` DSN.
- **Module-layout fork:** single-module + `cmd/` is the chosen layout; a go.work multi-module layout is the alternative if strict per-service module isolation is later required.
