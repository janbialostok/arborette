# Arborette (Automated Causal Abstraction Engine)

## Overview

Arborette lets non-technical business and data analysts at a large financial institution (e.g. card fraud, data privacy/regulatory compliance) build domain-expert-level knowledge agents without writing code. An analyst describes a business goal in plain English and points the system at a dataset; the system translates that goal into a structured optimization function, then runs a two-phase discovery cycle. In **V1** — the current target — this cycle is purely **observational**: an **Active Hypothesis Loop** where an LLM proposes candidate data-segment definitions (read-only filters / `GROUP BY`s) that are measured against the wired data and recorded as strict, non-hallucinated **observational findings** — correlations ($P(\text{Outcome} \mid \text{Segment})$), not do-calculus causality — and a **Sleep Cycle** where a background **Monte Carlo Tree Search (MCTS)** searches the space of feature combinations to surface high-value macro-segments the greedy loop missed, which an offline LLM pass then abstracts into generalized, domain-agnostic `Meta-Heuristic` rules. Every V1 edge is tagged with its epistemic provenance (`observational`), so a future **V2** — which adds physically-executed interventions and do-calculus causal edges behind a Control Plane Router (see V2 Roadmap) — layers onto the same graph additively rather than by rewrite. The resulting graph is exposed via MCP so any downstream AI agent can query accumulated expert knowledge without parsing raw data.

The MVP proves this pipeline end-to-end for a single analyst working with a single dataset, with both phases manually triggered (not continuous background services), while building the pieces (pluggable data-source interface, graph-DB abstraction, audit trail) that let it scale to the full multi-analyst, multi-department vision later.

Real analyst datasets are rarely clean tables: a third-party-management analyst building an agent to pull effective dates, termination dates, and SLOs out of contracts is working from unstructured PDFs with no labeled ground truth. Arborette's hypothesis loop extends to this case — an intervention can be an extraction/classification task against a document, not just a query against a table — and because that data is unlabeled, low-confidence results route to a human-in-the-loop verification queue that never blocks the loop itself, with a live confidence view so the analyst can see how much of the current run to trust. Finally, the pipeline's output doesn't have to stop at a queryable graph: an analyst can preview a working, conversational agent built on that graph directly in the web UI, and — in production — export it as a standalone deployable.

## Users

- **Business/data analyst** (e.g. an analyst in the card fraud division, the data privacy division, or third-party/vendor contract management) — a domain expert with no coding ability who wants to encode their expertise into a reusable, queryable knowledge agent scoped to their division's problem (fraud detection modeling, regulatory-impermissible-data-use detection, contract-attribute extraction, etc.), verify low-confidence results the system surfaces to them, and optionally walk away with a working conversational agent rather than just a graph.
- **Downstream AI agent / developer** — consumes the seeded graph via the MCP interface to get pre-computed heuristics and audit trails without needing to understand the underlying graph schema.

## Requirements

### Analyst Goal Intake & Data Wiring

- **R1.** As an analyst, I want to describe my optimization goal in plain English so that I don't have to write code to define objectives and constraints.
  - Acceptance: An API endpoint (mirroring `submit_analyst_goal`) accepts a natural-language goal plus a data source reference and returns a structured `optimization_function_id`.
  - Acceptance: The system uses the LLM to translate the goal into a structured Evaluation Matrix (targets to maximize/minimize, plus hard-constraint boundaries).
  - Acceptance: `submit_analyst_goal` only registers the goal, produces the Evaluation Matrix, and wires the data source — it does **not** start the Active Hypothesis Loop. This departs from the concept doc, where goal submission auto-kicks off Phase 1; the MVP's manual-trigger scope (R5, R9) requires separating registration from execution.
  - Acceptance: The registered goal, its Evaluation Matrix, and its data-source reference persist in the goal registry (see Design § Data Model) so a later, separate call to trigger Phase 1 can look them up by `optimization_function_id`.
- **R2.** When an analyst points the system at a data source, the system shall introspect its schema and identify variables relevant to the optimization targets without the analyst writing connectors or joins.
- **R3.** The system shall expose data-source access behind a pluggable interface, so new source types (e.g. a Spark connector or STS-token-based data-lake access) can be added later without changing hypothesis-loop or orchestration code.
- **R4.** For the MVP, the system shall support file-based data sources only (an uploaded file, or a file already present on disk).
  - Acceptance: Uploaded files are written to durable, shared storage (an object store) reachable by both the Orchestrator and the separately-deployed Sandbox Execution service, referenced by an object key/path stored alongside the goal registration — not local disk on either service. "A file already present on disk" means a path on a volume mounted into the Orchestrator's environment (e.g. a configured local-import directory); the Orchestrator reads it from that mount and copies it into the object store during goal intake exactly like an uploaded file, so both ingestion paths converge on the same object-store-backed representation before Sandbox Execution ever touches them. This applies uniformly to tabular files and to document files (R16) — no separate on-disk mechanism for documents.

### Active Hypothesis Testing Loop (Phase 1)

- **R5.** When an analyst triggers the hypothesis loop for a submitted goal, the LLM shall propose a directed tree of candidate interventions, using system-chosen defaults for tree breadth, depth, and stopping condition — no analyst configuration required for the MVP.
  - Acceptance: A dedicated REST endpoint, distinct from `submit_analyst_goal`, starts the Active Hypothesis Loop for a given `optimization_function_id`.
- **R6.** The system shall evaluate each candidate intervention as a read-only analytical query or simulation against the wired dataset — interventions never enact real-world side effects in the MVP.
  - Acceptance: Intervention parameters proposed by the LLM (via structured outputs) compile to a deterministic, read-only SQL query or aggregation executed by an embedded query engine over the wired file data.
  - Acceptance: In V1 a "candidate intervention" is a purely **observational data-segment definition** — a read-only filter / `GROUP BY` slice of the wired data, not a physically-executed action. The word "intervention" is retained for schema and API continuity (the reified `Intervention` graph node — see Data Model), but V1 never mutates the world; physically-executed interventions are a V2 concept (R25, V2 Roadmap). This is what makes V1's findings correlational rather than causal (R7).
- **R7.** The system shall measure each intervention's outcome against the analyst's Evaluation Matrix and write the result as a strict, empirically-grounded **observational triplet** — `(Measured Start State) -> [Reified Segment] -> (Measured Outcome State)` (the `[Reified Segment]` is the `Intervention` graph node — V1's reified read-only data-segment; see R6, R25, Data Model) — with no hallucinated or unverified values. **What is guaranteed is the *measurement*, not causation:** V1 records a correlation, $P(\text{Outcome} \mid \text{Segment})$, exactly as computed from the data; it does **not** claim the segment *causes* the outcome — that is V2's do-calculus job (R25, V2 Roadmap). The inbound `PRODUCED` edge carries `epistemic_source: observational` (R25). This "empirically-grounded" guarantee — the correlation is exactly measured, never hallucinated — holds unconditionally for `query`-type interventions (R6, a deterministic result computed directly from the data); a `query`-type triplet's `PRODUCED`-edge confidence weight (see Design § Data Model) is fixed at 1.0, since the measured correlation requires no verification. For `extract`-type interventions (R17), see R17's scoped distinction between schema-constrained and verified values — an `extract` outcome only reaches confidence 1.0, and only becomes eligible to feed the Sleep Cycle (R9), once it is HITL-confirmed (R18).
- **R8.** The Active Hypothesis Loop shall run interactively and synchronously within a single analyst session (not as a continuous background process) for the MVP.
  - Acceptance: The Orchestrator streams loop progress (tree nodes and observational triplets as they're produced) to the web UI over the same session, so "synchronous" means the analyst stays in one continuous session rather than the request blocking until the entire loop completes.

### Sleep Cycle & Heuristic Abstraction (Phase 2)

- **R9.** When an analyst manually triggers the Sleep Cycle, the system shall run a **Monte Carlo Tree Search (MCTS)** over that analyst's accumulated observational segment findings to discover high-value **macro-segments** — conjunctions of the single-feature segments the greedy Phase 1 loop produced — that score better against the goal's objective than any single segment alone. This compensates for the myopic, greedy nature of the Phase 1 LLM, which proposes one segment at a time and cannot see that a feature *combination* wins. MCTS replaces Louvain community detection as the Phase 2 discovery mechanism for the MVP; clustering/grouping of heuristics is a deferred optimization (see MVP Scope, V2 Roadmap).
  - Acceptance: A dedicated REST endpoint triggers the Sleep Cycle for the analyst's dataset.
  - Acceptance: MCTS rollouts are **empirically measured, not estimated**. A candidate macro-segment's objective value is obtained by compiling its conjoined filter into a read-only query and executing it through the Sandbox Execution service (the same deterministic `query` path Phase 1 uses, R6) — the search never scores a combination from an assumed-independence estimate over single-segment stats, so a macro-segment finding carries the same non-hallucination guarantee as a Phase 1 finding (R7). A rollout whose Sandbox `query` call errors or times out (Sandbox unavailable, or a DuckDB error on a pathological conjoined filter) is scored as a non-improving miss and recorded via the audit-write API — it does **not** abort the Sleep Cycle run, mirroring Phase 1's per-branch failure handling (R6, Key Flow 2).
  - Acceptance: Each materially-better macro-segment MCTS surfaces is written back to the graph **as a full R7-shaped observational triplet** — a `State` (the parent/baseline segment the macro-segment refines) + `PRE_CONDITION_FOR` edge + `Intervention` (`type: query`, flagged MCTS-derived, its parameters the conjoined filter) + `PRODUCED` edge (`epistemic_source: observational`) + `Outcome` — not merely the `Intervention→Outcome` fragment. The complete `State→Intervention→Outcome` path is required because `trace_causal_chain` (R12) matches only complete paths; without the `State` and `PRE_CONDITION_FOR` edge the derived macro-segment — the very finding a `Meta-Heuristic` abstracts — would be silently dropped from every trace and the audit drill-down.
  - Acceptance: The write-back is **idempotent and crash-safe**. The derived `Intervention` (and its paired `State`/`Outcome`) take a **deterministic id** derived from the goal id and the canonicalized conjoined filter, so the graph repository's MERGE-on-id makes a Sleep-Cycle re-run after a mid-write crash re-write the same nodes rather than append duplicate macro-segment triplets — which would otherwise pollute the next MCTS run's input, since re-triggering accumulates rather than replaces (Key Flow 2). This extends the Worker's crash-safe progress guarantee (Design § Architecture) from the abstraction/embedding stage back to cover the write-back stage.
  - Acceptance: The MCTS search space only draws on segment findings whose `Outcome.verification_status` (see Design § Data Model) is `verified` (all `query`-type outcomes, always — R7) or `confirmed`/`corrected` (`extract`-type outcomes HITL-resolved — R18). This status field, not the `PRODUCED`-edge confidence weight, is the actual gate — confidence is a self-reported, unverified signal (R17) and is never sufficient on its own to make a finding search-eligible, no matter its value. An `extract` outcome with `verification_status: unverified` (above-threshold, not yet reviewed) or `rejected` is excluded from the search; unverified outcomes remain in the graph for audit and become eligible only once an analyst confirms them (R18, including on-demand review of above-threshold outcomes, not just queued ones). This keeps every `Meta-Heuristic` traceable to empirically-grounded evidence per R7/R10, at the cost of Sleep Cycle data volume on extraction-heavy goals where most results go unreviewed — accepted because a bad heuristic propagates to every future `get_optimized_heuristics` query that surfaces it (see Design § Tech Stack — Phase 2). Note this is a *different*, stricter bar than R19's loop-level branch pruning, which uses unverified confidence scores freely — pruning is a reversible, in-loop search decision, while abstraction creates a permanent, served `Meta-Heuristic`.
  - Acceptance: If the search is degenerate — no macro-segment scores materially better than the best single segment, or there are too few verified findings to form any combination (plausible given a single dataset's limited history) — the run records that no `Meta-Heuristic` could be abstracted rather than forcing an abstraction from an insufficient sample.
- **R10.** The system shall use an offline/background LLM pass to abstract each high-value macro-segment path MCTS surfaced (R9) into a generalized `Meta-Heuristic` node, establishing an `ABSTRACTED_FROM` link back to the specific observational triplets that support it (the single-feature segments composing the macro-segment plus the derived macro-segment finding).
  - Acceptance: **Ontological naming (in-MVP):** before writing, the abstraction pass strips domain-specific payloads and maps the concrete variables to a universal, high-level *structural* ontology (e.g. `HomePlanet = 'Mars'` → `[Primary Population Center]`; `Transport Rate` → `[System Output]`), so the `Meta-Heuristic`'s semantic definition is portable-by-construction rather than bound to one dataset's column names. This is cheap phrasing work done at abstraction time and ships in the MVP.
  - Acceptance: **Cross-dataset reuse (deferred):** a new dataset's Phase 1 querying prior `Meta-Heuristic` nodes to seed its first segment proposals (the "Cold Start" bootstrap) requires cross-dataset lookup and an ontology→concrete-column remapping step, and is deferred alongside R11's cross-dataset discovery (see MVP Scope). The MVP produces ontology-named heuristics but does not yet consume them across datasets.
- **R11.** For the MVP, the Sleep Cycle's MCTS search and abstraction operate within a single analyst's single dataset; cross-dataset / cross-department discovery — and the cross-dataset *reuse* of ontological `Meta-Heuristic`s to bootstrap a new dataset (R10's deferred Cold-Start path) — are the full-vision behaviors and are deferred.

### MCP Interface

- **R12.** The system shall expose `submit_analyst_goal`, `get_optimized_heuristics`, and `trace_causal_chain` as MCP tools, per the schemas in the concept spec, so any downstream AI agent can consume the seeded graph without parsing raw graph data.
  - Acceptance: The MCP server's `submit_analyst_goal` tool delegates to the Orchestrator's REST API rather than writing directly — `get_optimized_heuristics` and `trace_causal_chain` remain read-only queries against the graph and vector stores.
  - Acceptance: `get_optimized_heuristics` matches the caller's operational-state string to relevant `Meta-Heuristic` nodes via embedding-based semantic similarity search (see Design § Tech Stack — Embeddings & Vector Search), not exact or keyword matching.
  - Acceptance: MCP's role in the MVP is read-side heuristic consumption for downstream agents (`get_optimized_heuristics`, `trace_causal_chain`) plus goal registration (`submit_analyst_goal`, proxied to the Orchestrator). Advancing a registered goal through Phase 1 or Phase 2 is a REST-only, human-analyst-driven action in the MVP — a pure-MCP consumer can register a goal but cannot itself trigger either phase; this is intentional, not a gap.

### Audit & Compliance

- **R13.** The system shall append an immutable, append-only audit record — capturing actor identity, timestamp, and action — for every intervention, outcome, heuristic-injection, HITL-verification-resolution (R18), and hypothesis-loop-branch-failure event.
  - Acceptance: All services that produce auditable events — including the Sleep-Cycle Worker's heuristic-injection events and its MCTS-derived `intervention`/`outcome` write-backs (R9), which emit `intervention` and `outcome` audit events per this requirement's blanket "every intervention, outcome" scope — write audit records through an internal audit-write API exposed by the Orchestrator, rather than writing to the audit table directly. Only the Orchestrator holds credentials to the audit table itself.
- **R14.** For the MVP, every audit record shall carry a single configured analyst identity (stub identity, no login flow); full authentication and per-department access control are deferred (see Open Questions).

### Web UI

- **R15.** As an analyst, I want a modern web interface to submit goals, watch the hypothesis loop progress, and browse resulting heuristics, so that product demos aren't derailed by rough UX.
  - Acceptance: A goal-submission form with a data-source picker (file upload / on-disk file selection).
  - Acceptance: A live or progressively-updating view of the hypothesis tree and resulting observational triplets as Phase 1 runs.
  - Acceptance: A heuristic browser listing `Meta-Heuristic` nodes with drill-down into their supporting evidence (i.e. a UI over `trace_causal_chain`).

### Multi-Modal & Unstructured Data Sources

- **R16.** As an analyst, I want to point the system at semi-structured or unstructured documents (e.g. a contract PDF), not just tabular files, so that I can build agents around goals like "accurately extract effective date, termination date, and SLOs from a contract."
  - Acceptance: The pluggable `DataSource` interface (R3) gains a document-oriented implementation (PDF, MVP scope) alongside the existing file-based (CSV/Parquet) implementation, without changing the interface contract other consumers depend on.
  - Acceptance: Schema introspection (R2) for a document `DataSource` returns a set of candidate extractable fields (e.g. inferred from the analyst's goal text plus a sample pass over the document) instead of a tabular column list. As with the tabular case (R1/R2), the Evaluation Matrix's targets/constraints are produced from goal text alone, then a subsequent field-binding step — introspection, per Key Flow 1 — maps those targets to these candidate fields rather than to table columns; the Matrix itself is not blocked on introspection completing first.
- **R17.** When the hypothesis loop evaluates a candidate intervention against a document `DataSource`, the system shall treat the intervention as an extraction/classification task rather than a deterministic query.
  - Acceptance: The Sandbox Execution service's intervention-execution contract (R6) is generalized to a `type` discriminated union: `query` (existing DuckDB path, unchanged) and `extract` (new path). An `extract` intervention specifies a target field and an extraction method (e.g. a prompt template or field-specific instructions); execution compiles it into a Claude API call with the document supplied via the Files API/PDF input, using structured outputs (`output_config.format`) to constrain the returned value to the field's expected type — never freeform text. This call does not enable Citations (`citations: {enabled: true}`) — Citations and `output_config.format` are mutually incompatible on the Claude API (a combined request is rejected) — so the extraction call returns only the typed value and a confidence score; provenance is computed separately (see R18).
  - Acceptance: Structured outputs make an `extract` result **schema-constrained** in exactly the way a DuckDB result is deterministic — the value's type/shape cannot deviate from the declared schema — but this is not the same as **verified**. Whether the extracted value is actually correct is not guaranteed by structured outputs alone; that correctness question is exactly what the outcome's confidence score and the HITL threshold (R18) exist to gate. An unverified `extract` outcome (above-threshold, not yet reviewed) is a typed model assertion, not an empirical measurement in the sense R7 means for the `query` path; it becomes an empirical measurement only once HITL-confirmed (R18).
  - Acceptance: The measured "outcome" of an `extract` intervention is the extracted value plus the model's confidence in that extraction; this outcome is evaluated against the Evaluation Matrix and written as an observational triplet exactly as R7 already specifies — `(Measured Start State) -> [Reified Intervention] -> (Measured Outcome State)` — so `extract` and `query` interventions produce triplets with the same shape and flow through the same graph, audit, and heuristic-abstraction machinery unchanged.
  - Acceptance: For a document goal with multiple target fields (e.g. effective date, termination date, and SLOs from a single contract), each target field is evaluated as its own sub-tree within the run rather than one combined tree spanning all fields. Within a field's sub-tree, R5's "breadth" corresponds to competing extraction methods or prompt strategies tried for that field, and "depth" corresponds to refinement iterations (e.g. re-extracting with additional document context or a different strategy after a low-confidence result) — not to different fields, which R16's schema introspection has already enumerated up front.

### HITL Verification & Confidence

- **R18.** As an analyst, I want low-confidence extraction/intervention results routed to a human verification queue, so that the system doesn't silently trust unlabeled data it isn't sure about.
  - Acceptance: Every `extract`-type outcome (R17) carries a confidence weight on its inbound `PRODUCED` edge (the existing edge field from R7's Design — see Design § Data Model). A system-default confidence threshold (configurable per goal, not hardcoded) determines whether the outcome is auto-accepted or queued for HITL review — below-threshold outcomes queue; at-or-above-threshold outcomes proceed unverified (see R17's schema-constrained-vs-verified distinction).
  - Acceptance: Every `extract`-type `Outcome` also records a provenance locator, computed deterministically rather than requested from the model (the extraction call can't request Citations alongside structured outputs — R17). Once the extraction call returns the typed value, the Sandbox Execution service runs a standard PDF-text-extraction pass over the document (independent of the Claude call) and locates the value's first matching occurrence in that plain text, recording the match's page number and character span as the locator. If no exact match is found (e.g. the model reformatted the value — a differently-punctuated date, a normalized number), the locator is recorded as null and the HITL UI falls back to showing the full source page for review instead of a pinpoint excerpt. The web UI's HITL verification interface renders this excerpt (or the page fallback) alongside the queued outcome's extracted value, letting the analyst confirm, correct, or reject it.
  - Acceptance: A verification's resolution sets the `Outcome`'s `verification_status` to `confirmed`, `corrected`, or `rejected` (see Design § Data Model — this status, not the confidence weight, is what makes an outcome eligible for Sleep-Cycle search), and updates the confidence weight on the `Outcome`'s inbound `PRODUCED` edge to 1.0 on confirm or correct (analyst-confirmed ground truth). On a **correction**, the extracted value is updated and the provenance locator is recomputed against the new value (or nulled, falling back to the full-page view, if no exact match is found — same handling as the original extraction). On a **rejection**, the `Intervention -> Outcome` triplet is retained (not deleted, for audit) with `verification_status: rejected`, so the Sleep Cycle (R9) never abstracts a `Meta-Heuristic` from it; confirmed and corrected triplets flow into the Sleep Cycle and audit trail unchanged, like any other triplet.
- **R19.** The Active Hypothesis Loop shall not block on individual HITL verifications — verification requests queue and resolve asynchronously relative to loop execution.
  - Acceptance: When a tree depth level's candidates finish evaluating, the loop's default behavior is to proceed immediately to proposing and pruning the next depth level, using each branch's own (possibly unverified) confidence score for pruning — HITL verifications for the completed level continue resolving in the background. This is configurable per goal to instead block depth-level advancement until that level's queued verifications resolve, trading loop speed for pruning decisions that are never based on unverified data.
  - Acceptance: A verification that resolves after its depth level has already been pruned past does not retroactively re-run the loop; it updates the resolved triplet's `PRODUCED`-edge confidence and, on correction, the `Outcome` value, in place, and the next Sleep Cycle run (R9) — whose MCTS searches only verified triplets — is what makes a newly-confirmed outcome eligible for abstraction into a `Meta-Heuristic` for the first time. This asynchronous reconciliation, not loop replay, is how verification results ultimately feed back; see Open Questions for the known gap around already-abstracted `Meta-Heuristic` nodes whose supporting evidence is later corrected or rejected.
- **R20.** As an analyst, I want to see the system's current confidence during an active run, so that I can judge how much to trust in-progress results without waiting for the run to finish.
  - Acceptance: The web UI's live hypothesis-loop view (R15) includes a confidence-bin distribution — a histogram of `PRODUCED`-edge confidence weights (0.0–1.0, binned) across all triplets produced so far in the run, updating live as new triplets stream in over the existing SSE connection (R8).

### Agent Export

- **R21.** As an analyst, I want the hypothesis-testing/Sleep-Cycle pipeline to optionally produce a working, conversational agent — not just a queryable heuristics graph — so that the accumulated expertise is directly usable, not just inspectable.
  - Acceptance: The exported agent is a standard Claude tool-use agent whose available tools are the two read-only MCP tools (`get_optimized_heuristics`, `trace_causal_chain`) — connected via Claude's native MCP connector (no hand-written tool schemas or dispatch code), so the agent decides when to look up heuristics or trace evidence based on the conversation rather than following a fixed retrieval script. Which MCP server instance answers those tool calls differs by surface, not by tool set: the preview (R23) targets the arborette MCP Server (R12) directly; a production export (R24) targets the bundle's own vendored server instead — R21 defines the agent's tool set and connector-based architecture, common to both. `submit_analyst_goal` is deliberately excluded from this tool set: it's a write action with no defined confirmation/authorization flow for a chat surface, and including it is what created R24's original self-containment contradiction (see R24) — a conversational knowledge-consumption agent has no need to register new goals.
  - Acceptance: Claude's native MCP connector is a server-side Anthropic API feature — Anthropic's own infrastructure, not arborette's, is what opens the connection to the MCP Server URL, so that URL must be publicly reachable (not an in-network/VPC-private address) and is protected by the `mcp_servers[].authorization_token` field the connector supports. This is not new exposure: R12 already requires the MCP Server to be reachable by external downstream agents, so R21/R23 reuse that same public, token-authorized endpoint rather than standing up a separate one. A backend component (the Orchestrator, R23; a vendored equivalent for export, R24) holds the Anthropic API key and makes the `mcp_servers`/`mcp_toolset` call on the browser's behalf (see Design § Architecture); the browser only ever talks to that backend, never to the MCP Server or Anthropic directly.
  - Acceptance: The agent uses `claude-sonnet-5` by default — the best balance of speed and intelligence for a conversational, low-latency chat surface — configurable to a different model.
- **R22.** The exported agent shall present a default chat UI styled as a clean, minimal iMessage-style conversation — bubbled messages, no visual chrome beyond what a native chat app needs — so every agent produced by the system has a consistent, presentable default without per-analyst design work.
  - Acceptance: The default styling is a shared, reusable component (not duplicated per exported agent), documented as arborette's standard agent chat style.
- **R23.** As an analyst, I want to try the agent immediately after a run, so that I can validate it before deciding whether to export it.
  - Acceptance: The web UI (R15) gains a "preview agent" action that launches the default chat UI in a preview tab, backed by a chat endpoint on the Orchestrator (R21's second acceptance criterion) that holds the Anthropic API key and calls the Messages API with the native MCP connector pointed at the MCP Server (R12), scoped to the analyst's current goal/dataset context — no export or packaging step required to try it.
- **R24.** As an analyst, I want to bundle and export a validated agent as a standalone deployable, so that it can run outside the arborette web UI in production.
  - Acceptance: The exported bundle is self-contained — it packages the system prompt, model configuration, default chat UI, a minimal backend that holds its own Anthropic API key and makes the Messages-API/native-MCP-connector call (the same role the Orchestrator plays for the preview, R23), and a vendored copy of the MCP server scoped to the agent's two read-only tools — rather than depending on a separately-running arborette MCP Server instance, so the bundle has no runtime dependency on the arborette deployment that produced it. Critically, "vendoring the MCP server" alone is not sufficient: `get_optimized_heuristics` and `trace_causal_chain` answer from the goal's `Meta-Heuristic` subgraph (Neo4j) and embeddings (`pgvector`), which the vendored server code does not itself contain. The export step must also snapshot that goal-scoped graph and embedding data into an embedded datastore bundled alongside the vendored server (exact embedded-store choice left to implementation time, since R24 is deferred), so the exported agent's two tools can answer without reaching back into the arborette deployment's Neo4j/PostgreSQL instances.
  - Acceptance: Production export is explicitly out of MVP scope (see MVP Scope) — the demo preview (R23) is what ships first, built on the same native-MCP-connector architecture so export is additive packaging work, not a redesign.

### Epistemic Provenance & V2 Forward-Compatibility

- **R25.** V1 is a purely **observational** engine, and the graph shall record the epistemic provenance of every empirical edge so the future V2 interventional layer (see V2 Roadmap) can coexist on the same graph without a rewrite.
  - Acceptance: Every `PRODUCED` edge written in V1 carries an `epistemic_source` property set to `observational`. This is an **additive discriminator**, not a rename — the existing `PRODUCED` edge and all its current Cypher across the Orchestrator, MCP Server, and Sleep-Cycle Worker stay intact; only the new property is added. The revision's conceptual `OBSERVED_CORRELATION` vs. `PRODUCED_EFFECT` distinction is realized as this property value (`observational` vs. `interventional`) rather than as two physically-distinct edge labels, so V1 code needs no relabeling migration.
  - Acceptance: The reified middle node of a triplet (the `Intervention` graph label) is, in V1, always **observational** — nothing is physically executed. Its existing `type` field (R17's `query`/`extract` discriminated union) already distinguishes a read-only data-segment definition (`query`, R6) from a document-extraction task (`extract`, R17). A physically-executed action is a **new `type` value reserved for V2**, written together with the `epistemic_source: interventional` edge value; neither is written in the MVP. No new node-level field is introduced — the reservation reuses the existing `type` field.
  - Acceptance: Any V1 consumer that reads `PRODUCED` edges (the Sleep-Cycle MCTS, `trace_causal_chain`) shall treat a missing `epistemic_source` as `observational` and shall not assume the `interventional` value exists, so a V2 upgrade that starts writing interventional edges does not break V1 read paths.
  - Acceptance: No V1 requirement depends on the interventional path existing; R25 exists solely to keep V2 additive. The full V2 dual-engine design (Control Plane Router, sandboxed interventions, do-calculus scoring) is roadmap, captured in the V2 Roadmap section, not MVP requirements.

## Design

### Architecture

Split into independently deployable Go services from the start (not a monolith), reflecting the target production shape:

1. **Orchestrator/API service** — hosts the REST API the web UI calls, including explicit endpoints to register a goal (`submit_analyst_goal`), start the Active Hypothesis Loop for a goal, and manually trigger the Sleep Cycle. During goal intake, calls the Sandbox Execution service to introspect the wired file's schema (R2) rather than reading the file itself. Owns Phase 1 hypothesis-loop orchestration and streams its progress (tree nodes, observational triplets) to the web UI over Server-Sent Events (SSE) as they're produced — the loop itself runs independently of that SSE connection, so a dropped connection interrupts only the live view, not the loop. Owns the goal registry (registered goals, their Evaluation Matrices, and data-source references — see Design § Data Model) and is the only service holding credentials to the audit table, exposing an internal audit-write API that other services (e.g. the Sleep-Cycle Worker) call rather than writing to the table directly. Owns the HITL verification queue (R18): routes below-threshold `extract` outcomes onto it (also exposing any at-or-above-threshold outcome for on-demand review), exposes REST endpoints for the web UI to list/browse verifications and submit resolutions, and applies a resolution to the underlying `Outcome`'s `verification_status` and `PRODUCED`-edge confidence without blocking the hypothesis loop (R19). Includes the per-run confidence-bin distribution (R20) in the same SSE stream as tree/triplet progress, computed incrementally as triplets are written and re-pushed when a resolution changes an existing triplet's confidence outside that path. Also owns the agent-preview chat endpoint (R21/R23): holds the Anthropic API key server-side and, per browser message, calls the Claude Messages API with the native MCP connector (`mcp_servers` pointed at the MCP Server's public, token-authorized endpoint — the same one R12's external downstream agents already use, not a separate in-network address — `mcp_toolset` scoped to the two read-only tools) — the browser only ever talks to this endpoint over the same kind of streamed connection as Phase 1 progress, never to the MCP Server or to Anthropic directly.
2. **Sandbox Execution service** — executes candidate interventions against wired data sources on behalf of the orchestrator; stateless and horizontally scalable. Reads uploaded/on-disk files from the shared object store (see Design § Tech Stack — File Storage) by the key/path recorded in the goal registry, not from local disk. Also performs schema/field introspection at goal-intake time (R2, R16) — the same object-store access path used later for Phase 1 intervention execution. Two intervention-execution paths behind one discriminated-union contract (R17): `query` — the original path, compiling structured parameters into a deterministic, read-only DuckDB query over tabular file data; and `extract` — a Claude API call (structured outputs, document supplied via the Files API) over a document `DataSource`, returning a typed field value plus confidence. Both paths return the same triplet-shaped result to the Orchestrator, so R6/R7's observational-triplet writes don't distinguish which path produced them.
3. **Sleep-Cycle Worker** — a manually-triggered batch job that runs **MCTS** over the analyst's accumulated, verified observational segment findings to discover high-value macro-segments (R9), then abstracts each surfaced macro-segment path — applying ontological naming (R10) — via a synchronous Claude API call for the MVP (see Design § Tech Stack — Phase 2 for why this replaces the Message Batches API here). MCTS rollouts are empirically measured by calling the **Sandbox Execution service** to run each candidate macro-segment's conjoined read-only query (R9) — so the Worker depends on Sandbox Execution, not just the graph repository; a rollout whose Sandbox call errors or times out is scored as a non-improving miss and recorded, never aborting the run (R9). Each materially-better macro-segment is written back before abstraction as a full `State→Intervention→Outcome` observational triplet with a deterministic id (goal id + canonicalized conjoined filter), so the write-back is idempotent across re-runs and the derived finding is returned by `trace_causal_chain` (R9). Writes `Meta-Heuristic` nodes and embeddings through the same repository interface as the Orchestrator and MCP Server (see Design § Tech Stack — Graph Database), and reports heuristic-injection events — and the `intervention`/`outcome` events for its MCTS-derived write-backs (R13) — to the Orchestrator's audit-write API. Persists its own batch/abstraction progress so a restart resumes rather than reprocessing — an abstraction counts as done only once its `Meta-Heuristic` node has `embedding_pending: false` (see Design § Data Model), not merely on node existence, so a crash between the Neo4j and `pgvector` writes is picked back up rather than silently skipped. Records a per-macro-segment failure (rather than aborting the whole run) if an individual abstraction call errors. Runs as an ephemeral container locally and as an AWS Batch/Fargate job in production.
4. **MCP Server** — implements `get_optimized_heuristics` and `trace_causal_chain` as read-only queries against the graph and vector stores using the official Go MCP SDK. `submit_analyst_goal` on this server delegates to the Orchestrator's REST API rather than writing directly, so the MCP server itself never mutates state. Exposed on a public, `authorization_token`-protected endpoint — required by R12 so external downstream agents can reach it, and reused by R21/R23's native-MCP-connector call rather than standing up a separate in-network address (Anthropic's infrastructure, not arborette's, opens that connection, so it cannot be VPC-private). Downstream agents (R12, the original use case) reach all three tools directly; arborette's own preview/exported agent (R21/R23) is deliberately scoped to just the two read-only tools (R21) and reaches this server only via the Orchestrator's chat endpoint's native-MCP-connector call, never directly. Production export (R24, deferred) would vendor this server's two-tool read surface into the exported bundle, alongside its own key-holding backend and a snapshot of the goal's graph/vector data (see R24), rather than reuse the running instance or the Orchestrator.

A separate **web front-end** (React + TypeScript + Next.js) talks to the Orchestrator's REST API — kept as its own deployable so front-end iteration doesn't couple to the Go backend's release cadence. Includes a HITL verification interface, the live confidence-bin distribution, and a "preview agent" tab (R23) that renders the default iMessage-style chat component and streams over the Orchestrator's chat endpoint — the front-end never holds an Anthropic API key and never talks to the MCP Server or Anthropic directly.

**Local dev:** docker-compose runs all four Go services plus Neo4j, PostgreSQL, an object-storage emulator (e.g. MinIO) for file uploads, and the local embedding sidecar (see Design § Tech Stack — Embeddings & Vector Search). Since the native MCP connector requires a publicly-reachable MCP Server address (see MCP Server, above), exercising the live agent-preview flow (R23) against the real Claude API in local dev requires tunneling the MCP Server's port (e.g. `ngrok` or `cloudflared`) — core hypothesis-loop/Sleep-Cycle development does not need this, only live preview/chat testing does.
**Production (AWS):** ECS/Fargate hosts the always-on services (Orchestrator, Sandbox Execution, MCP Server); AWS Batch (on Fargate) runs the ephemeral Sleep-Cycle job; Neo4j and PostgreSQL run self-hosted (EC2/ECS); uploaded files live in S3 for the MVP.

### Tech Stack

- **Language:** Go across all backend services.
- **LLM provider:** Anthropic Claude, via the official Go SDK (`github.com/anthropics/anthropic-sdk-go`).
  - **Phase 1 (interactive):** Claude Opus 4.8, adaptive thinking enabled, `effort: high` (raise to `xhigh` for the hardest hypothesis-generation cases). Observational triplets and the Evaluation Matrix are produced via structured outputs (`output_config.format` with a JSON schema) rather than freeform text, so the "strict, non-hallucinated" requirement (R7) is enforced at the API level, not just by prompting.
  - **Phase 2 (offline/batch):** The Sleep Cycle has two stages. **(a) MCTS discovery** — a Go implementation of Monte Carlo Tree Search (UCT selection) explores the space of segment conjunctions over the verified observational findings (R9); each rollout's macro-segment objective value is measured empirically by calling the Sandbox Execution service's deterministic `query` path (never estimated from single-segment stats under an independence assumption), preserving the non-hallucination guarantee (R7). No Claude call is involved in discovery — it is pure search over measured data. **(b) Ontological abstraction** — for each high-value macro-segment MCTS surfaces, a standard (synchronous) Claude API call against Claude Opus 4.8 abstracts the path into a `Meta-Heuristic`, via structured outputs and a prompt that instructs the model to strip domain payloads and map variables to a universal structural ontology (R10). Synchronous rather than the Message Batches API because the Batches API's multi-hour turnaround conflicts with R15's demo-ability goal, and a single-analyst/single-dataset MVP surfaces few enough macro-segments per run that the cost difference is negligible. The Message Batches API (50% cost reduction) is a documented future optimization once real multi-dataset volume makes the savings meaningful; quality is still prioritized over cost, hence Opus 4.8, since a bad Meta-Heuristic propagates broadly to every future query that surfaces it. Louvain community detection — the previous clustering approach — is deferred as a heuristic-grouping optimization for when cross-dataset volume justifies it (MVP Scope, V2 Roadmap).
  - **Extraction interventions (R17):** `extract`-type interventions call Claude Opus 4.8 with the target document supplied via the Files API (PDF input) and `output_config.format` (structured outputs) constraining the response to the target field's expected type — never freeform text — so an extraction result's type/shape can't deviate from the declared schema. This is a schema guarantee, not a correctness guarantee (see R17) — the model can still return a well-typed but wrong value, which is what the confidence score and HITL threshold (R18) exist to catch.
  - **Exported/preview agent (R21):** `claude-sonnet-5` by default — the best speed/intelligence balance in the Sonnet tier for a conversational, low-latency chat surface (vs. Opus 4.8's higher latency and cost, which is justified for the analytical Phase 1/2 work but not for interactive chat). Connects to the arborette MCP Server's public, token-authorized endpoint via Claude's native MCP connector (`mcp_servers` + an `mcp_toolset` tool entry, beta header `mcp-client-2025-11-20`) rather than a hand-written tool-use loop — Anthropic's infrastructure handles the MCP round-trip server-side (which is why the endpoint must be public, not in-network), so the agent needs no custom tool schemas or dispatch code for `get_optimized_heuristics` or `trace_causal_chain`. Because the connector call is made by whichever backend holds the API key (the Orchestrator for preview, R23; a vendored equivalent for export, R24) and not by the browser, the browser/client never sees the Anthropic API key.
- **Graph database:** Neo4j (Cypher) for the MVP, chosen over Amazon Neptune specifically because Neptune has no faithful local-Docker equivalent (its Gremlin-Server/TinkerGraph local shim diverges from real Neptune behavior), which would break the docker-compose-locally / AWS-in-prod parity requirement. Neo4j runs identically in Docker locally and self-hosted on AWS. All graph access — from the Orchestrator, the MCP Server, and the Sleep-Cycle Worker alike — goes through a single repository interface, so a later migration to Amazon Neptune (the intended long-term target) is a swap behind that interface rather than a rewrite across three services.
- **Sandbox query engine:** DuckDB, embedded in the Sandbox Execution service, to run read-only SQL queries and aggregations directly over CSV/Parquet file data (R6). The LLM proposes intervention parameters (e.g. a filter, threshold, or aggregation change) via structured outputs; the Sandbox Execution service compiles those parameters into the corresponding DuckDB query rather than letting the LLM generate SQL freely, keeping trial execution deterministic and injection-safe.
- **File storage:** uploaded files are written to an object store — S3 in AWS production, a MinIO container in local docker-compose (S3-API-compatible, so the same client code runs unchanged) — referenced by object key/path stored in the goal registry. This gives the stateless Sandbox Execution service and the Orchestrator a durable, shared location for file-based data sources without relying on local disk on either service.
- **Embeddings & vector search:** PostgreSQL with the `pgvector` extension stores `Meta-Heuristic` embeddings for `get_optimized_heuristics`'s semantic-similarity matching (R12). Embedding generation sits behind a pluggable `EmbeddingProvider` interface: the MVP default is a local embedding sidecar (e.g. Ollama serving an open-source embedding model such as `nomic-embed-text` over HTTP — avoids embedding a model runtime directly into the Go binary), configurable to swap to a cloud embeddings provider (e.g. Voyage AI, Anthropic's recommended embeddings partner) in production — Anthropic's API does not offer an embeddings endpoint itself. A provider swap is **not** a live config toggle: different providers produce different-dimension, non-comparable vectors, so switching requires re-embedding every stored `Meta-Heuristic` and matching the `pgvector` column's fixed dimension to the new provider.
- **Goal registry:** the same PostgreSQL instance holds a table for registered goals — `optimization_function_id`, the natural-language goal text, the structured Evaluation Matrix, and the data-source object key/reference — so the Orchestrator can look up this state when a later, separate call triggers Phase 1 (R1, R5).
- **Audit trail:** the same PostgreSQL instance holds a single append-only audit table (inserts only, no updates or deletes) recording actor identity, timestamp, and action for every intervention, outcome, heuristic-injection, HITL-verification-resolution, and hypothesis-loop-branch-failure event (R13/R14). Only the Orchestrator holds credentials to this table; other services (e.g. the Sleep-Cycle Worker) submit audit records through the Orchestrator's internal audit-write API rather than writing directly.
- **MCP:** `github.com/modelcontextprotocol/go-sdk` — the official, actively maintained (with Google) Go MCP SDK.
- **Frontend:** React + TypeScript + Next.js.
- **Local orchestration:** Docker Compose.
- **Production orchestration:** AWS ECS/Fargate (always-on services) and AWS Batch on Fargate (the Sleep-Cycle job).

### Data Model

Carried forward from the concept spec:

**Nodes**
- `State` — snapshot/telemetry representing a point in time.
- `Intervention` — the reified middle node of a triplet. In V1 it is always **observational** (nothing is physically executed); its existing `type` field is `query` (a read-only data-segment / filter definition, R6) or `extract` (a document-extraction task, R17). MCTS-discovered macro-segments (R9) are `type: query` `Intervention` nodes whose parameters are the conjoined filter, additionally flagged MCTS-derived so they are distinguishable from Phase 1 single-feature segments; each takes a **deterministic id** (goal id + canonicalized conjoined filter) so re-runs MERGE idempotently rather than duplicating (R9), and is written as part of a **full `State→Intervention→Outcome` triplet** (its `State` being the parent/baseline segment) so it appears in `trace_causal_chain` (R9). A physically-executed action — with execution metadata and confidence bounds — is a new `type` value reserved for V2, written together with `epistemic_source: interventional` (R25, V2 Roadmap); neither ships in the MVP.
- `Outcome` — measured delta from an intervention, evaluated against the analyst's Evaluation Matrix. Carries a `verification_status` (`verified` for every `query`-type outcome, always — R7; for `extract`-type outcomes: `unverified` by default, or `confirmed` / `corrected` / `rejected` once HITL-resolved — R18). **This field, not the confidence weight, is what gates Sleep Cycle search (R9)** — the `PRODUCED`-edge confidence (see Edges, below) is the model's self-reported score and is never treated as proof of verification, so a model confidently self-reporting 1.0 cannot bypass HITL review. For an `extract`-type outcome, also carries a provenance locator (source document page number and character span, computed by deterministic post-hoc text search — not requested from the model, since Citations and structured outputs are API-incompatible, R17 — nullable if no exact match is found, and **recomputed against the new value (or nulled, falling back to the full-page view) on an HITL correction**, since the original locator no longer necessarily matches a corrected value) pinning the extracted value to the exact source excerpt it came from.
- `Meta-Heuristic` — semantic abstraction produced during the Sleep Cycle; carries an embedding vector (stored in PostgreSQL/`pgvector`, keyed by the Neo4j node ID) alongside its semantic definition, used by `get_optimized_heuristics` for similarity matching.

**Edges**
- `PRE_CONDITION_FOR` (`State` → `Intervention`)
- `PRODUCED` (`Intervention` → `Outcome`), carrying effect size, a confidence weight (0.0–1.0), and an `epistemic_source` discriminator (R25). In V1 `epistemic_source` is always `observational` — the edge records a measured correlation, not causation (R7); the `interventional` value (V2's do-calculus edges) is reserved, and consumers must treat a missing `epistemic_source` as `observational` (R25). Confidence is fixed at 1.0 for `query`-type triplets (R7, always the exactly-measured correlation); for `extract`-type triplets it is the model's self-reported extraction confidence, set to 1.0 on HITL confirm/correct (R18). This weight is a display/routing signal (R18's threshold, R20's histogram) — it is **not** the Sleep-Cycle search gate; see `Outcome.verification_status` (above) for what Sleep Cycle discovery (R9) actually checks.
- `ABSTRACTED_FROM` (`Meta-Heuristic` → `Intervention`/`State`/`Outcome`)

**Neo4j/pgvector write ordering (R10):** creating a `Meta-Heuristic` writes to two stores. Neo4j is the source of truth — the node, its `ABSTRACTED_FROM` edges, and an `embedding_pending: true` flag are written together in one Neo4j write (not set reactively after a failure — this closes the crash window between the two stores' writes). Only after the Sleep-Cycle Worker successfully writes the embedding to `pgvector` is `embedding_pending` cleared to `false`. An abstraction counts as fully done only once its `Meta-Heuristic` node has `embedding_pending: false`; the next Sleep Cycle run retries embedding generation for any node still flagged `embedding_pending: true` before processing new macro-segments — including one left flagged by a mid-write crash — so a heuristic is never silently unsearchable and `pgvector` never references a nonexistent node.

**Goal registry (R1/R5):** a PostgreSQL table holding `optimization_function_id`, the natural-language goal, the structured Evaluation Matrix, and the wired data source's object-store reference — the state a later, separate Phase 1 trigger call looks up.

**Audit trail (R13/R14):** a single append-only PostgreSQL table (not part of the mutable graph), recording actor identity, timestamp, and action for every intervention, outcome, heuristic-injection, HITL-verification-resolution, and hypothesis-loop-branch-failure event — kept distinct from the graph so it can't be altered by graph writes and stays simple to reason about for compliance review. Only the Orchestrator holds credentials to this table; other services submit records through its audit-write API.

**HITL verification queue (R18/R19):** a PostgreSQL table holding pending and resolved verification requests, each referencing the `Outcome` node it verifies (by Neo4j node ID), the extracted value and its provenance locator shown to the analyst, the `PRODUCED`-edge confidence weight at queue time, and its resolution (confirmed / corrected-with-new-value / rejected, plus resolving analyst and timestamp). A resolution writes the same value to the `Outcome`'s `verification_status` (`confirmed` / `corrected` / `rejected`) — the field Sleep Cycle search (R9) actually checks, distinct from the confidence weight. Queue entries aren't limited to below-threshold outcomes: the verification interface also lets the analyst pull up and resolve any at-or-above-threshold `extract` outcome on demand, since those otherwise have no path to `verification_status: confirmed` and would never become eligible for Sleep-Cycle search (R18). The goal registry (R1) carries a per-goal confidence threshold (default provided, analyst-overridable at goal-submission time) and an epoch-blocking mode flag (`speculative` default per R19, or `blocking`) that the Orchestrator reads when deciding whether depth-level advancement waits on pending verifications for that goal.

### Key Flows

1. **Goal intake:** analyst submits NL goal + data source via `submit_analyst_goal` → uploaded file (if any) is written to the object store → LLM produces an initial Evaluation Matrix (targets/constraints, from goal text alone) → Orchestrator calls the Sandbox Execution service to introspect the file's schema (tabular columns) or candidate extractable fields (documents, R16) and bind the Matrix's targets to concrete columns/fields → goal, the now-field-bound Evaluation Matrix, and data-source reference are written to the goal registry → `optimization_function_id` returned. This step only registers the goal; it does not start Phase 1.
2. **Hypothesis loop (Phase 1):** analyst calls the trigger-loop endpoint for an `optimization_function_id` → Orchestrator looks up the goal registry for the Evaluation Matrix and data-source reference → LLM proposes an intervention tree (system-default breadth/depth) → Sandbox Execution service reads the file from the object store, compiles each candidate into either a DuckDB `query` or, for a document data source, an `extract` call against Claude with structured outputs (R17), and runs it → Outcome (plus, for `extract`, a confidence score) measured against the Evaluation Matrix → observational triplet (`epistemic_source: observational`, R25) written to Neo4j → below-threshold `extract` outcomes are queued to the HITL verification table (R18) → progress and the live confidence-bin distribution (R20) streamed to the web UI over SSE (the loop itself runs server-side independent of that connection, so a drop interrupts only the live view — the analyst can reconnect or check the resulting triplets afterward) → once a depth level's candidates finish, the loop proceeds to prune and propose the next depth immediately by default (R19, `speculative` mode) rather than waiting on that level's queued verifications, or waits on them first if the goal is configured for `blocking` mode → loop continues to system-default stopping condition. If a sandbox execution or LLM call fails partway through, the loop aborts that branch, records the failure via the audit-write API, and continues evaluating sibling branches rather than failing the whole run. Re-triggering the loop for a goal that already has accumulated triplets appends new triplets rather than replacing or deduplicating prior runs — intentional, since the Sleep Cycle's MCTS searches across all of a dataset's accumulated history (R9).
3. **HITL verification (R18):** analyst opens the verification interface in the web UI → Orchestrator returns pending queue entries for the goal (extracted value + provenance locator, so the UI can render the source excerpt) — the analyst can also pull up any at-or-above-threshold outcome on demand, not just queued ones → analyst confirms, corrects, or rejects each → Orchestrator sets the referenced `Outcome`'s `verification_status` to `confirmed`/`corrected`/`rejected`, updates the `PRODUCED`-edge confidence to 1.0 (confirm/correct), and on a correction updates the extracted value and recomputes the provenance locator against it (or nulls it, same fallback as initial extraction) → writes the resolution to the HITL queue table, records the event via the audit-write API, and pushes an updated confidence-bin distribution (R20) over the same SSE stream if the goal's run is still active, since a resolution can change an existing triplet's confidence outside the normal new-triplet update path. Resolutions that land after their tree depth has already been pruned past do not replay the loop — they update the graph in place, and the next Sleep Cycle run (R9) is what makes a newly-confirmed/corrected outcome eligible for Sleep-Cycle search for the first time (rejected outcomes never become eligible).
4. **Agent preview (R23):** analyst clicks "preview agent" from the web UI for a goal with accumulated triplets/heuristics → web front-end opens a streamed chat session against the Orchestrator's chat endpoint → the Orchestrator calls the Claude Messages API (`claude-sonnet-5`, R21) with the native MCP connector pointed at the MCP Server's public, token-authorized endpoint (R12), scoped to the two read-only tools → the agent decides per-turn whether to call `get_optimized_heuristics` or `trace_causal_chain` based on the conversation, streamed back through the Orchestrator to the browser and rendered in the default iMessage-style chat UI (R22) — the browser never holds the Anthropic API key and never talks to the MCP Server directly. No export/packaging step is required for preview. Production export into a self-contained bundle (R24) is deferred past the MVP (see MVP Scope).
5. **Sleep cycle (Phase 2):** analyst calls the trigger-sleep-cycle endpoint → **MCTS** searches the space of segment conjunctions over the dataset's accumulated, **verified** observational findings only (R9 — `query`-type findings and HITL-confirmed `extract`-type findings; unverified and rejected `extract` outcomes are skipped), measuring each candidate macro-segment empirically via the Sandbox Execution service's `query` path and writing each materially-better macro-segment back as a derived observational triplet → if the search is degenerate (no macro-segment beats the best single segment, or too few findings to combine), the run records that no `Meta-Heuristic` was abstracted and stops; otherwise the Sleep-Cycle Worker abstracts each surfaced macro-segment path via a synchronous Claude API call — stripping domain payloads to a universal ontology (R10) — persisting per-abstraction progress so a restart resumes rather than reprocessing and recording a per-macro-segment failure (rather than aborting the run) if one call errors → each successful result is written to Neo4j as a `Meta-Heuristic` node with `ABSTRACTED_FROM` edges and `embedding_pending: true` in one write, then embedded and written to PostgreSQL/`pgvector`, after which `embedding_pending` is cleared to `false` (a node still flagged `embedding_pending: true` — whether from a failed embedding write or a mid-write crash — is retried on the next run rather than treated as done) → heuristic-injection events are reported to the Orchestrator's audit-write API.
6. **MCP query:** a downstream agent calls `get_optimized_heuristics` with an operational-state string → MCP server embeds the string via the configured `EmbeddingProvider` and runs a similarity search against PostgreSQL/`pgvector` → matching `Meta-Heuristic` node IDs are fetched from Neo4j and returned as semantic definitions; `trace_causal_chain` walks `ABSTRACTED_FROM` back to the underlying triplets for audit. A `submit_analyst_goal` call arriving over MCP is proxied to the Orchestrator's REST endpoint rather than handled locally; MCP exposes no way to trigger either phase in the MVP (intentional — see R12).

## MVP Scope

**In scope:** single analyst, single dataset (file upload or on-disk file, persisted in an S3-compatible object store), explicit REST endpoints for goal registration and manually triggering each phase (with goal/Evaluation-Matrix state persisted in a PostgreSQL goal registry between the two), DuckDB-backed read-only sandboxed trial execution, Neo4j graph storage behind a repository interface shared by all three graph-touching services, PostgreSQL for the append-only audit trail (written only by the Orchestrator, via an internal API for other services) and `pgvector`-based Meta-Heuristic embeddings (behind a pluggable `EmbeddingProvider`, local sidecar by default), MCTS-based Sleep-Cycle discovery of high-value macro-segments with empirically-measured (Sandbox-executed) rollouts (R9), ontological naming of `Meta-Heuristic`s into a domain-agnostic structural vocabulary (R10), the additive `epistemic_source` provenance discriminator on `PRODUCED` edges that keeps V2 additive (R25), synchronous (non-Batches) Phase 2 abstraction calls for demo-ability, the three MCP tools, a stub analyst identity on every audit record, and a React/Next.js web UI covering goal submission, live (SSE-streamed) hypothesis-loop progress, and heuristic browsing.

PDF-based document data sources and `extract`-type interventions (R16/R17), the HITL verification queue with configurable confidence threshold and configurable speculative/blocking epoch mode (R18/R19), the live confidence-bin distribution in the web UI (R20), and the agent preview tab backed by the native MCP connector and default iMessage-style chat UI (R21/R22/R23) are all in scope for the MVP — they extend the single-analyst/single-dataset demo rather than requiring the full multi-analyst vision.

**Explicitly deferred:** cross-dataset/cross-department discovery, the cross-dataset *reuse* of ontological `Meta-Heuristic`s to bootstrap a new dataset (R10's "Cold Start" path — the MVP produces ontology-named heuristics but does not consume them across datasets), Louvain community detection as a heuristic-grouping optimization (superseded by MCTS for the single-dataset MVP; revisited when cross-dataset volume justifies grouping — R9), the **entire V2 dual-engine layer** (Control Plane Router, physically-executed sandboxed interventions, do-calculus `PRODUCED_EFFECT`/`epistemic_source: interventional` edges, A\*-guided path selection — see V2 Roadmap; R25 keeps V1 forward-compatible with it but ships none of it), continuous/background (non-manual) triggering of either phase, a Spark connector or STS-token-based data-lake access (the pluggable interface is built, but only the file-based implementation ships), real authentication/SSO and per-division access control, the Amazon Neptune migration, and the Message Batches API for Phase 2 (a documented future cost optimization once real multi-dataset volume justifies its multi-hour turnaround). Non-PDF multi-modal document sources (images, audio, video) beyond the file-based/document-based `DataSource` split are deferred — the `extract` path and structured-output pattern are designed to extend to them later without an interface change, but no additional implementation ships in the MVP. Production agent export as a self-contained bundle (R24) is deferred — the preview tab (R23) is the MVP's agent-facing deliverable, built on the same native-MCP-connector architecture so export lands as additive packaging work.

## V2 Roadmap (Forward-Compatibility, Deferred)

This section records the intended V2 direction so V1's decisions — chiefly R25's `epistemic_source` discriminator and the reserved physically-executed `Intervention` `type` value — stay coherent with it. **None of this ships in the MVP.** It exists to guarantee V1 is additively upgradeable, not to scope current work.

V2 upgrades the architecture from a purely observational engine into an active layer that can *prove* causality by physically executing interventions in isolated sandboxes.

- **Control Plane Router.** A routing agent intercepts analyst input and directs each evaluation to one of two async tracks by intent:
  - **Engine A — Observational SQL (fast track):** exactly V1, retained unchanged — rapid subgroup discovery populating the graph with `observational` correlation edges.
  - **Engine B — State-Search Experimental Sandbox (verification track):** executes isolated physical interventions (e.g. code/config changes) in ephemeral containers to prove causality — answering "does enforcing this *cause* the lift, or is it merely correlated?" It uses **A\*** search, guided by `Meta-Heuristic` nodes as the heuristic function $h(s)$, to select the highest-probability path to test *before* paying for an expensive sandbox spin-up.
- **Graph impact.** Engine B writes `PRODUCED` edges with `epistemic_source: interventional` (the do-calculus, empirically-validated causal edges the revision calls `PRODUCED_EFFECT`) and `Intervention` nodes carrying a new physically-executed `type` value. Because V1 already tags every edge `observational` and reserves these values (R25), this is an additive write path, not a schema migration.
- **V2 Sleep Cycle.** The Phase 2 MCTS is extended to traverse the now-mixed graph: it explores the dense web of `observational` edges cheaply, but its scoring function applies a large multiplier to any path validated by an `interventional` edge, so abstracted `Meta-Heuristic`s are anchored in proven causality wherever it exists rather than correlation alone.
- **How V1 stays additive.** The `epistemic_source` discriminator (R25), the reserved physically-executed `Intervention` `type` value, the pluggable `DataSource`/repository interfaces, and the "consumers treat missing `epistemic_source` as observational" rule mean V2 lands as new writers + a router + an extended MCTS scoring function — with no rewrite of V1's observational path.

## Open Questions

- Exact hypothesis-tree default parameters (breadth, depth, stopping condition) — left to implementation-time tuning against real sample data rather than fixed here.
- Exact MCTS tuning for the Sleep Cycle (R9): rollout budget, UCT exploration constant, maximum macro-segment order (conjunction depth), and the "materially better than the best single segment" threshold that gates both write-back and the degenerate-run bail-out — left to implementation-time tuning. Also a scaling note, not a blocker for the single-dataset MVP: because rollouts are empirically measured through the Sandbox Execution service rather than estimated, MCTS depth trades directly against sandbox query volume.
- Source of the universal ontology used by ontological naming (R10): whether the abstraction prompt is handed a fixed controlled vocabulary (consistent structural terms across all heuristics, but a curation burden) or lets the model generate structural terms free-form per heuristic (zero curation, but risks two heuristics naming the same structure differently, weakening `get_optimized_heuristics` similarity matching). Free-form model-generated is the simplest MVP default; a controlled vocabulary is a future consistency improvement — left to implementation-time tuning.
- Timing/trigger for the Neo4j → Amazon Neptune migration — no action needed now given the abstraction layer, but not yet scheduled.
- Full authentication, SSO, and per-department access-control design for the post-MVP multi-analyst, multi-division system.
- Exact default confidence threshold for HITL queuing (R18) — a starting default of 0.8 is reasonable but should be tuned at implementation time against real extraction-accuracy data rather than fixed here. **Known risk:** this confidence is the model's self-report from structured outputs, which is not necessarily well-calibrated to actual extraction accuracy. This risk is now bounded rather than fully accepted: per R9, no `extract` outcome — regardless of its self-reported confidence — becomes eligible for Sleep-Cycle search without HITL confirmation, so a miscalibrated confidence can at most under- or over-populate the review queue's *priority* (auto-queuing something that didn't strictly need it, or requiring the analyst to proactively pull up something that did), not let a wrong extraction silently become a served `Meta-Heuristic`. The remaining tuning question is purely about queue ergonomics — how often the default threshold makes the analyst review results that turn out fine, versus makes them go looking for ones that didn't auto-queue.
- Exact packaging format for production agent export (R24) — container image, downloadable zip with a minimal runtime, or something else — left open since R24 itself is deferred past the MVP; the preview tab's native-MCP-connector architecture is designed so this is additive packaging work whenever it's picked up.
- **Known gap:** retiring or versioning an already-abstracted `Meta-Heuristic` when its supporting evidence is later corrected (R18) is not solved by this MVP. R18/R19 exclude a *rejected* outcome from future Sleep-Cycle search (R9) and let a *corrected* outcome's new value feed the next Sleep Cycle run as fresh evidence, but neither mechanism retracts or updates a `Meta-Heuristic` that was already abstracted from the old (now-corrected) triplet before the correction landed — that heuristic keeps serving via `get_optimized_heuristics` (R12) until a full invalidation/versioning design is built post-MVP. Flagged explicitly here rather than left implicit, since a bad heuristic propagating to every future query is exactly the failure mode R10's Design already calls out as costly.
