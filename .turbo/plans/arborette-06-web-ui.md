# Plan: Web UI

## Context

This is the analyst-facing surface, and it's the one place in the system where polish is explicitly a requirement, not a nice-to-have — demos of arborette shouldn't get derailed by rough UX. The web UI is a separate React/Next.js deployable that talks only to the Orchestrator's REST API (including its heuristic-browsing endpoints), covering the full analyst workflow: registering a goal, watching the hypothesis loop run live, and browsing the heuristics it eventually produces.

## Pattern Survey

### Analogous Features

- **No existing frontend/TS/Node/HTML/CSS code exists anywhere in the repo.** There is no `package.json`, `node_modules`, `*.ts(x)`, `*.js(x)`, `*.html`, or `*.css`. This is a pure Go monorepo — the web UI is genuinely greenfield, so the React/Next.js internals have no in-repo precedent and should follow external Next.js best practice. The `frontend-design` skill applies given the explicit polish requirement.
- `internal/mcpserver/orchestratorclient.go:56` — `SubmitGoal(ctx, goal, importPath)` is the closest analog to the BFF proxy the web UI needs: it builds the **exact multipart form** the orchestrator expects (`goal` + `import_path` fields via `mime/multipart`), POSTs to `baseURL+"/goals"`, treats non-201 as error, and decodes `{"optimization_function_id":...}`. It distinguishes analyst-safe orchestrator `{"error":...}` bodies (surface verbatim) from transport errors (mask) — `orchestratorclient.go:81-97`. The proxy should preserve this surface-orchestrator-error / mask-transport-error split.
- `cmd/mcpserver/main.go:58-60` — the other consumer-facing HTTP edge: wraps a handler with `service.RunHTTPServer`; bearer-token middleware wraps it externally. No auth/CORS in-process — consistent with the orchestrator, which is why the web app must be a same-origin proxy.
- Each Go service is an independently-deployable unit: `cmd/<service>/main.go` + `cmd/<service>/Dockerfile`, wired in `docker-compose.yml`. The web UI follows this deployable-unit shape as a new top-level dir (Node-based, not under `cmd/`).

### Reusable Utilities (exact wire contracts the client must match)

Routes registered at `internal/orchestrator/server.go:120-130`. All JSON responses set `Content-Type: application/json`; errors are `{"error":"<msg>"}` via `writeErr` (`server.go:148-162`).

- **`POST /goals`** (`submit.go:39`) — `multipart/form-data`. Fields: `goal` (required, trimmed, non-empty → else 400 `"goal is required"`); **exactly one** data source: `file` (file part) OR `import_path` (string). Both → 400 `"provide either a file upload or import_path, not both"`; neither → 400 `"a data source (file upload or import_path) is required"`; `import_path` escaping the mount → 400; on-disk import unconfigured → 400; missing on-disk file → 404 `"data source not found"`. Body cap **512 MiB** (`maxUploadBytes`, `submit.go:24`), oversized/malformed → 400. Success → **201 Created**, body `{"optimization_function_id":"<uuid>"}` (`submit.go:97`). Matrix-generation failure → **502** `"evaluation matrix generation failed"` (`submit.go:61`). This call is **synchronous and slow** (inline Claude call) — the proxy must allow a long timeout; MCP uses 2 minutes (`orchestratorclient.go:21`).
- **`POST /goals/{id}/hypothesis-loop`** (`hypothesis.go:38`) — no body. Missing goal → **404** `"goal not found"` (`lookupGoal`, `server.go:134`). Success → **202 Accepted**, body `{"optimization_function_id":"<id>"}` (`hypothesis.go:48`). Loop runs on a background context and returns immediately; an SSE disconnect never aborts it.
- **`GET /goals/{id}/stream`** (`stream.go:14`) — SSE. Headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. Frames are `data: <json>\n\n` only — **no `event:` line, no `id:` line**. The client discriminates on the JSON payload's `type` field, not the SSE event type. Each frame's JSON is an `Event` (`hub.go:11`): `{"type":"<string>","payload":{...}}` (`payload` omitted when empty). On connect the server **replays a bounded history buffer** (64 events, `hub.go:7`) then goes live, so a client subscribing after the trigger — or reconnecting after a drop — still sees the run start. The server closes the stream when the run completes. Event schemas (`hypothesis.go`):
  - `type:"triplet"` → `payload: {state_id, intervention_id, outcome_id, baseline (number), value (number), effect_size (number = value-baseline)}` (`hypothesis.go:221-228`)
  - `type:"branch_failure"` → `payload: {error: "<string>"}` (`hypothesis.go:242`); siblings continue, so this is non-terminal.
  - `type:"loop_complete"` → **no payload** (`hypothesis.go:56`); terminal event, published just before the hub closes the stream.
- **`GET /heuristics/search?q=&k=`** (`heuristics.go:53`) — `q` required (empty → 400 `"q is required"`); `k` optional, default **10**, clamped to max **100** (`heuristics.go:13-14,59-67`); non-positive/malformed `k` silently ignored. Success → **200**, body `[{"id","definition"}]` (always a JSON array, never null).
- **`GET /heuristics/{id}/trace`** (`heuristics.go:84`) — Success → **200**, body array of triplet DTOs (`heuristics.go:45-49`): `[{"state":{"id","properties":{}}, "intervention":{"id","type","properties":{}}, "outcome":{"id","verification_status","value":{}}}]`. `properties`/`value` are arbitrary JSON objects. **The trace DTO is richer than the SSE `triplet` payload** — different shapes for the same concept; the live view has only IDs + numbers, the trace view has full node properties.
- **`POST /goals/{id}/sleep-cycle`** (`sleepcycle.go:11`) — Phase 2 trigger, no body. Missing goal → **404**; launch failure → **500** `"failed to launch sleep cycle"`; success → **202** `{"optimization_function_id":"<id>"}` (`sleepcycle.go:33`). **Fire-and-forget** — it launches the Sleep-Cycle job and returns; there is no completion signal, so Meta-Heuristics appear asynchronously and the analyst re-queries the heuristic browser afterward.
- **Do not proxy for the UI**: `POST /internal/audit` (`server.go:128`) is a service-to-service endpoint, out of R15 scope.
- `internal/objectstore/client.go:50` `NewKey(parts...)` joins with `/`; ingestion keys are `datasources/<uuid>/<basename>`. `import_path` resolves relative to `ARBORETTE_LOCAL_IMPORT_DIR` (default `/import`, compose-mounted read-only from `./local-import`, `docker-compose.yml:137`); `..`/absolute escapes are rejected server-side. **There is no directory-listing endpoint** — on-disk "selection" is a relative-path text field, not a browse dialog.

### Convention Anchors

- **Config / ports**: env-based via `internal/config/config.go`. Ports pre-allocated: **8080 orchestrator, 8081 sandbox, 8082 mcpserver** (`config.go:198-211`) → the web UI takes **8083**. `ORCHESTRATOR_URL` is **already a defined env var** (`config.go:211`, `.env.example:52`, default `http://orchestrator:8080`) used by the MCP server — the BFF reuses this exact variable name/value.
- **Dockerfile**: multi-stage, one per deployable; Go flavors are `golang:1.24` build + `gcr.io/distroless/*-debian12` runtime (`cmd/orchestrator/Dockerfile`, `cmd/sandbox/Dockerfile`). A Node/Next.js image is a new pattern with no precedent; keep the multi-stage + minimal/distroless-family runtime spirit.
- **docker-compose service block** (orchestrator block `docker-compose.yml:127-150` is the model): `build: {context, dockerfile}`, `env_file: [.env]`, `ports`, `depends_on`. The orchestrator has **no healthcheck**, so a dependent gates on `condition: service_started` (same as MCP, `docker-compose.yml:197-200`). The web UI needs only the orchestrator — no DB/neo4j/minio/ollama deps. The `x-app-environment` anchor injects in-network infra hostnames and wins over `env_file`; the web service doesn't need infra hostnames but should pin `ORCHESTRATOR_URL`/`PORT` via `environment:` so a host-override in `.env` (e.g. the `make test` localhost overrides) never leaks into the container.
- **Env**: `.env` is gitignored (`.gitignore:2`); `.env.example` is the committed template. Add a web section reusing `ORCHESTRATOR_URL` and adding a `WEBUI_PORT` (8083) entry, following the section-comment style (`.env.example:41-52`).
- **Makefile**: targets `build`/`test`/`up`/`down`/`migrate-up/down`; `up` = `docker compose up -d --build`. No frontend build/lint/test target exists yet.
- **Toolchain discipline (`AGENTS.md`)**: strict Go dependency pinning; no Node/npm discipline documented. The analogous move is to add a short Node/Next.js version + lockfile note to `AGENTS.md`.

### Proposed Alignment

There are no analogous frontend features to mirror — this is the repo's first Node/Next.js deployable, so the JS/TS/React internals follow external Next.js best practice with the `frontend-design` skill for polish. Where the app touches the monorepo's seams it conforms tightly: (1) the BFF proxy preserves `orchestratorclient.go`'s surface-orchestrator-error / mask-transport-error discipline; (2) it matches every wire contract above exactly — especially the SSE quirk that events are discriminated by the JSON `type` field (no `event:` line) and that `loop_complete` is the terminal, payload-less frame; (3) compose/Dockerfile/env additions copy the orchestrator service block, take port 8083, reuse `ORCHESTRATOR_URL`, and gate `depends_on` on `service_started`.

**Contract-driven constraint (note, not a blocker):** the SSE `triplet` payload carries only IDs and numeric baseline/value/effect_size — no parent→child linkage and no intervention filter/definition detail (`hypothesis.go:221-228`). A true nested hypothesis *tree* is therefore not reconstructable from the live stream alone. The live view renders a **progressively-updating causal-triplet feed** (each triplet as a baseline→value effect-size bar, plus branch-failure notices, terminating on `loop_complete`), which satisfies R15's "live or progressively-updating view of the hypothesis tree and resulting causal triplets." Full node properties are only available post-abstraction via the trace endpoint. This is a fixed consequence of the already-implemented orchestrator contract (shell 02, `status: done`) and is honored here rather than forcing an upstream schema change.

**Downstream seam (advisory):** the next web-UI shell (arborette-10, which adds the R8 confidence-bin histogram, HITL verification, and an agent-chat preview) builds directly on this app. This plan gives it a stable seam — a shared design system, a typed orchestrator client + BFF-proxy pattern, and an extensible live-view route that already consumes the SSE stream — so shell 10 adds components/routes rather than restructuring the app. One data gap belongs upstream, not here: the SSE `triplet` payload carries no `PRODUCED`-edge confidence weight, which R8's histogram needs; sourcing that confidence is a shell-02/08 contract concern, and this plan neither blocks on it nor pre-solves it.

## Implementation Steps

1. **Scaffold the Next.js deployable**
   - Create a new top-level `web/` directory: **Next.js ≥15** (App Router, TypeScript, React), `package.json` with a committed lockfile, `next.config.ts`, `tsconfig.json`, Tailwind (or equivalent) for styling, and `.gitignore` entries for `web/node_modules`, `web/.next`. Set `output: 'standalone'` in `next.config.ts` for a minimal Docker runtime. Pin Next ≥15 deliberately: the TypeScript `next.config.ts` this plan uses requires Next ≥15, and Next 15 changed GET Route Handlers to be **uncached by default** — both assumptions silently break on Next 14.
   - Establish the design system up front (the `frontend-design` skill governs this): a small set of shared primitives (layout shell, cards, buttons, form controls, status badges) so the three screens read as one polished product, not three ad-hoc pages.

2. **BFF proxy to the orchestrator**
   - Proxy the browser's same-origin `/api/orchestrator/*` calls to `${ORCHESTRATOR_URL}/*` server-side so the Orchestrator's missing CORS is never hit. Implement as Next.js Route Handlers under `web/app/api/orchestrator/` (Node runtime) that forward method, path, query, headers, and body to `ORCHESTRATOR_URL`, rather than `next.config` rewrites, because three of the paths need explicit handling:
     - **`POST /goals`** — forward the raw `multipart/form-data` body and `Content-Type` unchanged (stream the request body through; do not let Next buffer/parse it, to preserve the 512 MiB path). When forwarding the Route Handler's `request.body` (a `ReadableStream`) into `fetch(upstream, { method, body: request.body, … })`, **pass `duplex: 'half'` on the `fetch` init** — Node/undici throws `RequestInit: duplex option is required when sending a body` without it, failing every upload. Use a long upstream timeout (≥2 min) to cover the inline Claude call. Pass the orchestrator's status + `{error}` body straight back to the client on non-201, mask only transport failures — mirroring `orchestratorclient.go:81-97`.
     - **`GET /goals/{id}/stream`** — fetch upstream and return `new Response(upstream.body, { headers: text/event-stream, no-cache, keep-alive })` so the SSE frames stream through unbuffered. Disable any response buffering/caching on this route. **Disable undici's body-inactivity timeout on this upstream fetch**: Node `fetch`/undici defaults to `bodyTimeout: 300_000` (a 5-min gap-between-chunks timer), but the orchestrator's `loopTimeout` is 10 min (`hypothesis.go:23`) and it emits no heartbeat frames, so a long quiet stretch between triplets (e.g. a slow `ProposeInterventionTree` call) would otherwise abort the proxied stream mid-run. Pass a custom dispatcher with `bodyTimeout: 0` (via undici `Agent`) on the stream fetch. The client's reconnect + the 64-event replay buffer is a second line of defense, not a substitute.
     - The remaining JSON endpoints (`POST /goals/{id}/hypothesis-loop`, `POST /goals/{id}/sleep-cycle`, `GET /heuristics/search`, `GET /heuristics/{id}/trace`) pass through with status + body preserved.
   - On each proxy Route Handler, set the route-segment config `export const dynamic = 'force-dynamic'` (and `export const runtime = 'nodejs'`) so the pass-through and streaming routes are never statically cached or pre-rendered — required for the SSE stream and the live JSON endpoints regardless of the Next default, and explicit so the behavior doesn't hinge on the framework version.
   - Read `ORCHESTRATOR_URL` server-side only (never expose it to the client bundle).
   - Provide a typed client module (`web/lib/orchestrator.ts`) with functions and TypeScript types for every DTO above (`SubmitGoalResponse`, `TripletEvent`, `BranchFailureEvent`, `HeuristicMatch`, `TraceTriplet`, etc.), all calling the same-origin `/api/orchestrator/*` paths.

3. **Goal-submission form** (R15 acceptance 1)
   - A form (`web/app/(routes)/…` — e.g. the landing route) with an NL `goal` textarea and a data-source picker offering two mutually-exclusive modes: **file upload** (`<input type=file>` → `file` part) or **on-disk path** (a relative-path text field → `import_path`, with helper text that it resolves under the server's import mount). Client-side, enforce exactly-one-source so the "both"/"neither" 400s are avoided, but still surface the orchestrator's `{error}` verbatim if one slips through.
   - Submit as `multipart/form-data` to `/api/orchestrator/goals`; on 201 surface the returned `optimization_function_id` and route the analyst into the live view for that id. Show a clear pending state (the call is slow) and map known statuses to friendly messages (400 validation, 404 on-disk-missing, 502 matrix-generation-failed).

4. **Live hypothesis-loop view** (R15 acceptance 2)
   - A per-goal route (e.g. `web/app/goals/[id]/page.tsx`) with a "Run Phase 1" action that POSTs `/api/orchestrator/goals/{id}/hypothesis-loop` (202), then subscribes to `/api/orchestrator/goals/{id}/stream`.
   - Consume SSE with a `fetch` + `ReadableStream` reader (not `EventSource`) so the client controls termination on `loop_complete` and avoids `EventSource` auto-reconnect storms. Parse `data: <json>\n\n` frames, `JSON.parse` each, and discriminate on the frame's **top-level `type`** field — the frame is `{"type":"triplet","payload":{…}}` (`hub.go:11-14`), so dispatch on `event.type`, **not** `event.payload.type` (the inner `payload` object has no `type` key). Render `triplet` events as a progressively-updating feed of effect-size cards (baseline → value, signed `effect_size`), show `branch_failure` events as non-terminal inline warnings, and close the stream cleanly on `loop_complete`.
   - **Dropped-connection handling**: on reader error/EOF before `loop_complete`, show a "reconnecting" affordance and re-subscribe; the loop keeps running server-side and the 64-event replay buffer lets the reconnect catch up. Reflect the constraint noted in Proposed Alignment — this is a triplet feed, not a nested tree.
   - **Reload-after-completion / never-started handling (undefined at the contract level, so define it client-side)**: once a run completes, `Hub.Complete` deletes its `runState` (`hub.go:98-110`) and there is no endpoint to re-fetch a finished run's triplets. A fresh `GET /stream` for a completed *or* never-triggered id lazily creates an empty `runState` (`hub.go:37-44`), replays nothing, and then blocks indefinitely with zero events (`stream.go:32-44`) — the two cases are indistinguishable and `loop_complete` never re-fires. So the client must **not** treat an open, silent stream as "in progress" — but it must **not** over-correct either, because a freshly-triggered run is *also* silent throughout its startup: `runLoop` publishes nothing until the first triplet, and reaching it means introspect + a `ProposeInterventionTree` Claude call + baseline execute + first-candidate execute (`hypothesis.go:53-101`), realistically 5–15+ seconds. A blind "no event within a few seconds → not started" rule would flip the view to "not started" moments after the analyst clicks Run Phase 1. Resolve this with a **client-side per-id trigger record**: persist the run's lifecycle state keyed by id (e.g. `triggered` set when the client's `hypothesis-loop` POST returns 202, `completed` set on the first `loop_complete`, plus the received triplets). Then on a subscribe with an empty replay and no events, branch on that record: if the id is `triggered`-and-not-`completed`, **keep waiting / reconnecting** (a slow start, not an absent run); only when there is **no** local `triggered` record and the idle window elapses, resolve to the neutral "run finished or not yet started — trigger Phase 1 to (re)run" state rather than a perpetual spinner. Also define re-trigger semantics: POSTing `hypothesis-loop` again starts a **brand-new** run that appends duplicate triplets to the graph; surface that this re-runs rather than resumes, so the analyst isn't surprised.
   - After Phase 1 completes, expose a **"Run Sleep Cycle" (Phase 2) action** that POSTs `/api/orchestrator/goals/{id}/sleep-cycle` (202, fire-and-forget). This closes the demo loop — Phase 2 abstracts the run's triplets into Meta-Heuristics — so the heuristic browser (Step 5) has something to show. Surface that it's asynchronous with no completion event (heuristics appear on a later re-search), and map the 404/500 statuses to friendly messages.

5. **Heuristic browser** (R15 acceptance 3)
   - A route (e.g. `web/app/heuristics/page.tsx`) with a search box calling `/api/orchestrator/heuristics/search?q=&k=`, rendering the `[{id,definition}]` list. Guard the empty-`q` 400 client-side.
   - Clicking a result opens a drill-down detail (route or panel) calling `/api/orchestrator/heuristics/{id}/trace`, rendering the supporting causal chain: for each `TraceTriplet`, show `state.properties`, `intervention.type` + `intervention.properties`, and `outcome.verification_status` + `outcome.value` as readable evidence rows.

6. **Deployment wiring**
   - Add `web/Dockerfile`: multi-stage Node build (`node:22-*` builder running `npm ci` + `next build` with `output: 'standalone'`) → a minimal/distroless-family runtime image (e.g. `gcr.io/distroless/nodejs22-debian12`). Run the standalone server with **`node server.js`** (the `output: 'standalone'` build emits a self-contained `.next/standalone/server.js`; it deliberately omits the `next` CLI, so `next start` cannot run on a distroless runtime that has only `node`). The standalone output excludes static assets, so the runtime stage must **copy `.next/static` and `public` into the image** alongside `.next/standalone` or every JS/CSS asset 404s (fatal to the polish requirement). Set **`ENV HOSTNAME 0.0.0.0`** (the standalone `server.js` binds to `process.env.HOSTNAME`; without this it can bind to loopback and the compose `8083:8083` mapping is unreachable) and **`ENV PORT 8083`**.
   - Add a `web` service block to `docker-compose.yml` following the orchestrator block's env/ports/depends_on conventions, but with a **self-contained build context**: `build: {context: ./web, dockerfile: Dockerfile}`. Unlike the Go services (which need the repo-root context for the shared `go.mod`, hence their `context: .`), the web app is entirely under `web/`, so a `./web` context keeps the Dockerfile's `COPY` paths conventional (`COPY package*.json ./`, `COPY . .`) instead of root-relative (`COPY web/…`), which would otherwise be a silent build-failure trap. Add `env_file: [.env]`, `environment:` pinning `ORCHESTRATOR_URL: http://orchestrator:8080` and `PORT: "8083"`, `ports: ["8083:8083"]`, and `depends_on: {orchestrator: {condition: service_started}}`. Add a `web/.dockerignore` excluding `node_modules` and `.next` so local build artifacts don't bloat or poison the build context.
   - Add a web section to `.env.example` (reuse `ORCHESTRATOR_URL`, add `WEBUI_PORT=8083`), extend `.gitignore` for the Node artifacts, and add a short Node/Next.js pinning note to `AGENTS.md` to match the project's dependency-pinning ethos — concretely: **Next.js pinned to ≥15 (App Router)** on **Node 22**, with a committed lockfile (`package-lock.json`), calling out that Next 14 breaks the `next.config.ts` + uncached-GET-route assumptions. Optionally add `web-dev`/`web-build` Makefile targets.

## Verification

- **Build/typecheck/lint**: `cd web && npm ci && npm run build` succeeds (Next production build + TypeScript typecheck pass); `npm run lint` is clean.
- **Image + compose**: `make up` builds and starts the `web` service; `docker compose ps` shows it healthy/started and it comes up only after the orchestrator has started.
- **End-to-end smoke** (browser at `http://localhost:8083`, with a sample CSV in `./local-import` and a real `.env`):
  - Submit a goal via **file upload** → receive an `optimization_function_id` and land on the live view. Repeat via **on-disk path** (relative path under the import mount) → same result.
  - Trigger Phase 1 → causal-triplet cards stream in live with baseline/value/effect_size; the view terminates cleanly when `loop_complete` arrives.
  - Reload the live view mid-run → the replay buffer repaints the run so far, then live events resume (confirms graceful drop/reconnect and that the loop kept running server-side).
  - Reload the live view **after** `loop_complete` (and open a live view for a goal whose Phase 1 was never triggered) → within a few seconds the view resolves to the neutral "run finished or not yet started" state with a (re)run affordance, **not** a perpetual spinner; re-triggering Phase 1 starts a fresh run and the UI communicates that it re-runs rather than resumes.
  - Trigger the **Sleep Cycle (Phase 2)** action → 202; after the job produces Meta-Heuristics, the heuristic browser search returns `{id,definition}` rows.
  - Heuristic browser: a search returns `{id,definition}` rows; clicking one renders its trace evidence (state/intervention/outcome rows).
- **Edge cases to spot-check**: submitting with both a file and an `import_path`, or with neither, surfaces the orchestrator's 400 message verbatim; a non-existent on-disk path surfaces the 404 message; an empty search query is blocked client-side (no request) and, if forced, surfaces the `"q is required"` 400; a `branch_failure` event renders as a non-terminal warning without ending the stream.
