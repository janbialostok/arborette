# Objective Intake & Navigation

## Overview

Arborette's goal loop works but is not usable by a non-expert analyst. The objective prompt is rigid and unexplained: the evaluation matrix is generated from the goal text *alone*, blind to the dataset, so the analyst must phrase the goal such that its target field name and case exactly match a dataset column — otherwise the run fails at the root baseline with an opaque `sandbox /execute returned status 400` and zero triplets. Failures carry no intelligible reason. And once an analyst leaves the runner UI, a hypothesis run is unreachable without remembering its `optimization_function_id`.

This iteration makes the register → run → browse loop forgiving and navigable, and it does so before the subsequent shells build on these contracts. Three changes: (1) let Claude *fit* a loosely-phrased objective to the actual dataset schema — introspect first, resolve columns case-insensitively and semantically, and express the objective as a safe structured expression so boolean/categorical targets (e.g. "optimize for transported passengers" → maximize `avg(Transported = True)`) no longer fail; (2) surface *why* a run or registration failed in plain language, at both intake and run time; (3) add a persisted run-status model and a list view so analysts can return to previous and currently-running objectives by name, not by ID.

## Users

- **Analyst (primary)** — registers optimization goals against a dataset and reads the resulting causal knowledge. Range of sophistication; **some personas never inspect the dataset before registering a goal**, so the system must bridge intent to schema on their behalf and explain failures well enough to self-correct.

## Requirements

### Schema-Aware Objective Registration

- **R1.** When an analyst registers a goal against a **tabular** data source, the system shall introspect the source and generate the evaluation matrix with the dataset schema (columns and types) in context, resolving the objective to actual columns rather than to the analyst's verbatim phrasing. (Document sources keep the parent spec's matrix-from-text-then-bind ordering — see Downstream Compatibility.)
- **R2.** The system shall match the analyst's intent to columns **case-insensitively and semantically** — mapping intent to the right column even when the analyst's wording differs from the column name — so a persona who never inspected the dataset can still register a valid objective.
- **R3.** As an analyst, I want objectives that aren't just a bare numeric column so that goals like "maximize the rate of transported passengers" work.
  - Acceptance: the objective is `{ aggregation, value-expression, direction }`, **produced by matrix generation at intake** — the aggregation and the value expression are chosen when the matrix is fitted to the schema, not at run time.
  - Acceptance: the value expression is a **structured AST** — column references, literals, casts, arithmetic, comparisons, and `CASE`/bucketing — compiled to DuckDB SQL **by the sandbox** with every identifier validated against the introspected schema and safely quoted. The model never emits raw SQL; a raw-SQL path is out of scope.
  - Acceptance: a bare column reference remains expressible as the degenerate `ColumnRef` value expression.
  - Acceptance: because the fitted objective now carries the aggregation, the **root hypothesis-tree proposal no longer selects the objective aggregation/field**, and run-time objective pinning reads the matrix instead of the root proposal. Filter-candidate proposal is otherwise unchanged.
- **R4.** Where a target field is boolean or categorical, the system shall express the objective via casting/indicators (boolean → `0/1`; categorical `column = value` → indicator) so that `avg`/`sum` over such fields **no longer fails** with "numeric aggregation over non-numeric column."
- **R5.** As a maintainer, I want the matrix/objective contract change to be additive so downstream consumers and stored data aren't broken.
  - Acceptance: the matrix target gains optional `aggregation` and `value-expression` fields; a persisted **legacy field-only target** (`{field, direction}`, no aggregation, no expression) deserializes **without error** as a degenerate `ColumnRef` value expression (additive at the JSON layer).
  - Acceptance: consumers that read the matrix or the `Outcome` triplet (including not-yet-built shells) are not forced to change; a new plain-numeric objective (a `ColumnRef` carrying an aggregation) round-trips.
  - Acceptance: because objective selection **moved to intake**, run-time aggregation selection no longer exists — a legacy field-only matrix (which carries no aggregation) is **re-registered** to acquire one (trivial for the pre-release test goals). A matrix that reaches the loop without an aggregation is surfaced as a **clear terminal failure** (R7), never silently defaulted to a mismeasuring aggregate such as `count`.

### Failure Surfacing

- **R6.** As an analyst, I want registration to fail fast with a clear reason so I can fix the objective before wasting a run.
  - Acceptance: after fitting, the system validates the objective against the schema (every referenced column exists under case-normalization; the aggregation is type-compatible with the value expression). If invalid, it attempts a **single schema-aware repair** (feeding the validation error back to the model); if still invalid, registration fails with a clear, actionable message naming what could not be resolved.
  - Acceptance: because introspection is now a **precondition** of matrix generation, if introspection itself fails (unsupported format, unreadable source, sandbox unavailable), registration fails with a clear message rather than degrading silently.
- **R7.** When a hypothesis run fails, the system shall surface the **real underlying reason** (e.g. the sandbox's "field not present in schema: X", a type mismatch, a non-numeric objective value) through the branch-failure event and SSE stream — not a bare HTTP status — so the analyst knows how to fix the registered objective for subsequent runs.
- **R8.** As an analyst, I want failures explained where I encounter them so that I can self-correct.
  - Acceptance: the web UI renders the intake validation message on the registration surface, and renders run-time failure reasons in the live run view.
  - Acceptance: a settled run's **status and failure reason are persisted and retrievable after the fact** (the runs table), surfaced in the objectives list and when reopening the objective — independent of the ephemeral live stream. (Re-viewing a completed run's individual triplets after its live stream ends is out of scope — see MVP Scope.)

### Objectives Navigation & Run Status

- **R9.** The system shall persist **per-run rows** in a runs table — one row per hypothesis-loop trigger — carrying status ∈ {`running`, `completed`, `failed`}, start/end timestamps, and a failure reason. The Orchestrator is the sole writer. (`registered`/no-run is **not** a stored run status — see R10.)
- **R10.** The system shall expose a `GET /goals` endpoint listing registered objectives with each objective's **latest run status**, computing a synthetic `no run` state for a goal that has zero run rows.
- **R11.** As an analyst, I want a list of registered objectives so that I can return to previous or currently-running runs without remembering IDs.
  - Acceptance: a web list view shows each objective's goal text, creation time, and latest run status badge, linking into the existing run view.
  - Acceptance: the list is reachable from the app navigation; a running objective is reachable by opening it (the run view re-subscribes to the live stream); a settled objective's persisted status and failure reason are shown on reopen.
- **R12.** Run-status transitions shall be written across the Phase-1 loop lifecycle with **explicit terminal bookkeeping**: `running` on trigger; `failed` (with reason) when the loop terminates on a **root/terminal** failure (introspection, root proposal, or root baseline) that yields no usable run; `completed` otherwise — including a run whose baseline succeeded but no candidate improved. Non-terminal per-candidate branch failures (siblings continue) do **not** set `failed`. The terminal write shall use a context detached from the loop's own deadline/cancellation, so a timeout- or shutdown-terminated run is still marked `failed` rather than stranded at `running`.

## Design

### Architecture

Unchanged service topology (Orchestrator, Sandbox Execution, Store/Postgres, LLM, Graph, Web UI). The changes are contract refinements within it.

**Intake flow (Orchestrator `handleSubmitGoal`) — introspect-then-fit, tabular.** Reorder tabular registration to: ingest data source → **introspect** (already exists, moved earlier) → generate the evaluation matrix *with the schema* → deterministically validate the fitted objective → (one repair retry on failure) → persist goal → `201`. This replaces today's "matrix from goal text alone; bind later, non-fatally," superseding the parent spec's tabular Key Flow 1 ordering (documents are unaffected — see Downstream Compatibility). Introspection becomes a **precondition**: an introspection failure now fails registration with a clear message (R6) instead of the current log-and-proceed.

**LLM (`internal/llm`).** `GenerateEvaluationMatrix` becomes schema-aware: `GenerateEvaluationMatrix(ctx, goalText, schema)`. Its structured-output schema is extended so the model returns, per target, an **aggregation**, an **objective value expression** (the AST), and a **direction**, choosing real columns from the provided schema (case-insensitive, semantic). Because the objective's aggregation now lives in the matrix, the **root branch of `interventionTreeSchema` drops `objective_aggregation`/`objective_field`**, and `ProposeInterventionTree` proposes only filter candidates (its non-root behavior is unchanged). `pinObjective` (`internal/orchestrator/hypothesis.go`) is rewritten to read the objective from the matrix. Because objective selection no longer exists at run time, a matrix carrying no aggregation (a legacy goal predating this model) is **not** silently defaulted: `pinObjective` treats a missing aggregation as a terminal failure with a clear message directing re-registration (R5/R7), rather than falling back to the removed root-proposal selection or a fixed `count`.

**Objective expression AST + objective label (`internal/domain`).** A new discriminated-union expression type — `ColumnRef`, `Literal`, `Cast`, `Comparison` (e.g. `col = value` → boolean, cast to `0/1`), `Arithmetic`, `Case`/bucket — stored as jsonb inside the matrix. `Target` gains optional `Aggregation` and `Value` (Expression) fields alongside the retained `Field`/`Direction` keys; a `ColumnRef` node is the degenerate "bare column" objective, and legacy `{field, direction}` rows still deserialize. Because a compiled expression has **no single column name**, the objective is carried end-to-end under a **synthetic objective label** (a stable key, not a column): the execute request carries `{ aggregation, value-expression, objective-label }`; the sandbox keys `ExecuteResponse.Value` by that label; `numericValue` reads that label; and `writeTriplet`'s `Outcome.Value` is keyed by it. Hard constraints stay column comparisons; note that `constraintsSatisfied`'s on-objective-field check (`hypothesis.go`) only applies to bare-`ColumnRef` objectives and becomes a no-op for compound expressions (expression-based constraints are deferred).

**Sandbox (`internal/sandbox`).** The `query`-path execute contract's aggregation target becomes the compiled expression under the objective label. The sandbox **compiles the AST to a DuckDB SQL expression**, validating each `ColumnRef` against the introspected schema and quoting identifiers, then measures `aggregation(expression)` under the intervention filters and returns it keyed by the objective label. This is what makes `avg` over a boolean/categorical work (compiles to `avg(CAST(col AS INTEGER))` or `avg(CASE WHEN col = 'x' THEN 1 ELSE 0 END)`), retiring the "numeric aggregation over non-numeric column" hard failure for the supported cases. Compilation/validation errors return a descriptive `{error}` body.

**Failure propagation.** The Orchestrator stops collapsing sandbox errors into `sandbox /execute returned status N`: the Sandbox client parses the sandbox's `{error}` body and the loop's `branchFailure` publishes that real reason. Intake validation (R6) is deterministic in the Orchestrator against the introspected schema; its message is returned on the `POST /goals` response. Both the intake message and run-time branch-failure reasons are rendered by the Web UI; a terminal failure's reason is persisted on the run row (R8/R9) so it survives the ephemeral stream.

**Run status + list (`internal/store`, Orchestrator, Web).** A new **runs table** (migration): `run_id` PK, `optimization_function_id` FK, `status` ∈ {`running`,`completed`,`failed`}, `started_at`, `ended_at null`, `failure_reason null`. A runs store with `Create`/`SetStatus`/latest-by-goal, plus `GoalRegistry.List`. The Orchestrator creates a run row (`running`) when the hypothesis loop is triggered and transitions it across the lifecycle with **explicit terminal bookkeeping**: `runLoop` tracks a terminal error, its root-failure early-returns set it, and the terminal write chooses `failed`+reason vs `completed` from it — so the existing single `defer` cannot mislabel a root-failed run as completed, and non-terminal per-candidate `branchFailure`s don't flip status. The terminal `SetStatus` write (and its `failure_reason`) must run on a context **detached from the loop's `loopTimeout`/cancellation** with its own short deadline, so it lands even when the loop terminated *because* that context expired or the process is shutting down — otherwise a deadline-terminated run would strand its row at `running` and misreport forever. `GET /goals` returns goals joined to their latest run row, synthesizing `no run` where none exists. The Web UI adds a BFF route `GET /api/orchestrator/goals`, a list page (objective text, created-at, status badge) wired into `AppNav` and linking to `/goals/[id]`, and it surfaces the persisted status + `failure_reason` when an objective is reopened (a settled run shows its reason without the live stream).

### Data model

- **EvaluationMatrix** (jsonb): `targets: [{ field?, direction, aggregation?, value?: <Expression> }]`, `constraints: [...]` (unchanged shape). `Expression` is the AST union. Legacy `{field, direction}` targets deserialize without error (`aggregation`/`value` absent → degenerate `ColumnRef`); such goals are re-registered to acquire an aggregation, and a matrix reaching the loop without one is a clear terminal failure (R7), not a default.
- **runs** (new Postgres table): `run_id uuid pk`, `optimization_function_id uuid`, `status text` (`running`/`completed`/`failed`), `started_at timestamptz`, `ended_at timestamptz null`, `failure_reason text null`. Read by the runtime roles; written by the Orchestrator role only (mirrors the audit-writer ownership pattern). `no run` is derived by the `GET /goals` join, never stored.

### Key flows

1. **Registration (tabular)** — ingest → introspect (precondition; failure → clear `4xx`) → schema-aware matrix generation (objective resolved to real columns + expression + aggregation) → deterministic validate → [one repair retry] → persist goal → `201`. On unrecoverable validation failure → `4xx` with a clear reason.
2. **Run** — trigger → create run (`running`) → loop; on normal completion → `completed`; on a **terminal** failure → `failed` + the real reason, and `branch_failure` carries that reason to the SSE stream. Non-terminal candidate failures are streamed but don't set run status.
3. **Browse** — `GET /goals` → objectives + latest status (or `no run`) → web list → open objective → run view: live stream if running, else persisted status + `failure_reason`.

### Downstream Compatibility (advisory)

- **Shell 07 (multi-modal extraction)** shares the *concept* of schema-aware fitting but **not** this exact ordering: parent-spec R16/Key Flow 1 require a document's matrix to be produced from goal text and *not* blocked on introspection, whereas this spec makes introspection a precondition for the **tabular** path only. Shell 07 should keep its document matrix-from-text-then-bind flow; the reusable seam is the schema-aware fitting *idea* (a document's candidate-field set substituting for a tabular column list), not the tabular reorder. This spec supersedes the parent's tabular Key Flow 1 and should be read alongside R16.
- **Shells 04 / 08** reference the `Outcome`/matrix contracts; the objective change is additive (plain-numeric objectives are unchanged, `Outcome.Value` is still a `map[string]any` — now keyed by the objective label rather than a column name), so their clustering/HITL reads are not forced to change. The graph write contract (`writeTriplet` node/edge shape) is **unchanged**, which is why completed-run triplet replay is deferred (the triplets carry no goal/run id to query by).

## MVP Scope

**Ships:** introspect-then-fit for **tabular** sources; the objective expression AST covering numeric, boolean, categorical-equals-value, arithmetic, and `CASE`/bucket; intake + run-time failure surfacing with one repair retry; the runs table, `GET /goals`, and the web objectives list with status badges + persisted failure reasons for **Phase-1 hypothesis** runs.

**Deferred:** expression-based *constraints/filters* (constraints stay column comparisons); raw-SQL objective expressions; run-status for the Phase-2 sleep cycle; document-source fitting (shell 07, which builds on the schema-aware-fitting idea); **re-viewing a completed run's individual triplets** after its live stream ends (would require stamping a goal/run id onto the graph triplet writes — a graph-contract change that ripples into shells 04/08 — so settled runs show status + reason, and the run's knowledge surfaces via heuristics after the sleep cycle).
