# Plan: Engine A Hardening — Value Grounding & Windowed Objectives

## Context

Engine A remains V2's fast track unchanged in shape, but it still silently produces zero-triplet "completed" runs when Claude invents categorical values that exist in no row — the last remaining cause of goals that report success while producing nothing. Separately, entity-relative signals (velocity, trailing means — the native vocabulary of the fraud use case) are inexpressible because the sandbox emits only flat SELECTs. This shell grounds Phase-1 proposals in real column values (spec R20) and adds windowed objective support (spec R21) with its own threat pass, since the compiler's narrowness is currently a load-bearing injection defense.

Settled decision (registration open question): the low-cardinality cutoff for distinct-value return is a single knob — a column is eligible iff its distinct count is ≤ the cap, and eligible columns return all their values. Default **50**, env-configurable (`SANDBOX_DISTINCT_VALUE_CAP` via the `intEnv` pattern). Spec :173 expects this to be shared with Shell 6's CI-test binning cutoff, so keep it a named config field, not an inline literal.

Plan risks noted during expansion:

- Windowed objectives require the entity/time bindings to travel to the sandbox at execute time, which widens the `ExecuteRequest` wire DTO in `internal/sandboxclient` (shared, CGO-free) and the `objective.Objective`/`ExecuteRequestFor` seam in `internal/objective` — the Sleep-Cycle worker shares both. Downstream shells (6, 7, 9) consume these; adding optional fields/parameters is the stable seam — do not redesign the request shape.
- Spec :49 (Shell 7's verifier) gives windowed-objective findings a first-class `unsupported_objective` verification outcome. Nothing here must block that: the goal record must make "this goal has a windowed objective" cheaply detectable (bindings columns non-NULL / AST contains a window kind).

## Pattern Survey

### Analogous Features

The value analogue (distinct-value membership) is a direct structural clone.
- `internal/orchestrator/hypothesis.go:698` — `proposeValidCandidates` + `splitByColumns` (`:730`) is the full grounding+repair loop: propose → partition valid/invalid + collect unknowns → `RepairInterventionTree` up to `maxProposalRepairs` (`:52`, =3) → drop still-invalid + `branchFailure`. ### Convention Anchors

- **CGO firewall (load-bearing):** DuckDB/window SQL compilation lives ONLY in `internal/sandbox`. Deterministic pre-checks reused by the orchestrator live in `internal/domain` (why `UnknownFilterColumns`/`ExpressionDepth` are there). The value-validation helper and any window shape-guard reused by the orchestrator must live in `internal/domain`, never import sandbox.
- **Structured-output schema stays loose:** `internal/llm/schema.go` keeps filter/expression fields as plain strings/bounded `anyOf` — never per-column enums, never recursion — to stay under the constrained-decoding grammar ceiling (`:55–87` comments). Distinct values are prompt-grounded + deterministically post-checked, NOT pushed into the schema as enums.
- **Prompt grounding lives in system constants + `*Summary` helpers:** `evaluationMatrixSystem`, `interventionTreeSystem`, `filterShapeGuide`, `expressionShapeGuide` (`client.go:397–431`) plus `columnSummary`/`MatrixSummary`/`treePrompt` (`:433–486`). Value grounding extends `columnSummary` (currently `- name (type)`); window vocabulary is a new `*ShapeGuide` const.
- **AST is a flat "fat node" discriminated union:** `domain.Expression` (`domain.go:234`) with `Kind` selecting omitempty fields, stdlib-json marshalable. New window kinds add fields to this one struct + new `ExpressionKind` consts + arms in `compileExpr`, `staticValidateExpr`, `ExpressionDepth`, and `renderExpr` — all switch sites, no custom marshaler.
- **Non-fatal branch outcome:** `branchFailure` (`hypothesis.go:676`) records a `hypothesis_branch_failure` audit + publishes a `branch_failure` SSE event; siblings continue (`processCandidate:207`). The zero-row segment outcome is a new event/audit type in this same shape, distinct from measurement failure. (Today a count-objective empty segment persists a support-0 triplet via `writeTriplet` at `:228`, self-excluding from the S* floor; Step 4 deliberately replaces that with the zero-row outcome.)
- **Migration + Goal-struct + projection triad:** entity/time bindings touch `internal/store/migrations/` (next number **0012**; column-add pattern per `0007_document_goals.up.sql` — `ALTER TABLE goal_registry ADD COLUMN ...`, no new grants), the `store.Goal` struct (`goalregistry.go:27`), the `goalColumns` projection const (`:54`), and both `Insert` (`:60`) and `Get`/`List` `Scan` calls. NULL-able columns scan via pointer or COALESCE.
- **HTTP status mapping via sentinel `errors.Is`:** sandbox compile failures map to 400 in `writeStageErr` (`server.go:366`); new window-compile rejections reuse existing sentinels (`errUnknownOperator`, `errTypeIncompatible`) so no new status arm is needed.
- **Threat-pass test placement:** SQL-injection/quoting tests in `internal/sandbox/compile_test.go`; fencing/allowlist invariants in `internal/llm/fence_test.go` and `internal/domain/domain_test.go`. The widened-grammar threat pass adds cases to both.

### Proposed Alignment

Follow existing patterns closely — this shell is almost entirely extension of established seams. Value grounding: a `UnknownFilterValues`-style CGO-free helper in `internal/domain` wired into `proposeValidCandidates`'s partition-repair loop; capped distinct values surfaced through the `filesource.columns` → `toSchemaDTO` → `toSandboxSchema` → `columnSummary` pipeline, prompt-grounded (never a schema enum). Zero-row segments modeled on the `branchFailure` non-fatal shape but as a distinct event/audit type. Windowed objectives: new `ExpressionKind`s on the flat fat node with arms at all switch sites plus a window/frame allowlist, entity/time columns through `resolveColumn`+`quoteIdent`, bindings persisted via a `0012` migration and validated in `submit.go`'s dry-run repair loop. The one genuinely new area: `PARTITION BY`/`ORDER BY`/frame clauses have no current allowlist, so the threat pass is new coverage — assert both column quoting and that no frame/offset value is interpolated rather than bound.

## Implementation Steps

1. **Return capped distinct values from introspection**
   - Add `DistinctValueCap int` to the sandbox config block in `internal/config/config.go` via `intEnv("SANDBOX_DISTINCT_VALUE_CAP", 50)`, threaded into `sandbox.Server` construction the same way existing limits reach it (see `internal/sandbox/server.go` constructor and `cmd/sandbox` wiring).
   - Extend `datasource.Column` in the CGO-free `internal/datasource` package with `DistinctValues []string` (nil = ineligible/unknown, never partially populated). The field is populated only by the CGO-locked sandbox probe in `FileSource.Introspect` (`internal/sandbox/filesource.go:73`), so the firewall holds. `DocumentSource.Introspect` (`documentsource.go:54`) is an intentional no-op for values: it returns a column-less `KindDocument` schema and never opens a query engine — value grounding is tabular-only.
   - In `FileSource` introspection, after `columns()` (`filesource.go:364`), run one bounded probe per candidate column over the already-staged engine: `SELECT DISTINCT <quoteIdent(col)> FROM <tableFn> WHERE <col> IS NOT NULL LIMIT cap+1`, casting values to VARCHAR. If the probe returns > cap rows, the column is ineligible — leave `DistinctValues` nil. Restrict probing to text-like/boolean/integer-typed columns (the categorical surface); skip floating-point columns.
   - Thread values through the wire: `toSchemaDTO` (`internal/sandbox/server.go:355`), the shared `schemaDTO`/`Column` in `internal/sandboxclient/client.go:36` (add `DistinctValues []string \`json:"distinct_values,omitempty"\``), and `toSandboxSchema` (`internal/orchestrator/hypothesis.go:845`) into `llm.SandboxSchema` (`internal/llm/schema.go:12`).

2. **Value-ground the tree-proposal prompt**
   - Extend `columnSummary` (`internal/llm/client.go:469`) to append eligible columns' values: `- name (type) values: "a", "b", "c"`. The values are dataset-derived untrusted text: confirm the summary is interpolated inside the fenced region in `treePrompt` (`client.go:433`) and in the inline matrix-prompt assemblies at `client.go:97` and `:111` (both already fence `columnSummary`), wrapped by the per-request `Fence` with `Directive()` appended — never outside it.
   - Add prompt language to `interventionTreeSystem` (`client.go:397–431`) instructing that equality/membership filter values for a column with a listed value set MUST be drawn verbatim from that set; do NOT add enums to `interventionTreeSchema` (`internal/llm/schema.go:75`) — the grammar ceiling forbids it.
   - Add the new interpolation site to the poison-payload table in `internal/llm/fence_test.go` (`TestAllFencedClientMethodsFenceUntrustedInput`): a distinct value carrying an injection marker must not survive outside the fence.

3. **Deterministic value post-check + repair wiring**
   - Add `UnknownFilterValues(filters []Constraint, values map[string][]string) []string` (name/shape final at implementation) to `internal/domain/domain.go`, cloned from `UnknownFilterColumns` (`:481`): CGO-free, checks only equality/membership constraints against columns present in the map (columns without a value list are skipped — high-cardinality is not an error), case-insensitive per `columnKnown` precedent, first-seen dedupe, returns human-readable `column=value` offenders for the repair prompt. Stringification contract: the probe stores DuckDB `CAST(... AS VARCHAR)` output, while proposal operands arrive as `domain.LiteralValue` — the helper must render operands (via `renderLiteral`, `domain.go:296`, or an equivalent kept consistent with it) to strings that match the VARCHAR cast for every probed type, leaning on case-insensitive comparison for booleans (`true` vs `True`) and rendering integer literals without a decimal point for integer columns (`5`, not `5.0`) — a divergence here falsely rejects valid proposals and burns repair budget. Keep the signature dependency-free — Shell 6 reuses it for claim construction and grounding validation (spec R15).
   - In `proposeValidCandidates`/`splitByColumns` (`internal/orchestrator/hypothesis.go:698,:730`), partition on unknown values alongside unknown columns; feed both offender lists into the same `RepairInterventionTree` validation-error string, within the existing `maxProposalRepairs` (=3) budget. Build the `values` map once per run next to `columnNames` (`:750`).

4. **Zero-row segments become a distinct non-fatal outcome**
   - Detection ordering is load-bearing: in `processCandidate` (`internal/orchestrator/hypothesis.go:199`), read `RowCount` and branch on `counted && support == 0` **before** the `NumericValue` non-numeric bailout at `:213` — a zero-row segment under avg/sum/min/max (including the boolean-rate form) scans as SQL NULL (`filesource.go:151–152` returns `Value: nil, RowCount: 0`; the server emits `{label: null, row_count: 0}`), so `NumericValue` returns `(0, false)` and the current code reaches `branchFailure(errNonNumericValue)` first; only `count` objectives would ever reach a check placed at `:222`. `sleepcycle/search.go:220–231` already checks support before reading the value for exactly this reason — mirror that ordering. Never branch on `support == 0` alone: `RowCount` returns `(0, false)` when the reserved key is absent, a version-skew signal that must keep its current non-fatal log disposition (`:222–225`), not fire the new event. On a true zero-row segment, record a distinct audit event (`hypothesis_zero_row_segment`) and publish a distinct SSE event type (`zero_row_segment`), modeled on `branchFailure` (`:676`) but non-fatal and clearly distinguishable from measurement failure. Disposition is uniform across aggregations: record the event and return — **no `writeTriplet` (`:228`), no `recordConfidence` (`:237`)**. An empty segment supports no causal claim, so no triplet value is meaningful (avg/sum/min/max have no value at all — the aggregate scanned as NULL; a `count` objective's 0-over-empty is a true measurement but a meaningless effect size). This knowingly changes one existing behavior: today a count-objective empty segment persists a `value=0, support=0` triplet via `writeTriplet` — under this plan it stops doing so and records the zero-row outcome instead. Downstream impact is nil: support-0 triplets were already self-excluded from the Sleep Cycle's S* floor. After this reordering the `NumericValue` bailout fires only for genuinely non-numeric values on non-empty segments.
   - Retry mechanism and stopping rule (measurement time has no repair loop — `maxProposalRepairs` is consumed earlier inside `proposeValidCandidates` when the parent generates children, so no repair budget exists at the zero-row site). The up-signal is an explicit structural change: `processCandidate` is currently `void`, so give it a small result return (e.g. a `candidateOutcome` struct carrying `zeroRow bool` plus the candidate's filters) — the recursion's tail loop (`:267–269`) and the root loop (`runLoop`, `:190–192`) both collect zero-row children from these return values. After one expansion's loop completes, if any zero-row children were collected, make at most **one** `RepairInterventionTree` call (a new const `maxZeroRowReproposals = 1` beside `maxProposalRepairs` at `:52`) whose validation-error string names the empty filter sets, requesting replacement candidates. Replacements go through the same column/value post-checks, then **re-enter `processCandidate` with the same depth and parent-filter arguments as the children they replace**, so successful replacements write triplets and expand normally. A replacement that is again zero-row is recorded (audit + SSE, as above) and pruned — the budget is spent, terminal disposition reached. Only the `!counted` version-skew path (`:222–225`) keeps its exact current behavior: log, then proceed as today — it must not fire the zero-row event or the re-proposal.

5. **Entity-key + time-column bindings at goal registration**
   - Migration `0012_windowed_objectives.up.sql` / `.down.sql` in `internal/store/migrations/`: `ALTER TABLE goal_registry ADD COLUMN entity_key_column text, ADD COLUMN time_column text` (both nullable; no new grants), following the `0007_document_goals` column-add pattern.
   - Extend `store.Goal` (`internal/store/goalregistry.go:27`), the `goalColumns` projection (`:54`), `Insert` (`:60`), and the `Get`/`List` scans; nullable columns scan via `*string`/COALESCE per store convention.
   - Accept optional `entity_key_column`/`time_column` on goal registration (`internal/orchestrator/submit.go` request DTO). Validate at registration inside the existing introspect-then-dry-run flow (`:119–147`): both-or-neither present; each must resolve against the introspected schema (the orchestrator-side check mirrors sandbox `resolveColumn` semantics — case-insensitive unique match against `schemaDTO` columns); the time column must be orderable (temporal or numeric type). Resolution failure is a 422 like other objective validation failures.
   - A matrix whose value expression contains a window kind while the goal has no bindings is a deterministic 422 at registration and a validation failure in the dry-run repair loop (`isObjectiveValidationFailure`), so `RepairEvaluationMatrix` can strip or fix it.

6. **Windowed AST constructs with depth/shape guards**
   - Add `ExpressionKind` consts to `internal/domain/domain.go` (`:200–210`): `LagKind` (prior value of an inner expression, offset ≥ 1) and `TrailingAggregateKind` (allowlisted aggregate of an inner expression over a trailing row window, size ≥ 1). Add their fields to the flat fat-node `Expression` (`:234`): inner `*Expression`, integer offset/window-size (omitempty).
   - Extend `ExpressionDepth` (`:374`) so window kinds count their inner expression (no bypass of `MaxObjectiveExpressionDepth`), and add a CGO-free shape guard in domain: no window kind nested anywhere under another window kind, offsets/sizes positive and bounded (cap window size, e.g. 10_000 rows, as a domain const). Wire the shape guard where `errExpressionTooDeep` is enforced in the orchestrator (`hypothesis.go:775` precedent) and into registration dry-run validation.
   - Extend `renderExpr` (human-readable rendering) with both kinds.
   - **Teach the objective-fitting prompt the window kinds** — without this the feature is unreachable: objectives are Claude-generated (`GenerateEvaluationMatrix`, `submit.go:137`) and the expression shape is taught entirely through `expressionShapeGuide` (`internal/llm/client.go:415`), which currently enumerates only the six existing kinds. Extend that const with the `lag` and trailing-aggregate JSON shapes. The expression travels as a JSON-encoded string (per the grammar-ceiling convention), so this is prose-only — `evaluationMatrixSchema` does not change. Window kinds are valid only when the goal has bindings: thread a "windowed objectives available: yes/no" line into the matrix prompt from the registration request's bindings, instructing the model to use window kinds only when available (and never otherwise). The repair prompts (`evaluationMatrixRepairSystem`) inherit via the shared const.

7. **Compile windows in the sandbox**
   - Thread the bindings end to end — every hop is a named signature change, none of these values is reachable today: (a) `objective.Objective` (`internal/objective/objective.go:35`) gains optional `EntityKeyColumn, TimeColumn string`; `Pin` cannot see them (they live on the goal, not the matrix), so both orchestrator call sites populate them after `Pin` — `processCandidate`/loop setup from `store.Goal`, and registration's dry-run path (`dryRunObjective`, `hypothesis.go:778`) from the *submitted request's* bindings (the goal row does not exist yet — without this, a valid windowed goal dry-runs bindings-less, trips the absent-bindings rejection below, and 422s spuriously). The Sleep-Cycle worker populates them the same way from its goal record. (b) `ExecuteRequestFor` (`objective.go:64`) copies them into new optional `ExecuteRequest` fields (`internal/sandboxclient`, additive — the wire DTO is shared and CGO-free; stable seam for Shells 6/7/9), and the sandbox's own mirror `ExecuteRequest` struct (`internal/sandbox/server.go:124`) gains the same fields with identical JSON tags, per the byte-for-byte mirror convention. (c) In the sandbox, `handleExecute` passes them down the `ExecuteCounted` → `compileObjectiveCounted` → `compileExpr` chain — bundle `cols` + the resolved/quoted entity and time columns into a small compile-context struct rather than growing every signature twice.
   - In `internal/sandbox/compile.go`: `staticValidateExpr` gains arms for both window kinds (allowlist `allowedWindowAgg` following the `allowedAgg` map convention at `:31–91`; reject unknown funcs/shapes via existing sentinels `errUnknownOperator`/`errTypeIncompatible` so `writeStageErr`'s 400 mapping needs no new arm). Reject any execute request containing window kinds whose bindings are absent (schema-independent check, so it also runs pre-staging).
   - **The subquery form is the only compile shape for windowed objectives, not a fallback**: the objective is always an aggregate (`compileObjectiveCounted` → `aggregateSelect`, `compile.go:305,:409`, unconditionally wraps `agg(<operand>)`), and DuckDB rejects a window function nested inside an aggregate call (`Binder Error: aggregate function calls cannot contain window function calls`). When the value expression contains a window kind, compile `SELECT CAST(<agg>(<alias>) AS DOUBLE)[, CAST(count(*) AS BIGINT)] FROM (SELECT *, <window-expr> AS <alias> FROM <tableFn>) WHERE <predicates>` — window computed in the inner select over the entity's **full history**, intervention filters and `count(*)` applied in the outer select. The alias must be collision-proof: datasets are arbitrary user CSVs, so a fixed literal (`w`) collides with a real column of that name and makes the outer aggregate reference ambiguous — pick a sentinel name and verify it absent from `cols` (suffix until unique) at compile time. Window-over-history (not window-over-filtered-rows) is the deliberate semantic: a row's velocity/trailing mean is an intrinsic property of the row's entity history, so the same row carries the same value in every segment — otherwise parent and child segment values are computed from different window inputs and effect_size comparisons break. Non-windowed expressions keep the existing single-SELECT shape byte-identical.
   - Window fragments: `lag(<inner>, ?) OVER (PARTITION BY <entity> ORDER BY <time>)` and `<agg>(<inner>) OVER (PARTITION BY <entity> ORDER BY <time> ROWS BETWEEN <N> PRECEDING AND 1 PRECEDING)`, where entity/time columns pass through `resolveColumn` (`:668`) + `quoteIdent` (`:691`) and the aggregate name comes from the allowlist map, never request text. Bind the `lag` offset as a `?` param — it is a function argument, not a frame bound, and binds fine. For the frame-bound window size, attempt `?` binding first and verify against the pinned go-duckdb version in a compile test (a CLI probe on DuckDB 1.5.5 accepted `ROWS BETWEEN ? PRECEDING`, contradicting the assumption that frame bounds are unbindable — do not assume either way); only if the pinned driver rejects it, fall back to a strconv-formatted integer that the domain shape guard has already range-checked, with a comment naming the driver limitation.

8. **Threat pass on the widened surface**
   - `internal/sandbox/compile_test.go`: extend `TestCompileQueryRejections` and the literal-path guard (`:446` precedent) with window cases — malicious entity/time column names (`x"); DROP TABLE users; --`) rejected by `resolveColumn` or safely quoted by `quoteIdent`; lag offsets bound as `?` params, and window sizes either bound or (only if the pinned driver rejects frame-bound params) emitted solely as range-checked integers — assert out-of-range/negative/NaN shapes were rejected before compile and that no request text reaches the SQL string; non-allowlisted window aggregate rejected; window kind with missing bindings rejected; nested-window AST rejected.
   - `internal/domain/domain_test.go`: table tests for `UnknownFilterValues` (case-insensitivity, high-cardinality skip, dedupe) and for `ExpressionDepth`/shape-guard on window kinds (nested window rejected, depth counted through inner expressions).
   - `internal/llm/fence_test.go`: the distinct-values interpolation site added to the poison-payload invariant table.
   - Record the threat-pass result as test coverage in these three files — the gate for enabling the widened grammar is these tests passing (spec R21: threat pass "before it ships").
