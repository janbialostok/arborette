# Plan: HITL Verification Backend

## Context

Since extraction results have no labeled ground truth, the system routes low-confidence results to a human verification queue — but the loop must never block on individual verifications by default, and the trust gate for the Sleep-Cycle search must be an explicit human-confirmed status, not a self-reported confidence number the model could report as 1.0 without ever being reviewed. This plan builds the Orchestrator-side machinery: the verification queue, its REST endpoints, the `verification_status` write-through on resolution, and the live confidence-bin distribution that streams alongside hypothesis-loop progress. The web UI that consumes these endpoints is a separate downstream plan (`arborette-10`), so the REST and SSE contracts defined here are its stable seam.

Decisions locked at expansion:

- **Default confidence threshold: 0.8** (user-confirmed), env-configurable as `HITL_CONFIDENCE_THRESHOLD` and analyst-overridable per goal at registration. This tunes queue ergonomics only; the `verification_status` gate (`domain.SearchEligibleStatuses`) protects the Sleep-Cycle search regardless of threshold calibration.
- **Meta-Heuristic invalidation on late correction/rejection stays post-MVP** (user-confirmed). Note: `Repository.MarkStaleMetaHeuristics` (`internal/graph/repository.go:77`) already sweeps rejected-outcome-derived Meta-Heuristics at the next Sleep-Cycle run, so a rejection here is partially self-healing; no work in this plan.

**Design conflict, resolved (spec-vs-code):** the spec describes epoch gating level-wise (R19 acceptance: "when a tree depth level's candidates finish evaluating, the loop proceeds to the next depth level"). The hypothesis loop is actually **depth-first pre-order recursion** with no level barrier (`processCandidate` recurses at `internal/orchestrator/hypothesis.go:225`, `processExtractionCandidate` at `:317`); the spec's level-wise description is stale. This plan implements the contract's intent per-branch: in `blocking` mode, descent below a queued (below-threshold) extraction outcome waits for that outcome's resolution; in `speculative` mode (default) the loop never waits. This preserves both invariants — "never block by default" and "blocking mode trades speed for verified pruning decisions" — without restructuring the traversal.

Blocking mode's consequences are structural and must be stated plainly: the loop is a **single sequential goroutine** (`handleTriggerLoop` launches one `go func()`; `runDocumentLoop` iterates fields×methods serially), so a wait at one below-threshold node stalls *everything* behind it in the traversal — sibling methods, deeper levels, and every later target field — and the runs row stays `running`, the SSE stream stays open, and `loop_complete` fires only after all waits resolve. This is the trade the analyst opts into per goal. Because human review takes far longer than the default `loopTimeout = 30 * time.Minute` (`hypothesis.go:37-38` — expiry flips the whole run to `RunFailed` via the `runLoop` defer at `:94-104`), a blocking-mode run gets a **dedicated, human-scale deadline**: `handleTriggerLoop` selects `HITL_BLOCKING_LOOP_TIMEOUT_MINUTES` (env, default 1440 = 24h, plumbed like the threshold) instead of `loopTimeout` when the goal's `epoch_mode` is `blocking`. Deadline expiry while waiting remains the documented backstop: the run fails with a clear reason, exactly like today's timeout path.

### Convention Anchors

- **Migrations**: numbered `NNNN_name.{up,down}.sql`, embedded via `//go:embed *.sql`. **Next is `0009`.** Grants for a new table are co-located in the table-creating migration (see `0006_runs.up.sql`), not in `0005_grants`. No `CREATE ROLE` in migrations. A queue table the orchestrator writes needs `GRANT SELECT, INSERT, UPDATE ON <table> TO arborette_orchestrator` (+ `GRANT SELECT ... TO arborette_service`, mirroring `runs`).
- **Store types**: one type per table wrapping `*Pool`, `NewX(pool)` constructor, explicit column-list SQL, string-enum status types, no delete methods on write-restricted tables. Least-privilege role is the primary boundary.
- **REST handlers**: `mux.HandleFunc("METHOD /path", ...)` (`server.go:156-164`), `{id}` via `r.PathValue`, `lookupGoal` for goal 404, `writeJSON`/`writeErr` with `errorResponse{Error string}` envelope, `MaxBytesReader` on bodies. Sandbox faults classified by `SandboxError.Status` → 400 analyst-fixable / 5xx→502 (`submit.go:310`).
- **SSE**: framing is `data: <json>\n\n` with no `event:` line (`stream.go:57`); every event carries a top-level `type`. Existing types: `triplet`, `branch_failure`, `loop_complete`. `Hub.Complete` evicts the run and closes subscriber streams; `Publish` to an unknown id lazily recreates run state (leak risk for post-completion publishes — addressed in Step 6).
- **Graph seam**: all Cypher is Neptune-portable openCypher, keyed on the UUID `id` property; nothing outside `internal/graph` touches the driver. Properties that must be MATCHed (e.g. `goal_id`, intervention `type`) are top-level node props, never inside JSON blobs.
- **Handler tests**: `httptest` + hand-written fakes per consumer interface (`server_test.go` `newTestServer`/`newTestServerRepo`). Store tests are integration-gated against live Postgres with grants-boundary assertions. Graph tests are integration-gated similarly.
- **Config → Server plumbing**: primitive-arg infra constructors; per-goal defaults enter via `config.Load` → `OrchestratorConfig` → `NewServer` params.

### Proposed Alignment

Follow existing patterns closely — most seams already exist. The resolution graph write (`UpdateOutcomeVerification`) is fully built and stubbed; the queue table mirrors `runs.go`/`0006_runs.up.sql`; endpoints mirror `heuristics.go` (GET) and `submit.go`/`sleepcycle.go` (POST); the excerpt endpoint slices `sandbox.DocumentText` output by the byte-offset locator; per-goal columns follow `0007`; the SSE histogram is a new `Event.Type` on the existing Hub. Two areas have no precedent and get explicit designs below: the blocking-mode gate (the loop has no level barrier — per-branch gating instead, see Context) and histogram state (in-memory during the run, recomputed from the graph for out-of-band re-pushes).

## Implementation Steps

1. **Migration `0009_hitl_verification` + goal-registry columns**
   - Add `internal/store/migrations/0009_hitl_verification.up.sql` / `.down.sql`.
   - `verification_queue` table: `queue_id uuid PRIMARY KEY`, `optimization_function_id uuid NOT NULL REFERENCES goal_registry(optimization_function_id)`, `outcome_id uuid NOT NULL` (Neo4j-side application UUID — no FK; add `UNIQUE` so one outcome queues once), `field text NOT NULL`, `extracted_value text NOT NULL`, `provenance jsonb` (locator snapshot at queue time, nullable), `confidence double precision NOT NULL` (at queue time), `status text NOT NULL DEFAULT 'pending'`, `resolution text` (`confirmed`/`corrected`/`rejected`, null while pending), `corrected_value text`, `created_at timestamptz NOT NULL DEFAULT now()`, `resolved_at timestamptz`. Index `(optimization_function_id, status, created_at DESC)`.
   - Grants co-located per `0006_runs.up.sql`: `GRANT SELECT, INSERT, UPDATE ON verification_queue TO arborette_orchestrator; GRANT SELECT ON verification_queue TO arborette_service;`.
   - `ALTER TABLE goal_registry ADD COLUMN confidence_threshold double precision;` (NULL = use server default) and `ADD COLUMN epoch_mode text NOT NULL DEFAULT 'speculative';` — no new grants needed (0005 table-level grants cover new columns, per the `0007` comment).

2. **Store layer: `VerificationQueue` type + `Goal` fields**
   - New `internal/store/verificationqueue.go` mirroring `runs.go`: `VerificationQueue` wrapping `*Pool`, `NewVerificationQueue(pool)`; string enums `QueueStatus` (`pending`/`resolved`) and `QueueResolution` (`confirmed`/`corrected`/`rejected`); methods `Enqueue(ctx, Entry)`, `ListForGoal(ctx, goalID, status)` (status optional), `GetByOutcome(ctx, outcomeID)`, `Resolve(ctx, outcomeID, resolution, correctedValue)`, `EnqueueResolved(ctx, Entry, resolution, correctedValue)`, `CountPending(ctx, goalID)` (for the blocking gate and run-status surfaces). Explicit column lists; provenance marshalled with `encoding/json`.
   - **Concurrency guards (these make the handler's 409 implementable):** `Resolve` is a guarded claim — `UPDATE ... SET status='resolved', resolution=$2, corrected_value=$3, resolved_at=now() WHERE outcome_id=$1 AND status='pending'`, returning a typed `ErrAlreadyResolved` when `RowsAffected() == 0` (row missing is distinguished by `GetByOutcome`). `EnqueueResolved` (the on-demand path) is `INSERT ... ON CONFLICT (outcome_id) DO NOTHING` with the same rows-affected → `ErrAlreadyResolved` mapping, so two concurrent on-demand resolutions of one outcome yield one 200 and one 409 instead of a unique-violation 500. `Unclaim(ctx, outcomeID, resolution)` is the owner's compensation (Step 6 invariant rule 1): `UPDATE ... SET status='pending', resolution=NULL, corrected_value=NULL, resolved_at=NULL WHERE outcome_id=$1 AND status='resolved' AND resolution=$2`, rows-affected-checked — the resolution-value guard means it only reverts the claim this owner wrote.
   - Store integration tests must cover `Unclaim`'s guard directly: reverts the owner's own claim; no-ops (0 rows) against a pending row or a row resolved with a different resolution value.
   - `internal/store/goalregistry.go`: add `ConfidenceThreshold *float64` and `EpochMode EpochMode` to `Goal` (`EpochMode` a store string enum like `RunStatus`: `EpochSpeculative`/`EpochBlocking`); extend `Insert`, `Get`, `List` column lists and scans; `Insert` writes `epoch_mode` defaulting to `speculative` when empty.
   - Store integration tests in `internal/store/store_test.go`: queue round-trip (enqueue → list → resolve → list-empty), unique-outcome conflict, and a `TestVerificationQueueGrants` grants-boundary test mirroring `TestRunsGrants:482` (service role can SELECT but not INSERT/UPDATE). Per the store-layer memory: use `Exec`/`QueryRow` for denial checks, never unread `Query` rows.

4. **Graph layer: outcome listing + correction write**
   - `internal/graph/repository.go` + `internal/graph/neo4j.go`: add three methods, all Neptune-portable openCypher keyed on top-level props:
     - `ListExtractionOutcomes(ctx, goalID) ([]ExtractionOutcome, error)` — `MATCH (i:Intervention {goal_id: $goalID, type: 'extract'})-[e:PRODUCED]->(o:Outcome) RETURN o, e.confidence, i.properties` mapped to a new `ExtractionOutcome{OutcomeID, GoalID, Field, Method, Value, Provenance, VerificationStatus, Confidence}` struct (reuse `outcomeFromNode`/`unmarshalProvenance`). Serves the on-demand browse endpoint.
     - `GetExtractionOutcome(ctx, outcomeID) (ExtractionOutcome, error)` — the single-outcome form (`MATCH (i:Intervention)-[e:PRODUCED]->(o:Outcome {id: $id}) RETURN ...`), needed because the existing `GetOutcome` (`neo4j.go:155` → `getNode`) returns only the node — never the PRODUCED edge's `confidence` or the intervention's `field` — and the resolution flow needs both (the on-demand `EnqueueResolved` row's NOT-NULL `confidence`, and the field key for the corrected-value map). The resolution and excerpt handlers use this instead of `GetOutcome`. The struct **must include `GoalID`** (read via `outcomeFromNode`, which already maps the node's top-level `goal_id`) — it is what the handlers' goal-mismatch 404 checks against.
     - `UpdateOutcomeValue(ctx, outcomeID string, value map[string]any, provenance *domain.ProvenanceLocator) error` — `MATCH (o:Outcome {id: $id}) SET o.value = $value, o.provenance = $prov` via `marshalProvenance`; complements the existing `UpdateOutcomeVerification` for the correction path.
   - Stub all three on `fakeRepo` in `internal/orchestrator/server_test.go`; add integration coverage alongside existing graph tests.

5. **Queue routing on extract outcomes**
   - In `processExtractionCandidate` (`internal/orchestrator/hypothesis.go:294`), after a successful `writeExtractionTriplet`: if `confidence < effectiveThreshold(goal)`, `queue.Enqueue` with the outcome id, field, value, locator snapshot, and confidence. Enqueue failure logs and continues (queue routing must never fail the branch — same posture as audit-write failures at `hypothesis.go:397`).
   - `writeExtractionTriplet` returns the created `outcomeID` (signature change from bare `error`) so the caller can enqueue and gate on it. `writeTriplet` gets the symmetric change — its `outcomeID` (created internally at `hypothesis.go:378`) is what the query path's histogram `Add(outcomeID, confidence)` keys on in Step 8.

6. **REST endpoints (new `internal/orchestrator/verification.go`)**
   - `GET /goals/{id}/verifications?status=pending|resolved` — lists queue entries for the goal (`lookupGoal` 404; heuristics.go query-param pattern); response rows carry `queue_id`, `outcome_id`, `field`, `extracted_value`, `provenance`, `confidence`, `status`, `resolution`, `corrected_value`, timestamps, plus the goal's `effective_threshold` and `epoch_mode` at the top level so the UI needs no second call.
   - `GET /goals/{id}/outcomes` — on-demand browse of **all** extract outcomes (at-or-above-threshold ones included) via `repo.ListExtractionOutcomes`; snake_case DTOs with `verification_status` and `confidence` so the UI can pull up any outcome, not just queued ones.
   - `POST /goals/{id}/verifications/{outcomeID}` — the resolution endpoint, body `{"action": "confirm"|"correct"|"reject", "corrected_value": "..."}` (`MaxBytesReader` + `json.NewDecoder` per the `audit.go:43-46`/`chat.go:81-83` precedent; 422 on unknown action or `correct` without a non-empty `corrected_value`). The handler performs writes across two datastores, so the **order and each failure's disposition are part of the design**:
     1. **Validate** — `lookupGoal` → 404; `repo.GetExtractionOutcome(outcomeID)` → 404 if missing or `GoalID` mismatch (also yields the field name and current edge confidence used below); decode/validate body → 422.
     2. **Claim (Postgres, the concurrency gate)** — `queue.Resolve(outcomeID, resolution, correctedValue)` when `GetByOutcome` finds a pending row, else `queue.EnqueueResolved(...)` (the on-demand path — keeps the queue table the complete resolution history), populating the row from `GetExtractionOutcome`: `confidence` from the edge, `field`, provenance snapshot, and NOT-NULL `extracted_value` derived as `Value[field]` string-asserted (a missing or non-string entry is a data-integrity 500 — extraction always writes the field-keyed string, `hypothesis.go:454`). Either method returning `ErrAlreadyResolved` routes to the **repair check** defined by the invariant below. Claiming first is what prevents a double resolution (or a double-click race) from re-firing graph writes with a *different* action — e.g. confirm-then-reject interleaving would otherwise leave the graph rejected while the queue says confirmed.
     3. **Graph write-through** — on **confirm**: `repo.UpdateOutcomeVerification(outcomeID, domain.VerificationConfirmed, 1.0)`. On **correct**: fetch pages via `s.sandbox.DocumentText` (sandbox faults → 502 per `submit.go:310` classification), recompute `locateProvenance(pages, correctedValue)` (nil when no exact match — same fallback as initial extraction), `repo.UpdateOutcomeValue(outcomeID, map[field]corrected, locator)`, then `UpdateOutcomeVerification(..., domain.VerificationCorrected, 1.0)`. On **reject**: `UpdateOutcomeVerification(outcomeID, domain.VerificationRejected, 0.0)` — rejected outcomes are excluded from the search by status regardless (`SearchEligibleStatuses`); zeroing the edge confidence makes the histogram reflect the rejection. Failure handling for everything after the claim — the correct-path `DocumentText` fetch (502) and `locateProvenance` as much as either graph write — is governed by the invariant below: the claim **owner** compensates with a guarded un-claim and returns 500/502 for the analyst to retry; a **repairer** never un-claims. Either way an incomplete resolution is *conservative* (the outcome stays `unverified`, which `SearchEligibleStatuses` keeps out of the Sleep Cycle — fail-safe, never fail-open) and **self-healing** (the next attempt repairs it).
   - **Resolution state-machine invariant** — the source of the repeated edge cases in earlier drafts, so it is stated once and binds every path above. The (queue row, graph outcome) pair only moves forward through `pending/unverified` → *(claim)* → `resolved/unverified` → *(write-through)* → `resolved/⟨confirmed|corrected|rejected⟩` → *(audit)*.
     1. **Ownership**: exactly one request wins the claim (guarded `Resolve` rows-affected, or `EnqueueResolved`'s insert). Only the owner may un-claim, only within the same request, via `queue.Unclaim` (Step 2) — its resolution-value guard means it never reverts a claim written by a different request. Before un-claiming, the owner re-reads the graph status and **skips the un-claim if the outcome is no longer `unverified`** (a concurrent repairer finished the write-through the owner's own write lost to — the resolution has in fact landed, so the row must stay `resolved`).
     2. **Repair entry**: a request that receives `ErrAlreadyResolved` re-reads the row via `GetByOutcome`. Row `pending` (the `EnqueueResolved` insert lost to the loop's own `Enqueue` in the triplet-write→enqueue window): retry as a normal `Resolve` claim — never repair, the stored resolution would be NULL. Row `resolved` + graph status already resolved: **409**, nothing to do. Row `resolved` + graph still `unverified`: a prior attempt died between claim and write-through — perform the write-through **from the stored row's resolution and `corrected_value`** (the request body is ignored; if it differs from the stored resolution, still repair from the stored values, then 409 so the caller knows their action didn't apply), then the flow-4 audit with `"repair": true` in the detail, then 200.
     3. **Repairer never un-claims**: it owns no claim, so on any repair-path failure it returns 5xx and leaves the row `resolved` for the next attempt — the row must not be reverted to `pending`.
     4. **Idempotent window, transient divergence accepted**: a repairer racing the live owner (both see `resolved/unverified` mid-flight) writes identical graph SETs derived from the same stored row, so racing writes cannot conflict on values. What the invariant guarantees is *convergence*, not per-step atomicity: brief windows exist where queue and graph disagree — e.g. a correct-path `UpdateOutcomeValue` lands but `UpdateOutcomeVerification` fails and the owner un-claims (queue `pending`, graph holding the corrected value, still `unverified`) — and every such state is fail-safe (`unverified` never enters the search) and converges on the next resolution attempt, which re-claims and rewrites both graph properties. The race can produce a duplicate audit row — benign in an append-only log and distinguishable by the `repair` flag; R13's guarantee (every resolution audited) is at-least-once here, never zero (the repair path audits precisely because the dead owner's flow never reached flow 4).
     Worked failures this invariant must keep covered: correct-path sandbox 502 after claim (owner un-claims, retry works); crash between claim and write (repair completes + audits); concurrent request during a live owner's window (idempotent repair or 409, no foreign un-claim); `EnqueueResolved` colliding with the loop's fresh `pending` row (retry as claim, never NULL-repair); double-click on a fully resolved entry (plain 409).
     4. **Audit (mandatory, not best-effort)** — `recordAudit(ctx, "hitl_verification_resolution", "verification", {optimization_function_id, outcome_id, action, corrected_value?, confidence_at_queue})`. R13 mandates an audit record for every HITL resolution, so this deliberately deviates from the loop's log-and-continue posture (`hypothesis.go:397`): on audit failure return **500 with a body stating the resolution itself persisted** — the graph and queue writes stand (visible on refresh), and the 500 surfaces the missing compliance record instead of silently dropping it.
     5. **SSE re-push + respond** — adjust the live run's histogram if one is tracking this outcome and publish (Step 8); this in-process step never fails the request. Respond `writeJSON(w, 200, ...)` with the resolved entry.
   - `GET /goals/{id}/outcomes/{outcomeID}/excerpt` — excerpt/page retrieval: `GetExtractionOutcome` → 404 if missing **or its `GoalID` mismatches the URL's `{id}`** (the same goal-scoping rule as the resolution handler — otherwise goal X's locator would slice goal Y's document); `s.sandbox.DocumentText(goal.DataSourceRef)`; with a non-nil locator return `{"fallback": false, "page": N, "char_start": a, "char_end": b, "excerpt": pages[N][a:b], "page_text": pages[N]}` (byte-offset slicing with bounds-guard — out-of-range locator degrades to the fallback shape rather than panicking); with a nil locator return `{"fallback": true, "pages": [...]}` (full document, since a nil locator carries no page index). This reuses the sandbox's `pdfPages` routine so the excerpt matches what produced the locator. Known cost, accepted for MVP: the sandbox is stateless, so every excerpt view (and every `correct` resolution) re-parses the whole PDF in a synchronous cross-service round trip — an analyst paging through an N-entry queue triggers N full parses. Note this in the handler comment; a goal-scoped page-text cache is the follow-up if queue review feels slow, not part of this plan.
   - Register all four routes in `Routes()` (`server.go:156`).

7. **Blocking-mode epoch gate**
   - In `processExtractionCandidate`, after queue routing and the existing `Improves`/depth checks, when `goal.EpochMode == store.EpochBlocking` **and** this outcome was enqueued: poll `queue.GetByOutcome` on a ticker (package const, e.g. 2s) under the loop ctx until the entry resolves. On `rejected` → return (prune the branch — its value is known wrong, so nothing below it is trustworthy). On `confirmed`/`corrected` → continue recursion, keeping the model's original confidence as the `parentConfidence` comparison baseline (the 1.0 trust write is a verification marker, not a pruning signal — children would never beat 1.0). `speculative` mode (default): no wait, current behavior — the loop never blocks.
   - The wait runs under the run's deadline, which for blocking-mode goals is the dedicated `blockingLoopTimeout` (Step 3, default 24h) rather than the 30-minute `loopTimeout` — see Context for why, and for the explicit statement that the sequential DFS stalls everything behind the waiting node. Context cancellation/deadline expiry aborts the wait cleanly (run fails with a clear reason via the existing `runLoop` defer, not a hang).
   - **SSE keepalive:** blocking mode is the first feature that holds a subscribed stream open for hours with zero frames (the stalled DFS emits nothing until resolution), and idle intermediaries reap frameless connections. Add a periodic SSE comment frame (`: keepalive\n\n`, ~30s ticker) to `handleStream` (`stream.go:14`) — protocol-standard, invisible to event parsing, and it keeps the arborette-10 UI's connection alive through long waits (reconnect+replay still covers a drop, so this is robustness, not correctness).

8. **Confidence-bin distribution over SSE**
   - New `confidenceHistogram` type in `internal/orchestrator/verification.go`: 10 fixed bins (`[0.0,0.1) … [0.9,1.0]`), mutex-guarded; `Add(outcomeID, confidence)` (also records `map[outcomeID]confidence` so a later resolution can find and move this outcome's bin), `Rebin(outcomeID, newConfidence) bool` (false when the outcome isn't tracked), `Payload()` → `{"bins": [10 counts], "total": N}`.
   - **Run-scoped registry (this is what keeps the re-push per-run):** the `Server` holds `map[goalID]*confidenceHistogram`, mutex-guarded; the loop registers its histogram at start and deregisters in the `runLoop` defer just before `hub.Complete`. Outcome nodes carry no run identifier and loops append triplets across runs, so a graph-wide recompute (`ListExtractionOutcomes`) would conflate every historical run's outcomes onto the active run's stream — the registry avoids that entirely.
   - **Registry/hub serialization (the leak guard):** registry presence alone does not make `Hub.Publish` safe — the resolution handler and the `runLoop` defer race, and the interleaving *lookup → deregister+`hub.Complete` → publish* would lazily recreate an unevictable `runState` (the leak the survey flagged). Therefore the registry mutex serializes the whole re-push: the handler holds it across *lookup → `Rebin` → `hub.Publish`*, and the defer takes the same mutex to deregister **before** it publishes `loop_complete`/calls `hub.Complete`. Once deregistration wins, the handler finds no entry and publishes nothing; once the handler wins, its publish lands before `Complete`. Deregistration is **compare-and-delete** (delete only if the stored pointer is the run's own): `handleTriggerLoop` has no in-progress guard and re-triggering is a supported operation, so a second concurrent run for the same goal overwrites the registry entry — compare-and-delete stops run A's defer from tearing down run B's live histogram (A's own mid-run re-pushes simply stop, consistent with the two runs' frames already interleaving on the shared goal-keyed hub stream).
   - **In-run incremental path**: each loop entry point (`runDocumentLoop` at `hypothesis.go:253` and the tabular loop driving `processCandidate`) owns one registered histogram instance threaded through its recursion; after each successful triplet write (`writeExtractionTriplet` / `writeTriplet`) it adds the PRODUCED confidence and publishes `Event{Type: "confidence_distribution", Coalesce: true, Payload: hist.Payload()}` — same `optimization_function_id` key, interleaved with `triplet` events on the existing stream. R20's acceptance spans *all* triplets in a run, so the query path emits too; its confidences are fixed 1.0 by construction (R7), giving a degenerate top-bin histogram, which is correct and lets the UI treat both goal kinds uniformly.
   - **Replay-ring coalescing:** one histogram frame per triplet roughly doubles a run's frame count, and `replayBufferSize = 256` (`hub.go:5-10`) is sized so a mid-run reconnect "replays the whole run rather than dropping the earliest triplets" — naive publishing would evict early `triplet` frames and regress that stated guarantee. Since only the *latest* cumulative histogram matters, add a `Coalesce bool` field to `Event` **tagged `json:"-"`** (it is a hub-internal routing hint; untagged it would serialize `"Coalesce":false` into every SSE frame — `triplet`, `branch_failure`, all of them — silently changing the wire shape arborette-10 consumes, since `writeSSEFrame` marshals the whole `Event`): `Hub.Publish` replaces the run buffer's previous frame of the same `Type` (instead of appending) when set, while fanning out to live subscribers normally. `internal/orchestrator/hub_test.go` covers coalescing (buffer holds one histogram frame after N publishes; replay order preserved) alongside normal fan-out.
   - **Out-of-band re-push (mid-run resolutions only)**: the resolution handler looks up the goal's registered histogram; if present and `Rebin(outcomeID, newConfidence)` returns true (1.0 on confirm/correct, 0.0 on reject — the outcome belongs to the live run), it publishes the updated payload. When no live run exists or the outcome predates it, there is deliberately **no re-push**: a finished run's stream is closed (`Hub.Complete`), and post-run clients get current state from `GET /goals/{id}/outcomes` instead. This replaces any graph-recompute path — the SSE distribution is strictly per-run, matching R20 and the in-run frames the UI has been accumulating.
