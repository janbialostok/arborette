# Plan: Sandbox Execution Service

## Context

The Sandbox Execution service is where the system's core empirical claim gets proven or disproven: every LLM-proposed intervention becomes a deterministic, read-only query over the analyst's actual data, never a hallucinated guess. It's deliberately a separate, stateless, horizontally-scalable service from the Orchestrator — it owns the only DuckDB-over-object-store access path in the system, used both for schema introspection at goal intake and for executing intervention queries during the hypothesis loop. Keeping intervention execution deterministic (parameters compiled into a query, not LLM-generated SQL) is what makes it safe to run untrusted-shaped LLM output against real data.

Scope note: this shell delivers only the tabular `query` path (partial R6). The spec's R17 generalizes the intervention-execution contract into a `query`/`extract` discriminated union; the `extract` path over document sources is a later shell (`arborette-07-multi-modal-extraction`). To keep that shell additive, this plan designs the request contract with an explicit intervention `type` seam (defaulting to `query`) and keeps DuckDB isolated to the sandbox so the document path can add its own execution branch without reworking this one. See **Downstream compatibility** under Verification.

- **No HTTP server exists — greenfield for the repo.** No router/middleware/handler/JSON-response helper; `docker-compose.yml` publishes **no ports** for any app service (`sandbox` block, no `ports:`). Std-lib `net/http` + `http.ServeMux` is the consistent choice — no web framework is in `go.mod`.
- **Config is env-based**: struct field + `Load()` wiring (`config.go:16-22`, `117-153`) + `.env.example` entry. There is currently **no port/listen-address config**; a `SandboxConfig{Port}` with an `env("SANDBOX_PORT", ...)` default is the idiomatic addition. `Load` never validates per-service (`config.go:110-116`).
- **Infra constructors take primitive args, not `Config`** (`objectstore.NewClient(...)` at `client.go:30`, `graph.NewNeo4jRepository`, `NewOllamaProvider`). New constructors accept the object-store client + primitives, not the whole `Config`.
- **Package doc comment** as a full paragraph on the first line of the package's primary file, explaining *why* the seam exists (`datasource.go:1-4`, `objectstore/client.go:1-3`).
- **Errors**: lowercase `fmt.Errorf("verb noun %q: %w", ...)`, wrapped, no logging inside library code; `log.Fatalf("<service>: ...")` only in `main`. Sentinel discrimination via `errors.As` (`client.go:95-102`).
- **Interface-first pluggable seams** (`graph.Repository`, `embedding.Provider`, `datasource.DataSource`) with a `var _ Iface = impl{}` check.
- **Testing: two tiers.** Pure-unit table tests run always (`config_test.go:33-52` slice-of-cases style); anything touching infra calls `testutil.RequireIntegration(t)` first and skips cleanly (`objectstore_test.go:15`, `store_test.go:14-19`). Run with `-p 1` per AGENTS.md.

### Proposed Alignment

Reuse the existing seams and types wholesale — implement `datasource.DataSource` for the file reader, drive it with `objectstore.Client` and the `domain.EvaluationMatrix/Target/Constraint` types, add config via the env-helper pattern, follow the `ctx`-first / `%w`-wrap / interface-with-compile-check / integration-gated-test conventions. The HTTP layer is genuinely new (std-lib `net/http` + `http.Server` with signal-driven graceful `Shutdown`, extending `internal/service`), plus a compose port and a `SANDBOX_PORT` field. Keep the service stateless: take the data-source ref and intervention parameters from the request body. **One deliberate deviation from the survey's placement suggestion:** the concrete file reader, query compiler, and handlers live in a new sandbox-owned package (`internal/sandbox`), *not* in `internal/datasource`, so the CGO DuckDB dependency stays isolated to this one service — putting it in the shared interface package would force CGO on every importer of the interface (orchestrator, mcpserver, sleepcycle). `internal/datasource` stays the pure, dependency-free interface it is today.

## DuckDB access-path invariants (load-bearing)

Steps 4–7 all touch one seam — the DuckDB-over-a-staged-file query path — and every review round has surfaced a defect there when one of these invariants was violated. Treat them as the contract the code must satisfy; the enumerated failures are the concrete things each prevents:

1. **File paths are SQL literals, never bound parameters.** DuckDB resolves `read_csv_auto`/`read_parquet` file arguments at *bind* time and rejects a `?` there. Embed the staged path as a single-quote-escaped literal. *Safe because the path is a server-generated `os.MkdirTemp` name, never request-derived* — prevents "introspection/execute fail before running" and reintroducing injection via a ref-derived path.
2. **Read-only-ness comes from emitting only `SELECT`/`DESCRIBE`, not from `access_mode`.** The engine is a transient in-memory DuckDB (`sql.Open("duckdb","")`); `access_mode=read_only` requires an existing on-disk DuckDB *database* file and errors on an in-memory one (and a CSV/Parquet file is not a database). Prevents "hard startup error on first query."
3. **Every aggregate is `CAST(... AS DOUBLE)` and every numeric aggregate is guarded to numeric columns.** `count`→`BIGINT`, `sum`→`HUGEINT`, `min`/`max`→the column's own type (`VARCHAR`/`DATE`); an unguarded `sql.NullFloat64` scan then fails as an opaque 500. Prevents "min/max/sum returns a value the scan can't hold."
4. **One `stage(ctx)` downloads + configures the engine once; both `Introspect` and `Execute` share it.** Prevents "Execute re-materializes the object" and "Execute has no `cols` to validate against."
5. **Bounded download (`maxObjectBytes+1` overflow check) + isolated spill dir bounded by `SANDBOX_MAX_TEMP_DIR_SIZE`, with cleanup that closes the `*sql.DB` and removes the dir.** Prevents "silent truncation → wrong aggregate," "disk exhaustion," "leaked DuckDB handles under load," and "spill fails on a non-writable container cwd."

3. **Add a graceful HTTP-server helper to `internal/service`**
   - Add `RunHTTPServer(name, addr string, handler http.Handler) error` (new file `internal/service/httpserver.go`, or extend `shutdown.go`) mirroring `WaitForShutdown`'s style: start `&http.Server{Addr: addr, Handler: handler}` in a goroutine that sends its `ListenAndServe` result (ignoring `http.ErrServerClosed`) to an error channel, then `select` over **both** that error channel and a SIGINT/SIGTERM signal channel (`signal.Notify`). If `ListenAndServe` fails first (port already bound, bad addr), return that error immediately instead of blocking on the signal forever — otherwise a fatal startup failure is masked and the process lingers with no listener. On a signal, call `srv.Shutdown(ctx)` under a bounded timeout context and return its result. Log readiness and the received signal under `name`, reusing the signal pattern from `shutdown.go:15-21`. The caller (`main`) `log.Fatalf`s a non-nil return.

4. **File-based `DataSource` implementation (`internal/sandbox/filesource.go`)**
   - New package `internal/sandbox` with a `FileSource` type constructed from the `*objectstore.Client`, a `dataSourceRef` key, the `maxObjectBytes` limit, and the `maxTempDirSize` string (primitive args, per the infra-constructor convention). Package doc comment paragraph explaining the seam (why DuckDB lives here and not in `datasource`).
   - `Kind() datasource.SourceKind` returns `datasource.KindTabular`. Add `var _ datasource.DataSource = (*FileSource)(nil)`.
   - **Shared staging helper** `stage(ctx) (db *sql.DB, tableFn string, cleanup func(), err error)` — the single path both `Introspect` and `Execute` use, so the object is downloaded and the DuckDB engine configured exactly **once** per request (F1):
     - Create a unique per-request working dir with `os.MkdirTemp`. The returned `cleanup` **closes the `*sql.DB`** (once opened — every request opens a fresh one, and an unclosed `sql.DB` leaks DuckDB connections/native handles under load, F3) and then `os.RemoveAll`s the dir (covers the staged object **and** any DuckDB spill); it is invoked via `defer` on **every** path, including a failure after `sql.Open`.
     - `objectstore.Client.Get` the ref and stream it into a file in that dir — DuckDB reads from a path, and `Get` yields a stream. **Bounded materialization (P1-E/F3):** copy through `io.LimitReader(r, maxObjectBytes+1)` and reject when the copy yields more than `maxObjectBytes` bytes — `LimitReader` capped at exactly the max silently truncates (a CSV cut at a row boundary would yield a silently wrong aggregate), so read one extra byte to *detect* overflow rather than swallow it. Run the copy under `ctx` so a slow `Get` is cancellable.
     - Open a **transient in-memory** DuckDB (`sql.Open("duckdb", "")` — empty DSN; **not** `access_mode=read_only`, which requires an existing on-disk DuckDB database and errors on an in-memory one — a CSV/Parquet file is not a DuckDB database file). Immediately `Exec` `SET temp_directory='<the per-request dir>'` and `SET max_temp_directory_size='<maxTempDirSize>'` (the `SANDBOX_MAX_TEMP_DIR_SIZE` value, e.g. `2GiB` — a DuckDB size string, not a bare int): an in-memory DuckDB otherwise defaults its spill dir to `./.tmp` under the working directory, which on the distroless `cc-debian12` image is not writable — so any *spilling* query (large `GROUP BY`/sort/join; a bare streaming `avg` never spills) would fail. Pointing spill at the controlled writable dir removes that failure and bounds disk blast radius. Both are GLOBAL-scope settings, valid via `database/sql` `Exec`.
     - Detect format from the ref's extension (`.csv`/`.parquet`) and build `tableFn` = `read_csv_auto('<staged path>')` or `read_parquet('<staged path>')`. The staged path is a **server-generated** name under the `os.MkdirTemp` dir (never request-controlled), embedded as a single-quote-escaped SQL literal — DuckDB resolves table-function file arguments at **bind time** and rejects a `?` placeholder there, so the path cannot be a bound parameter. (Local staging is chosen over DuckDB `httpfs` deliberately: it reuses the existing S3 client/credentials and keeps the query path off extra network config; the size cap bounds disk cost.)
   - `columns(ctx, db, tableFn) ([]datasource.Column, error)` runs `DESCRIBE SELECT * FROM <tableFn>` and maps the result rows into `datasource.Column`s.
   - `Introspect(ctx) (*datasource.Schema, error)` = `stage` → `columns` → `datasource.Schema{Kind: KindTabular, Columns: [...]}`. Read-only-ness is guaranteed by emitting only `SELECT`/`DESCRIBE` over the ephemeral connection, not by any `access_mode`.

5. **Deterministic intervention-parameter → DuckDB query compiler (`internal/sandbox/compile.go`)**
   - `compileQuery(tableFn string, cols []datasource.Column, agg string, target domain.Target, filters []domain.Constraint) (sql string, args []any, err error)` producing a single `SELECT CAST(<AGG>("<target field>") AS DOUBLE) FROM <tableFn> WHERE ...`, where `tableFn` is the `read_csv_auto('<escaped path>')` / `read_parquet('<escaped path>')` string built in Step 4 (the path is a server-generated literal, per P0-A — not a `?`). The explicit `CAST(... AS DOUBLE)` normalizes every allowed aggregate — `count` (`BIGINT`), `sum` (`HUGEINT` over integers), and `avg`/`min`/`max` — to one `DOUBLE`/`NULL` return, so the scan contract is uniform (P2-F) and go-duckdb never hands back a `*big.Int` or `VARCHAR`.
   - **Injection safety is the crux:** SQL cannot parameterize identifiers, so (a) validate every `target.Field` and every `filter.Field` against the actual introspected column set (`cols`) — reject unknown fields with a wrapped error; (b) quote validated identifiers with double-quotes, escaping embedded `"`; (c) map `agg` through an allowlist (`avg`/`sum`/`min`/`max`/`count`) — reject anything else; (d) map `Constraint.Op` (`lt`/`lte`/`gt`/`gte`) to `<`/`<=`/`>`/`>=`; (e) bind every **`Constraint.Value`** (the only upstream-influenced input) as a `?` parameter in `args`, never interpolated. This guarantees only schema-present columns, allowlisted aggregations, and fixed operators reach the SQL string, and every threshold value is bound. `TargetDirection` informs result interpretation, not the SQL.
   - **Column-type guard (P2-F/F2/F4):** define `isNumeric(Column.Type)` as membership in the canonical DuckDB numeric set — `TINYINT`, `SMALLINT`, `INTEGER`, `BIGINT`, `HUGEINT`, `UTINYINT`, `USMALLINT`, `UINTEGER`, `UBIGINT`, `UHUGEINT`, `FLOAT`, `DOUBLE` — **plus** a `strings.HasPrefix(t, "DECIMAL")` case, since `DESCRIBE` reports fixed-point columns as `DECIMAL(p,s)` (common in Parquet) and an exact-string match would spuriously reject them. Reject `avg`/`sum`/`min`/`max` over a non-numeric **target** column with a clean 400 — `min`/`max` over a `VARCHAR`/`DATE` return that type, which the `CAST AS DOUBLE` rejects and no numeric Outcome can represent. **Apply `isNumeric` to every filter field too (F4):** each `Constraint.Value` is a `float64`, so a `lt`/`gt` predicate on a non-numeric column reaches DuckDB and fails as a runtime cast error (a 500); reject it up front as a 400. `count` is allowed over any column type. Empty-set behavior (F5): `avg`/`sum`/`min`/`max` filter to `NULL` → scanned via `sql.NullFloat64` → nil → JSON `null`; **`count` yields `0`, not `NULL`** (standard SQL), so an all-filtered-out `count` returns `0.0` (Step 7).
   - `Execute(ctx, agg, target, filters) (*float64, error)` on `FileSource` calls the shared `stage(ctx)` (Step 4) **once** — obtaining the configured in-memory `db`, the `tableFn`, and a `cleanup` (deferred) — runs `columns(ctx, db, tableFn)` to get `cols`, then `compileQuery(tableFn, cols, ...)`, executes the single `SELECT` scanning into `sql.NullFloat64`, and returns the scalar aggregate (nil for empty/NULL). This shares one download + one engine with introspection's path rather than re-materializing the object. Read-only-ness comes from emitting only `SELECT`.

6. **Schema-introspection endpoint (`internal/sandbox/server.go`, `POST /introspect`)**
   - `Server` type holding the `*objectstore.Client`, the `maxObjectBytes` limit, and the `maxTempDirSize` string; a `Routes() http.Handler` returning an `http.ServeMux` with the two endpoints; constructed in `main`.
   - **JSON contract (P1-D):** every request/response struct carries explicit snake_case `json:"..."` tags. `datasource.Schema`/`Column` are tag-less today, so define sandbox-local DTOs with tags (`schemaDTO{ Kind string; Columns []columnDTO }`, `columnDTO{ Name, Type string }`) and map from the domain types — do **not** add tags to the shared `datasource` package.
   - Request `IntrospectRequest{ DataSourceRef string \`json:"data_source_ref"\`; Targets []domain.Target \`json:"targets"\` }`; decode with `json.NewDecoder`. Build a `FileSource` for the ref, call `Introspect`, then bind each `Target.Field` to a column. **Binding algorithm:** case-insensitive exact match of `Target.Field` against `Column.Name`; no match → empty `Column`, `Matched: false`; a target matching more than one column case-insensitively is an ambiguous-schema error surfaced as a 400. Respond `IntrospectResponse{ Schema schemaDTO \`json:"schema"\`; TargetBindings []TargetBinding \`json:"target_bindings"\` }` where `TargetBinding{ Target string \`json:"target"\`; Column string \`json:"column"\`; Matched bool \`json:"matched"\` }`, so the Orchestrator learns which columns back the optimization targets (R2).
   - **Error contract:** add `writeJSON(w, status, v)` and `writeErr(w, status, msg)` helpers (the repo has none). Errors return `{"error":"<message>"}` — `400` for a malformed body / unknown field / ambiguous binding, `404` for a missing object-store key (map the object-store not-found via `errors.As`), `500` otherwise — never a bare panic.

7. **Read-only execution endpoint (`internal/sandbox/server.go`, `POST /execute`)**
   - Request `ExecuteRequest{ DataSourceRef string \`json:"data_source_ref"\`; Type domain.InterventionType \`json:"type"\`; Aggregation string \`json:"aggregation"\`; Target domain.Target \`json:"target"\`; Filters []domain.Constraint \`json:"filters"\` }`. An empty `Type` defaults to `query`; reject any value other than `query` with a clear "unsupported intervention type" 400 (the `extract` branch is `arborette-07`), keeping the discriminator seam in place.
   - **Call model (P1-D):** `/execute` measures **one** target aggregate per call — the Orchestrator fans out one `/execute` per `EvaluationMatrix` target (the sandbox stays a single-measurement primitive; assembling the per-goal matrix is the Orchestrator's job in `arborette-02`). State this explicitly so shell 02 does not expect a batch endpoint.
   - Build the `FileSource`, call `Execute`, and return `ExecuteResponse{ Value map[string]any \`json:"value"\` }` shaped like `domain.Outcome.Value` — `{"<target field>": <measured aggregate>}`, where the aggregate is a JSON number, or `null` when a `sum`/`avg`/`min`/`max` filters to an empty set; **`count` over an empty set is `0`, not `null`** (standard SQL semantics, F5) — so the Orchestrator can write the causal triplet's Outcome directly (R6/R7). Use the same `writeJSON`/`writeErr` helpers and error-status mapping as `/introspect`.

8. **Wire the server in `cmd/sandbox/main.go`**
   - Keep `config.Load()` and the `objectstore.NewClient` + `EnsureBucket` wiring (`main.go:17-37`). Drop the neo4j wiring — the sandbox writes no triplets (the Orchestrator does), so `graph.NewNeo4jRepository`/`InitSchema` (`main.go:22-29`) are unused here; removing the `InitSchema` call is safe because the orchestrator/mcpserver/sleepcycle mains already run it. Update the "wired ..." log line to mention the HTTP listener.
