# Plan: Web UI — Causal Surfaces

## Context

Analysts are the primary persona, and V2 invisible in the web UI undercuts the product: the analyst needs to see *why* a segment matters (causal vs merely correlated), trigger verification, read confounded/not-identifiable answers in plain language, and correct the discovered graph without being required to review it. This plan ships the full surface: causal-graph view with edge correction (reusing the HITL correction interaction pattern), verify affordances on finding cards, epistemic badges everywhere edges render, and verification results with the sufficiency caveat attached.

Covers spec R32 in full and R13 partially (the caveat carried on all web renderings; unknown/missing `epistemic_source` treated as `observational`).

**Plan decision — badge sourcing:** live/trace triplet DTOs (`TraceTriplet`, `QueryTripletPayload` in `web/lib/orchestrator.ts`) do not carry `epistemic_source`. Rather than extending orchestrator DTOs (out of this shell's scope), finding/triplet badges are derived client-side by joining the goal's causal-verifications list on the intervention id: a latest non-stale `causally_verified` record ⇒ `causal_inferred`, anything else ⇒ `observational`. The join runs only on surfaces with a goal context and a verifications producer (the causal tab, goal-scoped HeuristicBrowser rows); the live run card gets a Verify button but no badge (Step 3). This matches R11's "serve only the latest non-superseded causal edge" reading.

**Plan decision — graph rendering:** no visualization library exists in `web/` (deps are only next/react/react-dom/undici) and no SVG precedent. The graph view is hand-rolled SVG/CSS in the `EffectReadout`/`ConfidenceHistogram` visual idiom (layered column layout + edge lines), not a new dependency.

## Pattern Survey

### Analogous Features

**BFF proxy routes (JSON + SSE + POST)**
- `web/app/api/orchestrator/goals/[id]/verifications/route.ts:6` — canonical GET JSON route: `await params`, then `forward(req, "/goals/${encodeURIComponent(id)}/verifications")`. Every route sets `export const runtime = "nodejs"` and `export const dynamic = "force-dynamic"`.
- `web/app/api/orchestrator/goals/[id]/sleep-cycle/route.ts` and `.../hypothesis-loop/route.ts` — POST JSON routes calling `forward()`; the shape the new corrections and verify POST routes mirror.
- `web/app/api/orchestrator/goals/[id]/verifications/[outcomeID]/route.ts:8` — nested-param POST using `forwardSubmit` (5-min cap) because that write re-reads a document. Causal-verify dispatch returns 202 quickly ⇒ plain `forward`, not `forwardSubmit`.
- `web/app/api/orchestrator/goals/[id]/stream/route.ts:6` — SSE GET via `forwardStream`. The orchestrator has a single SSE endpoint (`GET /goals/{id}/stream`); verification transitions ride it, so **no new SSE route is needed**.

**Orchestrator endpoints this UI calls** (registered `internal/orchestrator/server.go:275-278`):
- `GET /goals/{id}/causal-graph` → `causalGraphDTO` (`internal/orchestrator/causalgraph.go:37`): `{columns:[{name,kind}], edges:[{col_a,col_b,direction,provenance,confidence,status}], meta:{version,excluded_columns,budget_truncated,test_count,discovered_at}}`. 404 when no graph discovered yet.
- `POST /goals/{id}/causal-graph/corrections` (`internal/orchestrator/corrections.go:60`) — body `{op,from,to,direction?}`; `op` ∈ `flip|delete|add`, `direction` ∈ `""|a_to_b|b_to_a|undirected` (enums `internal/domain/causal.go:45-62`). Returns `{op,columns,graph_version,redispatched}`. Errors: 400 validation, 404 no graph, 409 `"another correction or discovery is in progress"`, 422 unknown column / no such edge.
- `POST /goals/{id}/findings/{interventionID}/verify` (`internal/orchestrator/causalverify.go:61`) — no body; returns **202** `{optimization_function_id, intervention_id}`; 404 finding missing/other goal, 502 `"verifier unavailable"`.
- `GET /goals/{id}/causal-verifications` (`causalverify.go:137`) → newest-first array of `causalVerificationDTO` (`causalverify.go:117`): `{id,intervention_id,graph_version,status,naive_effect,adjusted_effect,adjustment_set,refutation_score,confidence,stale,created_at,updated_at}`. **Nullable effects are pointers → JSON `null`** until terminal; render null, not 0. Status values (`internal/store/causalverifications.go:19-24`): `pending|causally_verified|confounded|not_identifiable|unsupported_objective|failed`.

**SSE verification event types** (delivered on the existing goal stream as `Event{Type, Payload}`):
- Verifier-relayed events are **wrapped**: `handleVerificationEvent` publishes `Event{Type: "verification", Payload: req.Event}` (`internal/orchestrator/verificationevents.go:38`), so the wire frame's top-level `type` is the constant `"verification"` and the transition name sits at `payload.type` — one of `verification_dispatched`, `verification_refutation`, `verification_outcome` (carries `status`), `verification_rejected`, `verification_error` (`internal/verifier/verify.go:60,70,244,250,86`), or the claim frames `claim_reified`, `claim_skipped`, `claim_construction_failed` (`internal/verifier/claim.go:40,98,270`).
- Orchestrator-direct events ARE top-level frame types: `causal_verification_dispatched` (`causalverify.go:103`), `causal_graph_corrected` (`corrections.go:106`).
- **Delivery constraint**: `Hub.PublishLive` (`internal/orchestrator/hub.go:126`) drops an event when no `runState` exists for the goal, and `Complete` evicts the run's state; `LiveRun` deliberately holds no open stream once a run is settled (`web/components/LiveRun.tsx:237-241`). Since verify is exercised against findings that exist only after Phase 1 completes, events published then reach nobody unless some client holds an open subscription — `Hub.Subscribe` lazily creates the `runState`, so a subscription owned by the causal surfaces makes delivery work. Two hub behaviors the design must respect: (1) `Hub.Complete` at loop end closes **every** subscriber channel — including the causal tab's — and `consumeStream` (`web/lib/sse.ts`) resolves on stream end without reconnecting, so the causal-tab hook must re-subscribe on stream end; (2) delivered frames land in `rs.buffer`, and `Subscribe`'s cancel evicts the lazily-created state only when the buffer is also empty (`hub.go:91`) — so a subscriber-created `runState` that received frames would outlive the analyst's visit. Implementation therefore also touched the hub — the one non-web change in this shell: `runState.loop` marks state a run owns, `PublishLive` deliberately claims no ownership, and `Subscribe`'s cancel evicts state no loop claims, identity-checked so it cannot delete a successor state `Complete` already replaced. Replayed causal frames reaching a later `LiveRun` subscriber are harmless: its `handleEvent` switch silently ignores unmatched types.

**HITL correction interaction (the pattern to reuse)**
- `web/components/VerificationQueue.tsx:97` `onResolved` — optimistic in-place update (no refetch); `VerdictRow.resolve` (`:369`) does pending-button state and on `OrchestratorError.status === 409` calls `onConflict()` → bumps a `generation` counter to refetch (`:54,138`). This is the draft-submit-optimistic-409-refetch pattern for edge corrections.
- `web/lib/review.ts` — domain logic kept out of the component (`isAwaiting`, `nextAwaiting`, normalizers). The causal surface gets an analogous `web/lib/causal.ts`.

**Epistemic / provenance rendering — greenfield.** Zero matches for `epistemic|observational|causal_inferred` in `web/**`. Domain source of truth: `internal/domain/domain.go:53-65` — `EpistemicObservational="observational"`, `EpistemicCausalInferred="causal_inferred"`, `EpistemicInterventional="interventional"`, and `CausalInferredCaveat = "causally supported (given the discovered model)"` (reuse this string verbatim). Surfaces needing the verify affordance + badge: `web/components/HeuristicBrowser.tsx:257` `EvidenceRow` / `:319` `VerificationBadge`, and `web/components/EffectReadout.tsx:13` (live triplet card).

### Reusable Utilities

- `web/lib/proxy.ts:82` `forward(req, path, {timeoutMs?})`; `:119` `forwardStream`. All four new routes use `forward`.
- `web/lib/orchestrator.ts:243` `requestJSON<T>`; `:207` `OrchestratorError` (carries `.status` for 409/404 discrimination); `:237` `errorMessage(err, fallback)`. New wrappers follow `listVerifications` (`:278`) / `resolveVerification` (`:305`); `encodeURIComponent` every path segment.
- `web/lib/sse.ts:12` `consumeStream<T>(body, onEvent, signal)`; `web/components/LiveRun.tsx:114` `handleEvent` is the `ev.type` switch to extend.
- `web/components/ui.tsx` — `Badge` (`:106`, tones `positive|neutral|warn|negative`), `Button` (`:32`, `variant` + `loading`), `Callout` (`:75`), `Panel`, `SectionLabel`, `Spinner`, `cn`. Badges are thin local `Badge` wrappers (the `VerificationBadge`/`StatusBadge` convention).
- `web/lib/format.ts:3` `renderValue`; `EffectReadout.tsx:99` `fmt(n)` (`—` for non-finite) is the pattern for nullable naive/adjusted effects.

### Convention Anchors

- **Route placement**: `web/app/api/orchestrator/<mirror-of-orchestrator-path>/route.ts`, one handler per method, `runtime="nodejs"` + `dynamic="force-dynamic"`, `params` is a `Promise` awaited first.
- **Typed-client boundary**: browser → `/api/orchestrator` via `orchestrator.ts` wrappers only; TS interfaces mirror Go `*DTO` snake_case shapes with doc comments on nullability.
- **Tab composition**: `web/components/GoalTabs.tsx:10` `TABS` array + lazy mount-on-visit (`visited` set `:31`), URL synced via `history.replaceState` (`:38`) to protect LiveRun's subscription.
- **Component-logic split**: pure logic in `web/lib/*.ts` with colocated vitest `*.test.ts` (`npm test` = `vitest run`); `web/lib/proxy.test.ts:26` shows `vi.stubGlobal("fetch", ...)` faking. No component tests exist — lib-only testing is the convention.
- **Error copy**: orchestrator `{error}` bodies are analyst-safe and surfaced verbatim; transport failures masked behind a fallback string.

## Implementation Steps

1. **Add BFF proxy routes for graph, corrections, and causal-verifications.**
   - Create `web/app/api/orchestrator/goals/[id]/causal-graph/route.ts` (GET), `web/app/api/orchestrator/goals/[id]/causal-graph/corrections/route.ts` (POST), `web/app/api/orchestrator/goals/[id]/causal-verifications/route.ts` (GET), and `web/app/api/orchestrator/goals/[id]/findings/[interventionID]/verify/route.ts` (POST), each mirroring `verifications/route.ts`: `runtime="nodejs"`, `dynamic="force-dynamic"`, `await params`, `forward()` with `encodeURIComponent` on every segment.
   - In `web/lib/orchestrator.ts`, add DTO interfaces `CausalGraph`/`CausalGraphEdge`/`CausalGraphMeta` and `CausalVerification` (with `naive_effect: number | null`, `adjusted_effect: number | null`, `refutation_score: number | null`, `confidence: number | null` matching the four Go pointer fields in `causalVerificationDTO`, and a `CausalVerificationStatus` union of the six statuses), plus wrappers `getCausalGraph(id)`, `correctCausalEdge(id, {op, from, to, direction?})`, `verifyFinding(id, interventionID)`, `listCausalVerifications(id)` beside `listVerifications`/`resolveVerification`.

2. **Build the causal-graph view with correction interactions and stale/provenance indicators.**
   - Create `web/lib/causal.ts`: graph normalization (column layering for layout, edge endpoint resolution), epistemic derivation from a causal-verifications list keyed by `intervention_id` (unknown/missing ⇒ `observational`, per R13 forward-compat), analyst-language status mapping (`causally_verified` → "Causally supported (given the discovered model)"; `confounded` → "Explained by a shared cause — not causal"; `not_identifiable` → "Can't be answered from this data (no valid adjustment)"; `unsupported_objective` → "This objective type can't be causally verified"; `failed`/`pending` accordingly), and the correction-request builder. Colocate `web/lib/causal.test.ts`.
   - Create `web/components/CausalGraph.tsx`: fetches `getCausalGraph` + `listCausalVerifications`; renders nodes/edges as hand-rolled SVG (columns of nodes, edge paths with arrowheads for `a_to_b`/`b_to_a`, plain lines for `undirected`), each edge labeled with provenance + confidence and an epistemic badge; a 404 renders an empty-state Callout ("No causal graph discovered yet").
   - Correction interactions on edge selection: **flip direction**, **delete edge**, and **add confounder** (pick two columns from `columns`) posting via `correctCausalEdge`; reuse the VerificationQueue interaction: pending `Button` state, optimistic edge update on 2xx, `OrchestratorError.status === 409` → conflict notice + `generation`-bump refetch, 422 error surfaced verbatim.
   - Stale indicators: render a `warn`-tone "re-verifying" badge on edges/verifications where `stale === true` or after a `causal_graph_corrected` event with `redispatched` results, cleared when the refetched record is fresh.
   - Register a `causal` tab in `web/components/GoalTabs.tsx` `TABS` (`:10`) with the same lazy mount-on-visit behavior as `verify`/`agent`.

3. **Add verify affordances + epistemic badges to finding/triplet surfaces.**
   - Add an `EpistemicBadge` component (thin `Badge` wrapper, local to a shared spot such as `web/components/CausalGraph.tsx` export or `ui.tsx` if reused across ≥2 files): `causal_inferred` → positive tone with the exact caveat string "causally supported (given the discovered model)" attached (visible `title` and adjacent caption where space allows — the caveat must be carried, not hidden); `observational` → neutral tone.
   - `web/components/EffectReadout.tsx` triplet card (`:13`): add a fire-and-forget **Verify** `Button` dispatching `verifyFinding(id, interventionID)` — `QueryTripletPayload` carries `intervention_id`, and the goal `id` is threaded as a new prop through LiveRun's render tree (`LiveRun` → `Feed` (`LiveRun.tsx:488`) → `EffectReadout` at `:581`), which is a small render-only change to LiveRun. On 202 flip to a pending state with a "result on the Causal tab" hint; surface 404/502 `{error}` copy verbatim via `errorMessage`. **No epistemic badge on the live card**: the join input (the causal-verifications list) has no producer inside `LiveRun`, and verifications for just-emitted findings essentially never exist yet, so the badge would be uniformly `observational` — noise, not signal. Badges render where edges render (causal graph, verification results) and on goal-scoped HeuristicBrowser rows, which keeps the R32/R13 "wherever edges render" contract intact.
   - `web/components/HeuristicBrowser.tsx` `EvidenceRow` (`:257`) has **no goal context by default**: the `/heuristics` page's `goalId` filter defaults to `""` (all goals, `:32/:60`), `TraceTriplet` carries no goal id, and `handleVerifyFinding` 404s when the intervention belongs to another goal (`causalverify.go:80`). Scope the affordances accordingly: when the analyst has set the goal filter (`goalId` non-empty), fetch that goal's causal-verifications once per search, join on the trace's nested `intervention.id` (not a flat `intervention_id` — the trace DTO nests it), and render `EpistemicBadge` + **Verify** (dispatching `verifyFinding(goalId, intervention.id)`); when browsing all goals, render neither — there is no goal to verify against client-side. Cross-goal badges are the DTO-extension follow-up noted under Verification.

4. **Build the verification-result view with caveated analyst-language outcomes.**
   - Create `web/components/CausalVerifications.tsx` rendered inside the `causal` tab below the graph: newest-first cards per `CausalVerification` showing naive vs adjusted effect side by side (null-safe `fmt`, `—` while pending), the `adjustment_set` (chips; empty set stated as "no adjustment needed"), `refutation_score`, and the analyst-language outcome line from `web/lib/causal.ts` — with the sufficiency caveat sentence attached to every `causally_verified` result ("given the discovered model; unmeasured confounding cannot be ruled out").
   - Outcome badges as a local `StatusBadge`-style tone map covering all six statuses: `causally_verified` positive, `confounded`/`not_identifiable`/`unsupported_objective` warn, `failed` negative, `pending` neutral — with an explicit default arm (unknown status → neutral, label rendered verbatim) so a future status never crashes or vanishes.

5. **Wire SSE so verification transitions appear live on the goal view.**
   - Extend the event union in `web/lib/orchestrator.ts` with three top-level frame types: `verification` (whose `payload.type` carries the transition name — `verification_dispatched`, `verification_refutation`, `verification_outcome`, `verification_rejected`, `verification_error`, or a `claim_*` frame), `causal_verification_dispatched`, and `causal_graph_corrected`. **LiveRun's `handleEvent` switch needs no change**: it has no default arm and silently ignores unmatched frame types (`:121`), so causal frames on its stream are harmless; the union extension exists for the causal-tab hook's typing. (LiveRun's render tree does change — the goal-`id` prop threading in Step 3 — but its event handling does not.)
   - Because `PublishLive` drops events once the run's `runState` is evicted (see Pattern Survey delivery constraint), LiveRun's stream alone cannot carry post-completion verification transitions. The causal tab owns its own subscription: while mounted, `CausalGraph`/`CausalVerifications` (via one shared hook in the causal tab component) open the existing `/api/orchestrator/goals/{id}/stream` route with `consumeStream`, filter for the three frame types above, and bump a local `generation` counter that triggers refetch — `Hub.Subscribe` lazily creates the `runState`, so delivery works regardless of run phase, and multiple subscribers per goal are supported. **Re-subscribe on stream end, refetch on every (re)subscribe**: `Hub.Complete` at loop end closes the causal tab's channel too, and `consumeStream` resolves without reconnecting — so on a clean stream end the hook reopens the stream after a short delay (mirror LiveRun's `onStreamEnd` → `scheduleReconnect` idiom, `LiveRun.tsx:156-166`); the fresh Subscribe lazily creates a loop-less `runState` and delivery of post-completion outcomes proceeds. Every (re)subscribe also bumps the `generation` counter to refetch the verifications list — an outcome published in the eviction→reconnect gap is dropped by `PublishLive`, and since the tab never remounts, only this read reconciles it (otherwise the card sticks at pending). Distinguish the error path: a fetch failure or non-ok stream response backs off (e.g., doubling delay, capped) instead of retrying at a fixed interval forever — unlike LiveRun, this hook has no terminal state to stop it. The subscription **persists across tab switches** (GoalTabs hides, never unmounts, visited tabs — `GoalTabs.tsx:26-33`); abort the connection and cancel any pending reconnect timer only in the React effect cleanup on component unmount (page navigation).
   - Belt-and-braces refetch independent of SSE: refetch the causal-verifications list immediately after a 202 from `verifyFinding` and refetch graph + verifications after a 2xx from `correctCausalEdge` — these confirm dispatch (the pending row appears at once); recovery of a *terminal* outcome whose frame was dropped is handled by the refetch-on-(re)subscribe above, and together they make a dropped stream degrade to eventually-consistent reads rather than a stuck pending card.

## Live-Delivery Invariant

Every claim that a UI element updates "live" must trace the full event path — emitter → hub `runState` existence → subscriber lifecycle → reconnect → reconciling read — before it is believed; each hop has already produced a worked failure during planning:

1. **Envelope**: verifier-relayed frames arrive wrapped (`type:"verification"`, transition at `payload.type`) — top-level switch cases for the inner names never match.
2. **Publisher gate**: `PublishLive` silently drops when no `runState` exists — delivery requires some client to hold an open subscription at publish time.
3. **Subscriber teardown**: `Hub.Complete` closes every subscriber channel and `consumeStream` does not reconnect — a subscription without stream-end handling goes permanently deaf at loop end.
4. **Reconciliation**: refetches that fire only at dispatch time cannot recover a terminal outcome whose frame was dropped in the eviction→reconnect gap — every (re)subscribe must also refetch.

Any implementation deviation in Step 5 (or a future surface consuming these events) must be re-checked against all four hops, not just the one it touches.

- `go test ./internal/orchestrator/ -run TestHub` — the hub's eviction rule: a subscriber-created state reaped on the last cancel, a loop's state retained until `Complete`, `PublishLive` resurrecting nothing after it, and a stale cancel not deleting a successor state.

  - Causal tab shows the discovered graph with provenance + confidence per edge; before discovery a fresh goal shows the 404 empty state, not an error.
  - Click **Verify** on a finding card → button enters pending, `causal_verification_dispatched` then a wrapped `verification` frame carrying `payload.type: "verification_outcome"` arrive on the causal tab's own subscription, and the verification card fills in naive vs adjusted effect, adjustment set, and refutation score without reload — **including when the run has already completed** (the post-completion path is the one `PublishLive` would otherwise drop). If analysts need epistemic badges on cross-goal traces, the fallback is an orchestrator DTO extension adding `epistemic_source` (and a goal id) to triplet payloads — a small follow-up, out of this plan's scope.
